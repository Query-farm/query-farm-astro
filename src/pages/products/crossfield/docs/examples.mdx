Start with the fulfillment example from the homepage, or choose investment reporting below. Each download includes source data, complete models, SQL, expected answers and verification notes. The other examples explore specific modeling and execution behaviors.

The bundles contain data and definitions, not binaries. **[Request evaluation access](/company/contact)** for a matching development engine and Crossfield extension before running them. Crossfield will ship in an upcoming Haybarn release; see [release details and build requirements](/products/crossfield/docs/compatibility). These local examples need no source checkout, Python package or API account.

## Run a bundle

For the fulfillment example, download [fulfillment.zip](/crossfield/examples/fulfillment.zip), extract it and start a fresh CLI from the extracted `fulfillment` directory. Replace both build paths:

```sh
unzip fulfillment.zip
cd fulfillment
/path/to/matched/haybarn -unsigned -init /dev/null :memory: \
  -cmd "LOAD '/absolute/path/to/crossfield.duckdb_extension';" \
  < session.sql
```

For an interactive session, omit the input redirection and run:

```sql
.bail on
.read setup.sql
.read run.sql
.read explain.sql
```

For another bundle, substitute its archive and extracted directory and use the CLI from its recorded build; earlier binaries may be named `duckdb`. Relative paths resolve from the extracted directory. Run setup once per fresh connection. Applications can execute the SQL in setup and run files; `.read` and `.bail` are CLI commands.

## Complete orders, delivered on time

[Download fulfillment.zip](/crossfield/examples/fulfillment.zip) · [walkthrough](/products/crossfield/docs/fulfillment) · [setup](/crossfield/examples/fulfillment/setup.sql) · [verification](/crossfield/examples/fulfillment/verification.txt)

Four eligible orders show why on-time shipments and on-time complete orders are different measures. Incomplete orders remain in the denominator; canceled orders and other due dates are excluded. Source preparation creates one stored fact per order.

| Question | Independently expected answer |
|---|---|
| Complete orders on time | 2 of 4 · 50% |
| Delivered shipments on time | 5 of 6 · 83.3%, a different measure |
| Use revised promises, retaining the original cohort | 50% → 75% · +25 percentage points |

The current and revised models read the same source facts. The source cutoff is fixed; this fixture does not automatically refresh order facts.

## Ossie dataset metrics

[Download ossie.zip](/crossfield/examples/ossie.zip) · [model](/crossfield/examples/ossie/model.ossie.json) · [queries](/crossfield/examples/ossie/run.sql)

Orders and returns each define a local metric named `revenue`. The orders model’s logical `amount` doubles the physical amount; returns uses its own amount directly.

```sql
SELECT orders.revenue AS sales, returns.revenue AS refunds
FROM SEMANTIC local_metrics.scoped_sales;
-- 84 | 7
```

The answer follows `2 × (10 + 20 + 5 + 7) = 84` and `3 + 4 = 7`; the NULL order amount is ignored by SUM. The full regression model also contains explicitly Crossfield-specific definitions. Read [the Ossie boundary](/products/crossfield/ossie) before treating it as a portable model.

## Measurement intervals

[Download measurements.zip](/crossfield/examples/measurements.zip) · [model](/crossfield/examples/measurements/models/utc.crossfield.json) · [queries](/crossfield/examples/measurements/run.sql)

Four rows demonstrate two locations, a midnight boundary and unequal measurement durations. ICU is required. Expected rainfall is A/January 1: **5 mm**, A/January 2: **7 mm**, B/January 1: **11 mm**. A’s January 2 duration-weighted flux is **40 W/m²**.

Run `reject.sql` separately after setup to see an interval mean rejected without its approved reduction. The [measurement guide](/products/crossfield/docs/time-and-measurements) explains why this is different from grouping timestamp labels. This local fixture does not use or qualify a live weather worker.

## Model-owned pipeline

[Download pipelines.zip](/crossfield/examples/pipelines.zip) · [model](/crossfield/examples/pipelines/model.crossfield.json) · [queries](/crossfield/examples/pipelines/run.sql)

One canonical model exposes a direct input and an approved driver/stage pipeline. The direct call `arithmetic.numbers(5)` and equivalent named `stop => 5` return count **5**, sum **10**. The alternative `seed => 4` executes the model-owned dependency and returns count **3**, sum **6**.

The [retrieval guide](/products/crossfield/docs/providers) explains those stages and distinguishes this native pipeline from worker-internal API traversal.

## Discovery and repair

The [AI agent guide](/products/crossfield/agents) uses the retail model. Its metadata queries discover the attached revisions, metric meanings and compatible dimensions before querying. In strict mode, `SUM(subtotal)` against `warehouse.orders` is rejected; the approved before-tax `revenue` is **6355.00**. The tax-inclusive `order_total` is **6730.75** and answers a different question.

The native [discovery and repair capture](/crossfield/examples/agent-session.txt) includes the actual structured rejection and approved results. It is an engine session, not a claim about a particular AI agent framework.

## What the evidence establishes

Expected answers are specified from the fixture values independently of generated SQL. Native execution of the extracted downloads is checked on the maintained EC2 build with the optimizer enabled and disabled. [Build and verification details](/crossfield/examples/verification.txt) distinguish fresh execution from earlier integration evidence.

The bundles record their source files and hashes. Passing these bounded cases does not establish arbitrary connector compatibility, a current source snapshot, or the correctness of a new business definition. Add numerical and rejection cases for your workload.
