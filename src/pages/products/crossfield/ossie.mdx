## Give teams a definition they can inspect and maintain

A metric should remain understandable when a report is rebuilt or a new AI application starts using the data. Recording its definition in a model gives the team a place to review the calculation, its source fields and its relationships independently of any individual report.

[Apache Ossie (incubating)](https://ossie.apache.org/) defines a format for exchanging semantic metadata across tools. Its vocabulary includes datasets, fields, relationships and metrics. Crossfield reads a documented subset of that format and adds the rules needed to execute approved queries in DuckDB.

Crossfield is independent Query Farm work. It is not an Apache product or a certified implementation. Supported expressions and execution policies still need checking when moving a model between engines.

## Describe a calculation the business recognizes

## Understand what each part supplies

| Part | What it does in this example |
|---|---|
| Ossie model | Describes fills, their fields and the execution-price expression. |
| Crossfield policy | Defines the allowed query interface, active-fill population, units and aggregation rules. |
| Crossfield SQL | Lets a caller attach the model, discover its members and select the named metric. |
| Haybarn engine integration | Lets Crossfield validate the query while DuckDB binds and executes it. |

`FROM SEMANTIC` is Crossfield’s query syntax; Ossie does not mandate it. Accepting an Ossie document also does not grant permission to execute every expression or provider it describes. Crossfield requires its explicit policy and resolvable source dependencies.

For a full authoring example, see [models and their policies](/products/crossfield/docs/models). That retail example also demonstrates a Crossfield extension: a root metric referencing another root metric. Qualified logical-field dependencies in field recipes are another extension to the supported profile.

## Check the compatibility profile you need

The reviewed profile follows the [core specification at revision 01a5488](https://github.com/apache/ossie/blob/01a5488d840deda309aac68cc0b312c195369b8d/core-spec/spec.md) and its [expression language](https://github.com/apache/ossie/blob/01a5488d840deda309aac68cc0b312c195369b8d/core-spec/expression_language.md). The core document identifies itself as draft version `0.2.0.dev0`.

Crossfield supports dataset-scoped metrics and local-field resolution in this profile. Expressions require a supported dialect, optional function families have limits, and Ossie’s relational `AGG()` draft is not implemented. Decimal `AVG` has a result-type difference: DuckDB returns DOUBLE where the reference profile expects decimal semantics.

The [small Ossie compatibility example](/products/crossfield/docs/examples#ossie-dataset-metrics) tests field resolution independently of the trading example. Its deliberately simple `raw_amount * 2` field produces an orders metric of 84; a separate returns dataset produces 7. This checks whether the compiler honors the declared field and keeps identically named dataset metrics separate.

The exact limits are recorded in `docs/MODEL_FORMAT.md` and `docs/PUBLIC_WORKLOADS.md` in the Crossfield checkout. Use [model validation](/products/crossfield/docs/validation) for structural and authoring checks, then test the numerical answers your reporting depends on.

The [Apache project](https://ossie.apache.org/) and [public specification](https://github.com/apache/ossie/tree/01a5488d840deda309aac68cc0b312c195369b8d/core-spec) are the authoritative places to follow Ossie’s development. The model format makes definitions available for inspection and exchange; each engine’s supported behavior determines how they can be executed.
