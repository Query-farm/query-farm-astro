**Three visitors on the first day, three on the second, two on the third. Eight people?** Only if nobody returned. In our sample, several did: the three days contain five distinct visitor IDs.

We will calculate the exact answer first, then build daily sketches that can be combined later. The key idea is preserving enough information about overlap to estimate a union, instead of adding incompatible counts.

## Establish the exact answer

Compare the sum of daily counts with an exact distinct count over the entire period:

<TutorialExample example={demo.examples[1]} />

Eight daily memberships belong to five distinct IDs. `SUM` is appropriate for additive measures such as event counts. A distinct count is not additive across overlapping groups.

If your raw data is available and an exact `COUNT(DISTINCT visitor_id)` meets your needs, use it. This tiny example does not need approximation. It exists to make the overlap visible before we introduce a technique for storing compact, mergeable summaries.

## Store a daily sketch, then merge it

Query.Farm's [DataSketches extension](/products/extensions/datasketches/) can build an HLL sketch from IDs and estimate the distinct count represented by it. The setup creates `daily_sketches` with one `datasketch_hll(12, visitor_id)` value per day. The `12` controls sketch size and accuracy; it is not a requested number of visitors.

Merge those saved sketches, then ask for an estimate:

<TutorialExample example={demo.examples[2]} />

The merge operates on sketch state, not on the displayed daily estimates. An estimate alone has lost the information needed for a union. That is the useful distinction between saving a count and saving a mergeable sketch.

Our result rounds to 5.00, matching the exact answer. **That agreement on five IDs is not an accuracy guarantee.** Sketches are approximate; larger inputs can produce estimates above or below the exact count. Rounding improves presentation, not accuracy.

Keep the sketch family, ID representation, and configuration consistent across partitions. Test the chosen settings against exact counts on representative samples before deciding the error is acceptable.

## Choose a smaller reporting window

Because each daily sketch is stored separately, we can select the days we need and combine only those summaries. The first two days contain four distinct IDs even though their daily counts sum to six.

## What this technique saves—and what it does not

Building a sketch still requires reading its input records. The reuse happens afterward: a rolling-period estimate can read the saved daily summaries instead of all the original events. Measure that tradeoff on the size and update pattern you actually have.

Ordinary HLL union does not provide subtraction. If an older partition is corrected, rebuild or replace that partition's sketch and recompute the requested union; do not subtract its previous estimate from a total. Preserve raw data according to the accuracy and correction requirements of your system.

Use exact aggregates when the result must be exact, including reconciliation of charges. Use mergeable sketches when compact reusable summaries and an understood approximation fit the question.
