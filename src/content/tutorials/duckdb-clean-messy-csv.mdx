**A CSV can load successfully and still contain unusable invoices.** “Pending” is not an amount, February 30 is not a date, and a negative number may violate the rules even though it parses perfectly.

We will keep the original text, convert it deliberately, and split the results into accepted records and a review queue. The goal is a useful clean result with an explanation for everything excluded.

## Start with the export's conventions

Our fictional invoice export uses ISO calendar dates, a period for decimal fractions, and optional commas as thousands separators. Amounts must be nonnegative. These are invoice rules; refunds would need a different policy.

The setup writes a real CSV, then reads it with `all_varchar = true`. That preserves troublesome values as text instead of asking type inference to decide what they mean. The downloaded CSV contains the same seven records. Its `1,200.00` field is quoted so the comma belongs to the amount, not the column separator.

## Separate parsing from acceptance

Trim whitespace, remove the thousands separators permitted by this export, and try the conversions:

<TutorialExample example={demo.examples[0]} />

`TRY_CAST` returns NULL for an amount it cannot convert. [`try_strptime`](https://duckdb.org/docs/2.0/sql/functions/dateformat) does the same for a date that does not match the chosen format or calendar. We use `DECIMAL(12,2)` for the invoice amount so the representation has a declared precision and scale.

The original strings remain in `raw_invoices`; `parsed_invoices` adds the converted columns. This matters because a NULL conversion result could mean a missing value or an invalid value. If you overwrite the raw text, you lose that distinction.

Removing commas is appropriate only because the export convention is known. In a decimal-comma locale, `19,95` could mean 19.95. Blindly removing punctuation would turn it into 1995. Likewise, values with more than two fractional digits need an explicit rounding or rejection rule before this pattern is used for them.

## Give excluded rows a reason

The `reviewed_invoices` view in the setup assigns the first applicable issue: invalid date, missing amount, invalid amount, or negative invoice. A row with no issue is accepted.

<TutorialExample example={demo.examples[1]} />

Record 5 has a perfectly parseable amount but an impossible date. Record 6 has a valid negative decimal but breaks our nonnegative-invoice contract. Merely filtering out NULL amounts would admit both.

A first-issue label keeps this example readable. In a fuller quality report, use separate boolean checks or a list of issues when one row can fail several independent rules. Keep the raw ID and fields so someone can investigate or correct it.

## Distinguish malformed CSV from invalid values

Our file has valid CSV structure. A broken quote or an unexpected number of columns is a different failure, encountered while reading the file. DuckDB's [CSV reject tables](https://duckdb.org/docs/2.0/data/csv/reading_faulty_csv_files) can retain information about rejected lines when `store_rejects` is enabled. Inspect those separately rather than assuming the value-validation view received every physical line.

For a recurring import, record the source filename and batch identifier alongside both accepted and review rows. Count parser rejects as well as value rejects. The next useful step is [choosing the latest record per key](/tutorials/duckdb-latest-row-per-group/) when a later export contains corrected invoices or repeated customer updates.
