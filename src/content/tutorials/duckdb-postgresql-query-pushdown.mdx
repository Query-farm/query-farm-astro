**A query that returns four rows might fetch thousands to calculate them.** When DuckDB queries a remote database, it can sometimes push the aggregate to that server and receive only the totals. In other cases, it fetches the input rows and aggregates locally.

That boundary depends on the connector, its version, and the expressions in your query. If a query feels slow, finding where the work happens gives you a useful place to investigate.

## Find the boundary when a query is slow

You can cross that boundary by changing an expression, too. In our tested connector build, `sum(length(status))` fell back to local aggregation—even though PostgreSQL has a `length` function. The connector must support translating the complete expression safely. Its [dialect checks](https://github.com/Query-farm/adbc_scanner/blob/02ccfac995/src/adbc_sql_dialect.cpp) determine what it can translate; support can change between releases.

For your own query:

1. **Inspect the plan.** Prefix it with `EXPLAIN`. Look for the aggregate in generated remote SQL, or a local grouping operator above the remote scan. Operator names and details vary by connector.
2. **Measure the work.** Use `EXPLAIN ANALYZE` when you are ready to execute the query. Compare rows entering the local aggregate with rows leaving it, and inspect operator timings. A large reduction tells you many input rows arrived for a small answer.
3. **Try one change.** Simplify a suspect expression and inspect the plan again. Check that the results stay equivalent before comparing elapsed time. Record the engine, connector, and driver versions.
4. **Follow the evidence.** If the aggregate already runs remotely, inspect the remote query's plan and server-side work. If it runs locally, investigate the rows being fetched and the local operators.

Fewer transferred rows can help, but they do not prove a faster query. Remote aggregation also consumes server resources. The useful skill is knowing which side is doing the work, then measuring that work.
