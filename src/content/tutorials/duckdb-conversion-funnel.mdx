## Define the question before counting

We use the fictional website from the [session tutorial](/tutorials/duckdb-event-sessions/). The full setup is included here too. A new session begins after more than 30 minutes of inactivity.

Our funnel starts at the **first view in each session**. A qualifying run must be strictly later than that view. An enquiry must be strictly later than the qualifying run. Both later steps must fall within 30 minutes of the first view, including the deadline. All three events must share the same user and session.

## Find the first valid next step

Build the sequence in stages. First find the entry timestamp. Then find the earliest eligible run after it. Finally find the earliest eligible enquiry after that run.

<TutorialExample example={demo.examples[1]} />

Notice where the event and time conditions sit: **inside each LEFT JOIN condition**. That preserves an entry when no next step exists, leaving its timestamp NULL. Moving those conditions into a later `WHERE` would remove the dropouts we need to measure.

`min` chooses one qualifying timestamp per stage, so Ada’s repeated run does not duplicate her session. Choosing the earliest eligible run also leaves the greatest possible time for the enquiry under this policy. A later view does not restart this funnel’s fixed clock.

The setup saves these stages as `funnel_steps`; every browser example can run independently.

## Count the journeys that remain

<TutorialExample example={demo.examples[2]} />

Nine sessions contain an entry view. Three proceed to a valid run. Two finish with an enquiry: Ada’s first session and Dee’s session. The entry-to-enquiry rate is **2 / 9 = 22.22%**.

`count(*)` counts all entries. `count(ran_at)` and `count(enquired_at)` ignore NULL timestamps, counting only reached steps. `nullif` avoids division by zero when a filtered dataset has no entries.

## Match the metric to the decision

This result diagnoses recorded behavior, not why someone stopped. Missing events, blocked tracking, and a broken form can resemble abandonment. Check instrumentation before drawing a product conclusion from a changing funnel.

To compare acquisition channels, attach the entry session’s channel under a clear attribution rule, then group this result. To ask whether people return later, move to [retention cohorts](/tutorials/duckdb-retention-cohorts/). Keeping those questions separate makes both metrics easier to explain.
