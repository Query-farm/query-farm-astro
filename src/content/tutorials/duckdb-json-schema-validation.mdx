Each order must contain an integer `order_id`, a nonnegative numeric `total`, and a `status` of `paid` or `cancelled`. Extra fields are allowed here: the schema does not set `additionalProperties` to false.

The full schema lives in the one-row `contract` table in the setup. Notice the separation between `properties`, which describes fields, and `required`, which says they must exist. A property declaration alone does not make a field mandatory.

The browser loads Query.Farm's JSON Schema extension for you. The downloaded walkthrough includes installation instructions for native DuckDB 2.0. The [extension reference](/products/extensions/json_schema/) covers other supported versions and its draft-07 target.

## Check the schema before checking the batch

Run the schema check on its own, outside any error-catching wrapper:

<TutorialExample example={demo.examples[0]} />

This verifies that the validator can load our contract. Also test it with known passing and failing documents: an accepted schema can still describe the wrong business rule.

This ordering matters because `TRY` catches errors in the schema as well as errors in a document. If you put a broken contract inside a blanket `TRY`, every incoming record could look like bad data when the real fault is the contract itself.

## Turn document failures into a visible classification

The extension returns true for a conforming document and raises an error when validation fails. For a batch classification, catch that failure and map it to false:

<TutorialExample example={demo.examples[1]} />

Records 1 and 2 pass. Record 3 has a string total, record 4 has a negative total, and record 5 lacks status. Our wrapper also treats record 6's SQL NULL as invalid.

`TRY` does not repair any of these records. The original payload stays unchanged. This is a classification that lets a later query route or inspect records without abandoning the entire batch on the first failure.

The extension does not return a structured list of failed keywords. The original payload and the schema remain the evidence for investigation; run validation on an individual failing record when you want its textual exception. For this small fixture, the mismatches are visible directly in the input table.

## Make the quality gate countable

A summary should account for the entire batch:

<TutorialExample example={demo.examples[2]} />

Six received, two accepted, four rejected. Persist a batch identifier and schema version alongside those outcomes in a recurring pipeline. That lets someone distinguish a changed source from a changed contract.

Validation and business filtering are separate steps. A cancelled order can be structurally valid. Conversely, the presence of the text `paid` does not prove that the rest of the document is acceptable.

## Where this check belongs

This lesson starts with parsed JSON. Malformed JSON text fails earlier, before the contract can inspect its fields; retain parsing failures as a separate category in an import workflow.

For fixed relational data, typed columns and SQL constraints may be a simpler way to express requirements. JSON Schema is useful when a JSON document is the thing whose structure you need to check. Validate it once at the boundary where the result becomes useful, rather than repeatedly on every dashboard query.

Once the contract passes, [flatten the nested data](/tutorials/duckdb-nested-json/) using a deliberate rule for empty arrays. Keep the raw payload available until the resulting tables have been reconciled with the input.
