**Yesterday’s export had an ID and an amount. Today’s adds a coupon column—and one amount says “pending.”** You want all four rows without silently losing the new field or pretending every value is usable.

We will solve the two separate problems: combine the schemas, then validate the values. The browser creates real CSV and Parquet files from the sample tables, so the queries exercise the file readers.

## Ask for the union of column names

<TutorialExample example={demo.examples[0]} />

[`union_by_name`](https://duckdb.org/docs/2.0/data/multiple_files/combining_schemas) asks the reader to combine the discovered column names. Missing fields become NULL. The explicit file list makes this small experiment reproducible; a glob can cover a larger export directory.

For CSV, `all_varchar = true` preserves the source fields as text instead of relying on type inference. We cast the known-good IDs deliberately. `parse_filename(filename)` reduces the reader’s provenance column to a readable basename.

This aligns fields, not business meanings. If the exporter renames `amount_text` to `total`, both names become separate columns. Decide whether the fields mean the same thing, alias each source to a common contract, and then combine them.

## Use the same idea with Parquet

<TutorialExample example={demo.examples[1]} />

Parquet already stores column types. Our fixtures deliberately store `amount_text` as VARCHAR in both files, so schema alignment succeeds. We then choose `DECIMAL(10,2)` as the analytical amount type.

`try_cast` converts `pending` to NULL instead of aborting the query. That makes the query run, but it also introduces a review obligation. A later sum would ignore this amount; it would not prove the source value was zero.

`union_by_name` is not a promise that arbitrary incompatible Parquet types can always be reconciled. For incompatible source contracts, read and normalize each source separately before combining the results.

## Keep a conversion audit

<TutorialExample example={demo.examples[2]} />

The original text remains beside the converted amount. ID 4 is marked `review`; the other three rows are accepted under this narrow amount rule. A missing amount would have its own status.

This is the same principle as our [messy CSV lesson](/tutorials/duckdb-clean-messy-csv/): preserve the evidence while making data usable. Avoid passing every row through an aggregate and hoping the total exposes a bad value.

## A small contract goes a long way

For a recurring import, record the expected key, units, field meanings, and required columns. Adding an optional coupon is different from changing dollars to cents. Retain source provenance, audit rejected values, and check duplicate IDs before treating the combined dataset as one authoritative table.
