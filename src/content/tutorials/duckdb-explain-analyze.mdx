## The business question comes first

We want the number of paid orders whose region has at least one promotional campaign. An order qualifies once, however many campaigns its region has.

The fixture contains 10,000 orders, of which 8,000 are paid. Each of the four regions has two campaigns. The expected count is therefore 8,000.

## Follow the actual row counts

The orders scan outputs 8,000 paid rows. The promotions scan outputs eight campaign rows. The inner join outputs 16,000 matching pairs because each order's region matches two campaigns. The final aggregate reduces those pairs to one count.

These are **operator output counts**, not interchangeable measures of stored rows, rows inspected, or network bytes. The full profile separately records scan details. A scan that returns 8,000 filtered rows may have examined more input rows to find them.

The captured join estimate is 10,000, but its actual output is 16,000. Comparing estimates with observations can identify where the planner's expectations diverge. Here, inspecting the join's meaning reveals the more urgent issue: we are counting order–campaign pairs.

In the captured build, DuckDB uses a semi join. It outputs each qualifying order once, leaving 8,000 rows for the aggregate. The exact plan may evolve, but the result and the intended one-count-per-order rule remain the checks that matter.

The rewrite deliberately changes the wrong answer. This is a correctness repair, not an equivalent-query speed comparison. The [join multiplication tutorial](/tutorials/duckdb-join-double-counting/) explores the same mistake on five visible item rows.

## Interpret timings with care

Operator timings help locate expensive work, but adding them is not a reliable way to reconstruct total elapsed time. Parallel execution and the way operator work is recorded matter. Use the reported query total as its own measure, and inspect the execution environment before interpreting a timing difference.

This tiny fixture is useful for row counts, not a performance benchmark. One cached run may differ from a cold run; profiling and browser startup have costs of their own. For a real optimization, keep input data and environment comparable, verify equivalent results, and repeat representative measurements. Record the engine and extension versions.
