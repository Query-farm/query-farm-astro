Your next DuckDB function could be five minutes away. Describe what it should do, choose the language you want to use, and let your coding agent build a [VGI worker](/vgi/), run it, and check the results through SQL.

We tested that workflow with real Codex and Claude Code sessions. They started in empty projects, wrote workers, installed dependencies, and ran their tests. A separate verifier then queried the generated workers through a real SQL engine. The initial runs used Haybarn; the same generated workers also pass on stock DuckDB 2.0.0. The source and tests are available for you to inspect and rerun.

[See the recorded build and measured results →](/vgi/build-with-an-agent/#recorded-build)

## Give the agent a way to finish

VGI makes an ordinary program available as typed SQL functions, tables, and catalogs. The worker runs in your chosen language, with access to that language's libraries. VGI carries inputs and results as Arrow data.

That gives a coding agent a practical development loop: implement the function, start the worker, attach it to the engine, execute a query, and compare the returned rows with the expected result. When something fails, the agent can inspect the error and try again.

The SDKs and local tooling are now mature enough to support this loop. Our [portable skills](https://github.com/Query-farm/vgi-skills) supply the version-specific details, testing helpers, and handoff requirements:

- **vgi-worker** builds or extends a worker and verifies its SQL behavior.
- **vgi-test** diagnoses an existing worker and adds repeatable SQL checks.
- **vgi-package** prepares a local archive, integrity manifest, and runtime instructions, then tests the extracted artifact.

Install the skills for Codex or Claude Code, or use the same portable package with Cursor, GitHub Copilot, and OpenCode. We have run live evaluations in Codex and Claude Code and checked installation for all five. The [evaluation report](https://github.com/Query-farm/vgi-skills#examples-and-compatibility) distinguishes those checks.

## You choose the language

The worker can use **Python, TypeScript, Go, Rust, Java, or C#**. Choose the language that fits your project and libraries. For a new project without a language choice, the skill asks; for an existing worker, it preserves the project's language and tooling.

The [quickstart](/vgi/build-with-an-agent/#start) prepares a prompt for your agent, language, and starting idea. Start with a small function, wrap an API as a table, or expose a dataset as a discoverable catalog. You can edit the prompt before copying it.

For our recorded example, we chose TypeScript and asked for a slugification function: lowercase text, normalize accented Latin characters, replace punctuation with hyphens, and preserve SQL NULL. The generated worker passed these queries:

The independent verifier also checked 10,000 input rows. The resulting project includes the worker, dependency lockfile, unit tests, and a manifest of SQL assertions. You can [inspect the recorded source and results](/vgi/build-with-an-agent/#recorded-build), then substitute your own function.

## About those five minutes

The recorded Claude Code TypeScript session on stock DuckDB completed in 1 minute 38 seconds, including its own tests. Independent verification took another second. A fresh Codex Python session on stock DuckDB took 4 minutes 19 seconds. An earlier Codex TypeScript session on Haybarn took 5 minutes 19 seconds. We publish all of them, alongside the other completed build runs.

These are small local examples on macOS, with shared package caches and the CLIs' configured models. They establish that an agent can complete the workflow today. They do not establish a universal time or success rate, or a ranking of models. New toolchains, dependency downloads, API authentication, and larger applications add work.

The useful promise is concrete: you can finish with source, a running worker, and SQL results that were actually checked. An estimate alone cannot provide that.

## A SQL capability you can keep extending

The five-minute starting point adds a capability through the VGI engine extension. Your artifact is a worker in your chosen language; a native `.duckdb_extension` binary is a different build and distribution path.

The quickstart now uses stock DuckDB 2.0.0. Configure the [Query Farm extension repository](/blog/duckdb-2-query-farm-repository/), then use `INSTALL vgi FROM query_farm` and `LOAD vgi FROM query_farm`. We verified the generated workers on macOS ARM64. [Haybarn](/products/haybarn/) is also tested and remains an option for existing projects.

Once your first worker passes, ask the agent to expose another function, add an option, or connect it to your own library. It can make the change and rerun the tests. When you are ready to share it, choose a [distribution method](/vgi/distributing-a-worker/) that fits your application.
