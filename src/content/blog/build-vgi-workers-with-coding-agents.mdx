An order can look profitable until you include shipping.

Your order table already has revenue, product cost, destination, and parcel weight. DuckDB can read it from a CSV, a Parquet file, or your database. **But the shipping rule lives in your application.** It may belong to a Java library, a Python package, or an API client your team already maintains.

To answer “which orders lose money after delivery?”, the query needs that code's answer. Therefore, make the function available where you're asking the question.

That's what **VGI—the Vector Gateway Interface—does**. It lets DuckDB call code running in another program. That program is a *worker*: ordinary source in your chosen language, using its normal packages and tools. The VGI extension discovers the worker's typed functions and makes them available from SQL.

## Keep the rule where it belongs. Bring its answer into the query.

In our example, the worker exposes `shipping.main.quote_cents(destination, weight_g)`. It returns a shipping estimate in integer cents. DuckDB can use that value in the same expression as the revenue and product cost it already holds.

<WorkerQueryFlow />

The query runs in DuckDB. The shipping function runs in the worker. VGI carries the inputs and outputs as typed Arrow columns, so the worker can handle batches of rows. A coding agent can write this program, but it isn't asked to invent a shipping price each time you run a query.

The result is a boundary you can understand: SQL owns the report; the library owns its rule.

## One quote proves the connection. But the useful question is bigger.

Start with a 500g parcel to the US. Our sample function returns $5.50. That's deliberately small enough to inspect.

You could write this tiny rate formula directly in SQL. Here it stands in for a shipping library: the benefit becomes clear when your application already owns the rule, or when the calculation depends on a package or service you want to keep using. Wrapping that code lets the query use the same implementation.

**But one quote does not identify the orders that need attention.** Therefore, call the function with the destination and weight columns from the order table, and use the returned prices to calculate margins.

<ShippingStory id="article-shipping-story" heading={false} />

Two sample orders now have negative margins: A-103 loses $2.50 and A-102 loses $2.00 after shipping. That is a report someone can act on.

There is another complication. Our fixture has no Australian rate. If the query only kept negative margins, the NULL calculation could quietly exclude that order. **Therefore, the report also keeps missing quotes visible.** A-105 needs review; it doesn't get a zero-dollar shipping estimate.

The rates and orders are fictional, but the example is executable. We checked these displayed results against a running VGI worker in stock DuckDB, along with NULL handling, weight boundaries, empty input, and 10,000 rows. You can <a href={vgiSkillsFile('examples/shipping-margin/README.md')}>download the source and rerun the checks</a>.

## The worker is useful. But someone still has to build it correctly.

A coding agent can write the function and connect the SDK. It can also make a plausible mistake: return the wrong integer width, put a log message into the protocol stream, mishandle NULL, or stop after the first batch.

That is why the task needs a result the agent can test. “Write a worker” is a starting instruction. “Make these SQL assertions pass through the actual engine, and leave the tests in the project” gives it a way to finish.

<AgentBuildLoop />

We've packaged that workflow into three [portable skills](https://github.com/Query-farm/vgi-skills). **vgi-worker** helps create or extend the worker, **vgi-test** reproduces failures through SQL, and **vgi-package** prepares a local artifact and checks it after extraction.

The skill supplies the SDK details and verification tools. Your agent still works in your project: it writes source, runs commands, reads failures, and fixes the implementation. You keep the code and the tests when the session ends.

## Use the language that already has your library.

The shipping example is written in TypeScript so there is a complete project to inspect. Your worker can use any of the six SDK languages:

<AgentLanguageMarks kind="languages" />

For a new project, you choose the language. For an existing worker, the skill preserves its language and tooling. A Python verifier does not turn your Java or Rust worker into a Python project.

The same pattern extends beyond a scalar shipping function:

| The missing piece | What a worker can expose | The query it makes possible |
| --- | --- | --- |
| Your application's validation library | Typed functions | Find records that fail the rules your application actually uses |
| An API with paginated results | A table function | Join remote records with a local customer or order table |
| A dataset behind a service | Tables, columns, and a catalog | Discover the available data and query it from SQL |

These are extensions of the same idea: bring the capability to the query, using code your project can maintain. API authentication, pagination, and failures need their own tests; a good first worker gives you a place to add them.

## Could your first worker take five minutes?

For a small, well-specified task, yes. We gave the shipping request to a fresh Claude Code session. It built its own TypeScript worker in 2 minutes 48 seconds. A separate verifier then checked the quotes, the order report, missing rates, NULL handling, empty input, and 10,000 rows through stock DuckDB. Those checks passed in another 1.1 seconds.

Our earlier Codex and Claude evaluations used a smaller slugification task. Some finished faster; one took more than five minutes. These runs used shared dependency caches. They show that an agent can complete the workflow, not that every library, API, or project has the same setup cost. The [full evidence](/vgi/build-with-an-agent/#proof) includes the engine versions, slower runs, and limitations.

The more useful milestone is a passing query. Once you have that, you can ask the agent to replace the sample rate function with your real library and rerun the tests.
