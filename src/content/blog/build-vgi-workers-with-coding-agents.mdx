We gave Claude Code an empty project, a VGI skill, and a request: build a TypeScript function that turns text into URL slugs, preserve SQL NULL, and test it through DuckDB.

**It wrote the worker, installed its dependencies, and ran its tests.** The build finished in 1 minute 38 seconds. A separate verifier checked the generated worker through stock DuckDB, including 10,000 input rows, in another second. No human corrections were supplied during the run.

Here is what that means in one query:

```sql
SELECT demo.main.slugify('Hello, VGI!');
-- hello-vgi
```

The function runs in source code written by the agent. You can inspect it, change it, and rerun the tests after the agent session ends.

## You know the function you want. But how does DuckDB call it?

Your project may already have a useful parser, validator, or calculation. Making that code available inside a query requires a connection between DuckDB and the program that owns it.

**VGI—the Vector Gateway Interface—provides that connection.** VGI is an installed DuckDB extension. A *worker* is a separate program in your chosen language that describes its functions and runs your code. VGI passes typed columns between the query and the worker.

The coding agent's job is to build that worker. It can use the language's normal libraries and tools, and it can run DuckDB to check its work. Therefore, the handoff can be a working query, source, and tests.

The slug function is deliberately small. It makes the request, generated code, and expected result easy to inspect. You could implement it in SQL too; the broader opportunity is to expose code your project already maintains, including packages that belong in another language.

## Generated code needs proof. Therefore, the agent runs SQL.

A worker can compile and still return the wrong type, lose NULL values, or fail when DuckDB sends another batch. A source file alone does not establish that the function works.

The **vgi-worker** skill gives the agent SDK guidance and a real SQL verifier. The request asks it to run the worker, compare actual rows with expected answers, and fix implementation failures before finishing.

In this recorded session, Claude Code ran 11 unit tests and seven SQL checks. Those checks covered accented text, punctuation, SQL NULL, the return type, multiple batches, and empty input. The independent verifier then tested known values, NULL, and 10,000 rows using assertions supplied outside the agent's own tests.

## One string proves the connection. Now use your data.

An article-title CSV gives the function a useful next job: prepare candidate URL slugs. The worker does not need to change. DuckDB reads the file and calls the same function for the title column.

## Your agent. Your language. Your next function.

The recorded example uses Claude Code and TypeScript. We also gave Codex a fresh Python project and the same slugification task. That stock-DuckDB build took 4 minutes 19 seconds, followed by independent SQL verification. Both agents produced working workers.

Live evaluations cover Codex and Claude Code. We verified skill installation for Cursor, GitHub Copilot, and OpenCode too. The skills use a portable format so developers can add the same workflow to their coding tools.

A new project starts with your choice. An existing worker keeps its language and conventions. The skill can guide a Python wrapper around a Python package, a Java wrapper around a Java library, or an equivalent worker in any of the six SDK languages.

The next request can be specific: “Expose this validation function to DuckDB. These inputs should pass; these should fail. Keep NULL visible and test more than one batch.” Workers can also expose tables and catalogs, which opens a path to querying API results or datasets through SQL.

But each new capability brings its own cases to verify. Start with one function and known answers, then expand the tests with the worker. The companion **vgi-test** skill helps diagnose an existing worker, and **vgi-package** prepares a local archive and checks it after extraction.

## Can the first build take five minutes?

Our recorded builds show that it can. They also include a run that took longer. These are small tasks on macOS ARM64 with shared package caches, not a guarantee for every environment or library.
