Since [DuckDB 2.0.0 was released on October 21](https://github.com/duckdb/duckdb/releases/tag/v2.0.0), **seven of our new core fixes have merged**, and **13 new code and build pull requests remain open** across the DuckDB organization. We have also filed **17 issues**, including reports that DuckDB maintainers have resolved with their own fixes.

Building DuckDB extensions and maintaining [Haybarn](/products/haybarn/) exposes problems at the boundaries: named arguments reaching the wrong binding path, browser threads waiting on extension loads, and test paths failing on Windows. An extension cannot repair every part of that chain, so we bring reproductions and proposed fixes to the upstream projects that own it.

The statuses below are current as of **November 5, 2026**. [Rusty Conover](https://github.com/rustyconover) submitted this work on behalf of Query Farm; the [contribution inventory](/media/posts/duckdb-2-upstream-contributions/contributions.csv) lists each submission and its dates. Two older core submissions also merged during this period and appear in a separate section.

## Seven new core fixes have merged

Our extensions need named options to reach the right function arguments. But in a correlated table-function call, DuckDB could treat a named option as another positional input. The same failure reproduces with the built-in `range` function:

```sql
SELECT count(*)
FROM (VALUES (3)) AS input(n),
     LATERAL range(input.n, hello => 123);
```

`range` has no option called `hello`. Before the fix, this query returned a count of 120 because the binder treated `123` as a second positional argument. With the fix, it reports an invalid named argument. Extension functions that declare named options receive those options correctly. [PR #27833](https://github.com/duckdb/duckdb/pull/27833) includes the regression tests.


Fixing the binder therefore helps both built-in functions and extensions. It is one of seven new core fixes that have merged, covering SQL behavior, query execution, and extension testing.

But an upstream merge is only one step toward getting a fix to users. These seven PRs merged into `main` after 2.0.0 shipped, so **they are not included in the released 2.0.0 binaries**, which remain the [latest stable engine release](https://github.com/duckdb/duckdb/releases) at this snapshot. A requested backport still needs to land on the release branch and ship before users receive it in a stable release.

## Open work for extensions and applications

The remaining work needs more than a release containing the merged fixes. Eight new core PRs remain open: some correct existing behavior, while others give extensions information or control that the engine does not yet expose.

<a class="status-badge status-badge--open" href="https://github.com/duckdb/duckdb/pull/27854" aria-label="Open: Map Arrow union type ids to members through the format string (duckdb/duckdb #27854)" title="Map Arrow union type ids to members through the format string (duckdb/duckdb #27854)"><span class="status-badge__icon" aria-hidden="true">○</span>Open</a> **Arrow union correctness.** [#27854](https://github.com/duckdb/duckdb/pull/27854) proposes a fix for how Arrow union type IDs select their members. DuckDB reads the schema's mapping but then uses the raw ID as an index. Data using IDs such as `5,9` can be rejected; swapped IDs can silently select the wrong values. The proposal follows the declared mapping and validates it, addressing an [older report](https://github.com/duckdb/duckdb/issues/21842).

<button type="button" class="status-badge status-badge--open" popovertarget="upstream-statement-checks" aria-haspopup="dialog" aria-label="Open: View 2 pull requests: Statement checks and parser diagnostics" title="View 2 pull requests: Statement checks and parser diagnostics"><span class="status-badge__icon" aria-hidden="true">○</span>Open</button> **Checks and diagnostics for extension-defined SQL.** [#27986](https://github.com/duckdb/duckdb/pull/27986) would let an extension inspect a statement before a PRAGMA expands or a connected catalog executes it remotely. Both arose from [Crossfield](/products/crossfield/), where model definitions can supply information the parser does not have.

- <a class="status-badge status-badge--open" href="https://github.com/duckdb/duckdb/pull/28090" aria-label="Open: Let table functions opt out of Bloom and prefix-range join filters (duckdb/duckdb #28090)" title="Let table functions opt out of Bloom and prefix-range join filters (duckdb/duckdb #28090)"><span class="status-badge__icon" aria-hidden="true">○</span>Open</a> [#28090](https://github.com/duckdb/duckdb/pull/28090) would let a table function request join bounds it can send to another system, instead of Bloom or prefix-range filters that depend on engine memory.

## Build improvements beyond the engine

Correct engine behavior is only part of delivering an extension or browser package. The same code still has to pass through build workflows, and those workflows can repeat work or wait on tasks they do not need. That led to four proposals to shorten the build process; all remain open.

<a class="status-badge status-badge--open" href="https://github.com/duckdb/extension-ci-tools/pull/456" aria-label="Open: Pass VCPKG_HOST_TRIPLET into the Linux Docker build (duckdb/extension-ci-tools #456)" title="Pass VCPKG_HOST_TRIPLET into the Linux Docker build (duckdb/extension-ci-tools #456)"><span class="status-badge__icon" aria-hidden="true">○</span>Open</a> In `extension-ci-tools`, [#456](https://github.com/duckdb/extension-ci-tools/pull/456) would forward `VCPKG_HOST_TRIPLET` into Linux build containers. The workflow sets this variable, but the container does not receive it, so host dependencies such as protobuf and gRPC can build unnecessary debug variants. We found this while building Airport for Haybarn. Passing the variable through would let the container use the intended release configuration.

<button type="button" class="status-badge status-badge--open" popovertarget="upstream-wasm-ci" aria-haspopup="dialog" aria-label="Open: View 3 pull requests: DuckDB-Wasm build improvements" title="View 3 pull requests: DuckDB-Wasm build improvements"><span class="status-badge__icon" aria-hidden="true">○</span>Open</button> Three DuckDB-Wasm proposals would remove avoidable CI work: [#2292](https://github.com/duckdb/duckdb-wasm/pull/2292) would allow compilation to begin alongside test-data generation; [#2294](https://github.com/duckdb/duckdb-wasm/pull/2294) would remove duplicate workflow triggers for new refs; and [#2296](https://github.com/duckdb/duckdb-wasm/pull/2296) would skip native engine source checkouts in JavaScript jobs that consume already-built Wasm.
