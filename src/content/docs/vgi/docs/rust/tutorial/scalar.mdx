The first tutorial step: build a worker with one **scalar** function and call it from SQL — about
**10 minutes**, for first-time VGI users with Rust 1.97+ (the crate's MSRV).

<InfoTip label="What's a “worker”?" title="What's a “worker”?">
A **worker** is a small program DuckDB launches as a subprocess and talks to over Apache Arrow. It
exposes one or more typed functions, and DuckDB calls them like built-ins. It is an ordinary Rust
binary — nothing is compiled into DuckDB, and nothing links against it.
</InfoTip>

<div class="kind-banner kind-banner--scalar"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/scalar.svg" alt="scalar shape" /><div class="kind-banner__text"><code class="kind-banner__formula">1 row → 1 value</code><p class="kind-banner__desc">Runs on each row independently and returns a single value — a pure per-row transform.</p></div></div>

<Callout type="tip" title="Why this is powerful">
`double` is intentionally trivial — DuckDB can already do `n * 2`. The point is that `process` is
**ordinary Rust**: pull in a crate, a model, a `reqwest` call, a parser DuckDB has never heard of,
and DuckDB calls it like a **native SQL function**.
</Callout>

## Step 1 — Write the worker

Create a crate and add the SDK:

<CodeBlock code={`cargo new calcscalar && cd calcscalar
cargo add vgi arrow-array arrow-schema`} lang="bash" tryable={false} />

`arrow-array` and `arrow-schema` are yours to name because your function signature is written in
Arrow types. Keep them on the same major as the SDK — **arrow-rs 59** for `vgi` 0.29.

<Callout type="warning" title="On vgi 0.29.0, pin vgi-rpc as well">
Every trait method returns `vgi_rpc::Result`, and on **0.29.0** that name has to come from a direct
dependency — but the published crate wants `vgi-rpc` **0.21**, while a bare `cargo add vgi-rpc`
installs 0.22. Cargo will not unify them (0.x minors are semver-incompatible), and the mismatch is
not a warning:

<CodeBlock code={`error[E0053]: method \`process\` has an incompatible type for trait
   = note: expected ... -> Result<_, vgi_rpc::errors::RpcError>
              found ... -> Result<_, RpcError>`} lang="text" tryable={false} />

So on 0.29.0, add `vgi-rpc = "0.21"` and import `Result`/`RpcError` from there.

**From the next release this goes away**: `vgi` re-exports the RPC layer, so `use vgi::{Result,
RpcError};` is the right version by construction and `vgi-rpc` leaves your manifest entirely. The
code below is written that way.
</Callout>

Then `src/main.rs`:

<CodeBlock code={workerSrc} lang="rust" title="src/main.rs" tryable={false} />

Four things to notice:

- **The trait is the function.** `ScalarFunction` wants `name`, `metadata`, `argument_specs` and
  `process`; `on_bind` has a default and is only overridden when the return type depends on the
  argument types.
- **Argument types are Arrow type strings.** `ArgSpec::column("n", 0, "int64", …)` — `int64`, not
  SQL's `bigint`.
- **A whole column at a time.** `process` receives an Arrow `RecordBatch`, not one row, and returns
  a single-column batch of the same length.
- **The catalog name is the `ATTACH` name.** They are not independent: attaching under any other
  name fails.

<InfoTip label="New to Apache Arrow?" title="New to Apache Arrow?" width="34rem">
[Apache Arrow](https://arrow.apache.org/) is a language-independent **columnar** memory format.
Rather than rows of objects, data lives in **arrays**: a contiguous, typed sequence of values for a
single column. VGI hands your function a whole column, and operating on it at once is what keeps it
fast across the process boundary. In Rust you work with these through
[arrow-rs](https://github.com/apache/arrow-rs) — `RecordBatch` is a chunk of a table, and
`Int64Array` is one int64 column of it.

<a href="https://arrow.apache.org/" target="_blank" rel="noopener" class="arrow-logo-link"><img src="/vgi/apache-arrow.svg" alt="Apache Arrow" class="arrow-logo" /></a>
</InfoTip>

## Step 2 — Build it

<CodeBlock code={`cargo build --release`} lang="bash" tryable={false} />

A VGI worker is a normal binary, and a Rust one has no runtime to ship alongside it — the whole
worker is `target/release/calcscalar`.

## Step 3 — Start Haybarn

VGI functions run inside a DuckDB-compatible engine. We'll use **[Haybarn](/haybarn)** — start it
from the folder holding the binary you just built:

<CodeBlock code={`npx haybarn@rc`} lang="bash" tryable={false} />

This opens Haybarn's in-memory SQL shell — the `memory H` prompt. (First run downloads the CLI; see
[other install options](/haybarn/install).)

<InfoTip label="Why Haybarn?" title="Haybarn serves the vgi extension">
Haybarn distributes the `vgi` extension through its own channel, so `INSTALL vgi FROM community;`
works out of the box. `vgi` isn't in DuckDB's public community repository, so stock DuckDB can't
`INSTALL` it today — Haybarn is the supported path. The extension is the same one Python, Go, Rust
and TypeScript workers all talk to.
</InfoTip>

## Step 4 — Attach and call it

At the `memory H` prompt:

<CodeBlock code={`INSTALL vgi FROM community;
LOAD vgi;

ATTACH 'calc' (TYPE vgi, LOCATION './target/release/calcscalar');`} lang="sql" tryable={false} />

Now call it:

<CodeBlock code={`SELECT calc.double(21);`} lang="sql" tryable={false} />

<QueryResult columns={["double(21)"]} rows={[[42]]} />

…or over a whole column:

<CodeBlock code={`SELECT calc.double(n) FROM (VALUES (1), (2), (3)) AS t(n);`} lang="sql" tryable={false} />

<QueryResult columns={["double(n)"]} rows={[[2], [4], [6]]} />

Nulls pass straight through, because collecting from `Option` carries them:

<CodeBlock code={`SELECT calc.double(n) FROM (VALUES (5), (NULL)) AS t(n);`} lang="sql" tryable={false} />

<QueryResult columns={["double(n)"]} rows={[[10], [null]]} />

**What just happened:** `ATTACH` launched `./target/release/calcscalar` as a subprocess and
registered `calc.double` in your SQL session. DuckDB handed your Rust the `n` column as a single
Arrow array, `process` ran over the whole thing, and the result streamed back — no row-by-row round
trips. Swap the body for any Rust you like and the SQL above doesn't change.

You've built and run your first VGI function in Rust. 🎉

<InfoTip label="It didn't work?" title="Troubleshooting" width="34rem" up>
- **`error[E0053]: method process has an incompatible type for trait`** — the `vgi-rpc` version
  mismatch above. Pin `vgi-rpc = "0.21"` on 0.29.0.
- **`IO Error: VGI worker not found or not executable`** — `LOCATION` is resolved from the directory
  the engine was started in. Check the path, and that `cargo build --release` produced the binary.
- **`No worker handles catalog 'x'`** — the name in `ATTACH` must equal the `CatalogModel.name`. It
  is not a free alias.
- **The `ATTACH` hangs** — run the binary directly. It speaks Arrow over stdin/stdout, so it *looks*
  like it hangs waiting for input; you're checking for a startup panic on stderr.
- **`Catalog Error: Scalar Function with name double does not exist!`** — the name comes from
  `name()`, qualified by the catalog name.
</InfoTip>
