<a id="AttachValidator"></a>
## <span class="api-icon api-icon--class"></span><span class="api-kind-tag api-kind-tag--class">func type</span> `AttachValidator`

<a class="api-source" href="https://github.com/Query-farm/vgi-go/blob/main/vgi/worker.go#L520" target="_blank" rel="noopener">source</a>

<pre class="api-sig"><code>type AttachValidator func(req *CatalogAttachRequestWire, callCtx *vgirpc.CallContext) (*AttachDecision, error)</code></pre>

<p class="api-section">Description</p>

AttachValidator is invoked by the default catalog_attach handler. It may
inspect the requested data_version_spec / implementation_version, perform
validation, and return resolved values. Returning an error causes the
ATTACH to fail with that message — the test suite treats a "ValueError"
RPC type as a user error the extension should surface verbatim.

<a id="CatalogVersionHook"></a>
## <span class="api-icon api-icon--class"></span><span class="api-kind-tag api-kind-tag--class">func type</span> `CatalogVersionHook`

<a class="api-source" href="https://github.com/Query-farm/vgi-go/blob/main/vgi/worker.go#L613" target="_blank" rel="noopener">source</a>

<pre class="api-sig"><code>type CatalogVersionHook func(attachOpaqueData []byte, callCtx *vgirpc.CallContext) error</code></pre>

<p class="api-section">Description</p>

CatalogVersionHook runs on every catalog_version RPC before the response is
returned. Returning a non-nil error causes the RPC to fail with that
message (wrapped as a ValueError). The hook can inspect call-context
cookies to assert the HTTP cookie jar is round-tripping correctly — a
useful regression check for versioned workers that set a sticky cookie at
ATTACH time.

</div>

catalogOfAttach names the catalog an unwrapped attach plaintext belongs to.
Every function is homed in exactly one catalog, so both the function listing
and bind dispatch need one catalog name per request — this is where it comes
from.

Writable catalogs mint their own "writable:&lt;name&gt;" plaintext, so their name is

replaced it with its own encoding (a resolved data version, encoded ATTACH
options), or no attachment at all — resolves to the worker's own catalog,
which is the only catalog such a worker can mean.

<a id="funcOrigin"></a>
## <span class="api-icon api-icon--class"></span><span class="api-kind-tag api-kind-tag--class">struct</span> `funcOrigin`

<a class="api-source" href="https://github.com/Query-farm/vgi-go/blob/main/vgi/worker.go#L847" target="_blank" rel="noopener">source</a>

<Code lang="go" code={`type funcOrigin struct {
	// catalog is the catalog that owns the function. Never empty: a
	// registration that names none is homed in the worker's own catalog.
	catalog	string
	// schema is the catalog schema declaring the function, lowercased.
	schema	string
	// unlisted hides the function from every function listing without
	// changing its home — it exists to back a catalog table, whose scan
	// resolves it by name, so publishing it as a callable function too would
	// be redundant surface area. Dispatch is unaffected.
	unlisted	bool
}`} />

<p class="api-section">Description</p>

funcOrigin is the single home of one registered implementation: exactly one
(catalog, schema) pair. There is no "unscoped" home — a function is never
visible in every schema, nor reachable from every catalog.

A function name is not a unique key: the same name may be registered in two
schemas of one catalog, or in two catalogs served by one worker process.
Registration is the only place that knows which, so the home is recorded here
and is what both the catalog listing and bind dispatch resolve against — a
bind naming schema `data` can only reach an implementation homed in `data`.

</div>

<a id="storageCleanupHook"></a>
## <span class="api-icon api-icon--class"></span><span class="api-kind-tag api-kind-tag--class">struct</span> `storageCleanupHook`

<a class="api-source" href="https://github.com/Query-farm/vgi-go/blob/main/vgi/worker.go#L59" target="_blank" rel="noopener">source</a>

<Code lang="go" code={`type storageCleanupHook struct {
	worker		*Worker
	pendingKeys	[]string	// keys from previous dispatch, candidates for cleanup
	staleKeys	[]string	// snapshot of pendingKeys at current dispatch start
	isHTTP		bool		// when true, skip storage cleanup (no reliable stream-end signal)
}`} />

<p class="api-section">Description</p>

storageCleanupHook implements vgirpc.DispatchHook to clean up storage
entries when execution streams complete.

Cleanup is deferred by one dispatch cycle: keys tracked during a dispatch
become "pending" at its end, and are only cleaned up in the next dispatch's
OnDispatchEnd — but only if the new dispatch did NOT reuse them. This handles
multi-worker (primary + secondary inits share an execution ID) and
table-in-out (INPUT + FINALIZE share an execution ID).

<pre class="api-sig"><code>func coldAttachScope(raw []byte) []byte</code></pre>

coldAttachScope derives the per-ATTACH plaintext scope on the cold-load path,
where parseBindRequest ran with no call context and so left the attach value
raw (the framework uuid(16) || plaintext, pass-through on subprocess). Strip
the UUID prefix to match what OnBind saw. On HTTP, where the raw value is a
sealed envelope this can't unwrap, the buffering RPC handlers re-derive the
scope from the live request instead; this is the subprocess best-effort.
