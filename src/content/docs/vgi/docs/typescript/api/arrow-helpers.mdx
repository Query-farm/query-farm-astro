<a id="decodeDictValue"></a>
## <span class="api-icon api-icon--function"></span><span class="api-kind-tag api-kind-tag--function">function</span> `decodeDictValue`

<a class="api-source" href="https://github.com/Query-farm/vgi-typescript/blob/main/src/arrow/impl-arrowjs/iterate.ts#L73" target="_blank" rel="noopener">source</a>

<pre class="api-sig"><code>export function decodeDictValue(value: any, index = 0): any</code></pre>

<p class="api-section">Description</p>

If `value` looks like a Dictionary-encoded Arrow scalar (Vector.get on a
dict column on the apache-arrow fork returns the underlying Data, not the
decoded string), pull out the decoded value at row `index`. Returns
`value` unchanged when it isn't dict-shaped.

Used at handler call sites where the incoming `params` came from the RPC
layer's row extractor (which doesn't auto-decode dictionaries) and the
handler needs the plain string.

</div>

  mask: Uint8Array,

<p class="api-section">Description</p>

Filter a RecordBatch using a Uint8Array mask (0=exclude, nonzero=include).
Returns a new batch containing only the rows where mask[i] is nonzero.

## <span class="api-icon api-icon--function"></span><span class="api-kind-tag api-kind-tag--function">function</span> `readCanonicalValue`

Read a single CANONICAL value at `index` from an arrow-js column (Vector).

<a id="safeNumber"></a>
## <span class="api-icon api-icon--function"></span><span class="api-kind-tag api-kind-tag--function">function</span> `safeNumber`

<a class="api-source" href="https://github.com/Query-farm/vgi-typescript/blob/main/src/arrow/impl-arrowjs/iterate.ts#L169" target="_blank" rel="noopener">source</a>

<pre class="api-sig"><code>export function safeNumber(value: any): number</code></pre>

<p class="api-section">Description</p>

Narrow a bigint to a number, refusing to do it lossily.

Arrow int64/uint64 values arrive as bigint. Several bind-time argument paths
want a plain number, and used to get one from a bare `Number(value)` — which
silently rounds above 2^53, so an id or a nanosecond timestamp passed as a
function argument came back subtly wrong with nothing logged anywhere.

Throwing is the lesser evil: a caller that genuinely wants a lossy narrowing
can still write `Number(v)` themselves, but nobody has to discover the loss
from mismatched output weeks later.

</div>
