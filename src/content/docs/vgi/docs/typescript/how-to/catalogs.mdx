A worker does not have to be a bag of functions. It can present itself as a **database**: a named
catalog you `ATTACH`, holding schemas that hold tables and views, queried with ordinary qualified
names. The user never sees a function call.

## The whole worker

<Collapsible summary="catalog.ts">
<CodeBlock code={catalogSrc} lang="typescript" tryable={false} />
</Collapsible>

<CodeBlock code={`ATTACH 'cat' (TYPE vgi, LOCATION 'bun run ./catalog.ts');
SELECT * FROM cat.data.cities;`} lang="sql" tryable={false} />

<QueryResult
  columns={["name", "population"]}
  rows={[["Charlottesville", 51000], ["Richmond", 230000], ["Virginia Beach", 457000]]}
/>

## Function-backed tables

The table is not stored — it is a **table function plus the arguments to call it with**:

<CodeBlock code={`tables: [
  {
    name: "cities",
    columns: citiesSchema,
    function: citiesScan,
    arguments: new Arguments([0]),   // min_population = 0, baked in
  },
],`} lang="typescript" tryable={false} />

`SELECT * FROM cat.data.cities` runs `citiesScan(0)`. The user passes nothing and never learns the
function exists. Declaring `columns` explicitly is what lets DuckDB describe the table without
calling the worker at all.

<InfoTip label="Same as DuckDB?" title="How this differs from a native table">
VGI tables live in DuckDB's catalog model, so you query them with ordinary qualified names, and
`duckdb_tables()` and `duckdb_columns()` see them. The difference is where the rows come from: a
native table is stored and managed by DuckDB, while a VGI table delegates its scan to your worker.
</InfoTip>

## Views

A view is pure SQL. Once its definition has been advertised at attach time, DuckDB evaluates it
itself — there is no worker round trip for the view, only for whatever tables it reads.

<CodeBlock code={`views: [
  {
    name: "big_cities",
    definition: "SELECT * FROM cat.data.cities WHERE population >= 100000",
  },
],`} lang="typescript" tryable={false} />

<QueryResult
  columns={["name", "population"]}
  rows={[["Richmond", 230000], ["Virginia Beach", 457000]]}
/>

<Callout type="note" title="Qualifying the definition with the catalog name is safe">
`cat` is hardcoded there, which normally would be fragile — but the name in `ATTACH` is not a free
alias. It must match the descriptor's `name`, and attaching under any other name fails at once with
*"No worker handles catalog 'mydb'"*. So the catalog name your worker declares is the name the view
will always be read under.
</Callout>

## Metadata surfaces

Comments and constraints are not decoration — they reach DuckDB's own catalog views:

<CodeBlock code={`SELECT column_name, is_nullable, comment FROM duckdb_columns() WHERE table_name = 'cities';`} lang="sql" tryable={false} />

<QueryResult
  columns={["column_name", "is_nullable", "comment"]}
  rows={[["name", false, null], ["population", true, "Most recent estimate"]]}
/>

`notNull: ["name"]` became `is_nullable = false`, and `columnComments` became the column comment.

## What else a table can declare

`TableDescriptor` carries considerably more than the example uses. The ones worth knowing early:

<table>
<thead>
<tr><th>Field</th><th>What it does</th></tr>
</thead>
<tbody>
<tr><td><code>notNull</code>, <code>unique</code>, <code>primaryKey</code>, <code>check</code>, <code>foreignKey</code></td><td>Constraints, surfaced to the planner and to <code>duckdb_constraints()</code>.</td></tr>
<tr><td><code>defaults</code>, <code>generatedColumns</code></td><td>Column defaults, and virtual columns DuckDB evaluates client-side.</td></tr>
<tr><td><code>statistics</code>, <code>inlinedCardinality</code></td><td>Optimizer hints. <code>inlinedCardinality</code> lets DuckDB skip the per-bind cardinality RPC entirely.</td></tr>
<tr><td><code>requiredFilters</code></td><td>Refuse an unbounded scan. An AND of OR-groups of column paths; the extension throws a <code>BinderException</code> naming any unsatisfied group.</td></tr>
<tr><td><code>supportsTimeTravel</code></td><td>The table answers <code>AT (VERSION …)</code> / <code>AT (TIMESTAMP …)</code> queries.</td></tr>
<tr><td><code>statisticsCacheMaxAgeSeconds</code></td><td>How long DuckDB may cache this table's statistics. <code>0</code> means never.</td></tr>
</tbody>
</table>

<Callout type="warning" title="Keep a cursor in state, not the result set">
The example puts the whole filtered slice in its scan state, which is honest for three rows and the
wrong shape for three million. State is carried between `process` calls, so whatever you hold there
is paid for repeatedly. A real scan stores a **cursor** — an offset, a page token, an iterator id —
and fetches each batch inside `process`.
</Callout>

## Beyond the descriptor

The declarative `CatalogDescriptor` is read-only and covers most workers. When you need DML, dynamic
schemas, or transactions, implement `CatalogInterface` directly and pass it as `catalogInterface`;
`CompositeCatalogInterface` lets you layer a custom implementation over a declarative base rather
than starting from nothing.
