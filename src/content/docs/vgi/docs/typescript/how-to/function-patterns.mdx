Each of the five VGI function shapes in TypeScript, with a complete, runnable worker for each — so
you can find the shape that fits your problem. (Do the
[tutorial](/vgi/docs/typescript/tutorial/scalar/) first.)

<InfoTip label="Before you run these" title="Session setup">
Each section assumes you're in a **[Haybarn](/haybarn)** shell that has loaded the extension once
with `INSTALL vgi FROM community;` then `LOAD vgi;`, and that you've installed the SDK in the
directory holding the worker:

<CodeBlock code={`bun add @query-farm/vgi @query-farm/apache-arrow @query-farm/vgi-rpc`} lang="bash" tryable={false} />

There is no build step — `LOCATION` names the command that runs the file, and `bun run` executes
TypeScript directly. `LOCATION` is resolved relative to the directory the engine was started in.
</InfoTip>

## Scalar

<div class="kind-banner kind-banner--scalar"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/scalar.svg" alt="scalar shape" /><div class="kind-banner__text"><code class="kind-banner__formula">1 row → 1 value</code><p class="kind-banner__desc">Runs on each row independently and returns a single value — a pure per-row transform.</p></div></div>

One value out per value in. No state, no finalize phase — `compute` gets a whole column and returns
a column of the same length.

<CodeBlock code={scalarSrc} lang="typescript" tryable={false} />
</Collapsible>

<CodeBlock code={`ATTACH 'calc' (TYPE vgi, LOCATION 'bun run ./calcscalar.ts');
SELECT calc.double(21);`} lang="sql" tryable={false} />

<QueryResult columns={["double(21)"]} rows={[[42]]} />

## Table

<div class="kind-banner kind-banner--table"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/table.svg" alt="table shape" /><div class="kind-banner__text"><code class="kind-banner__formula">args → N rows</code><p class="kind-banner__desc">A table-valued source: scalar arguments in, a whole set of rows out.</p></div></div>

Generate rows from arguments, with no input relation. Arguments are read once in `initialState`;
`process` is then called repeatedly until it calls `out.finish()`.

<CodeBlock code={calcSrc} lang="typescript" tryable={false} />
</Collapsible>

## Table-in-out

<div class="kind-banner kind-banner--table-in-out"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/table-in-out.svg" alt="table-in-out shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → M rows</code><p class="kind-banner__desc">Consumes a relation and streams a transformed relation back, batch by batch.</p></div></div>

Stream an input relation through, emitting per batch. Memory stays flat however large the scan is,
because nothing is held back.

<Collapsible summary="filter.ts">
<CodeBlock code={filterSrc} lang="typescript" tryable={false} />
</Collapsible>

<CodeBlock code={`ATTACH 'filters' (TYPE vgi, LOCATION 'bun run ./filter.ts');
SELECT * FROM filters.filter_positive((SELECT * FROM (VALUES (-2), (5), (0), (9), (-1)) AS t(value)));`} lang="sql" tryable={false} />

<QueryIO inColumns={["value"]} inRows={[[-2], [5], [0], [9], [-1]]} outColumns={["value"]} outRows={[[5], [9]]} />

<Callout type="note" title="The TABLE argument is implicit">
Unlike the Go SDK, nothing declares the input relation. It arrives as the stream of batches `process`
is called with, and its schema is on `params.bindCall.input_schema` at bind time — which is where a
passthrough function gets its output schema from.

The corollary is that `input_schema` can be absent, and the SDK will not stop you: check it in
`onBind` and throw a clear error, or the failure surfaces later as a null dereference.
</Callout>

## Aggregate

<div class="kind-banner kind-banner--aggregate"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/aggregate.svg" alt="aggregate shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → 1 value</code><p class="kind-banner__desc">Folds many rows down into a single value per group.</p></div></div>

Four phases — `initialState`, `update`, `combine`, `finalize` — and the split is what lets DuckDB
parallelise it. `combine` must be associative and commutative, because DuckDB decides how many
workers run and in what order their partials merge.

<Collapsible summary="sum.ts">
<CodeBlock code={sumSrc} lang="typescript" tryable={false} />
</Collapsible>

<CodeBlock code={`ATTACH 'agg' (TYPE vgi, LOCATION 'bun run ./sum.ts');
CREATE TABLE t AS SELECT * FROM (VALUES ('a',1),('a',2),('b',10),('b',NULL),('c',NULL)) AS v(category, value);
SELECT category, agg.vgi_sum(value::BIGINT) AS total FROM t GROUP BY category ORDER BY category;`} lang="sql" tryable={false} />

<QueryResult columns={["category", "total"]} rows={[["a", 3], ["b", 10], ["c", null]]} />

<Callout type="note" title="Allocate state lazily, and NULL semantics follow">
`nullHandling: "DEFAULT"` means DuckDB never calls `update` for a NULL input. Combined with
`ensureState` being called only when a row genuinely contributes, a group whose values are all NULL
never reaches the state map — so `finalize` finds nothing for it and emits SQL `NULL`, matching
built-in `SUM`. Group `c` above is that case.

Call `ensureState` unconditionally instead and the same group returns `0`. The difference is one
line, and it is the difference between matching SQL and not.
</Callout>

<InfoTip label="No registration step" title="State is just an object">
Aggregate state is an ordinary JS object with no serialization contract to satisfy — the Go SDK's
`gob.Register` step has no counterpart here, because the state stays inside the worker process.
Buffering functions are the exception: their phases can be split across processes, so their state
goes through `params.storage` explicitly.
</InfoTip>

## Buffering

<div class="kind-banner kind-banner--buffering"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/buffering.svg" alt="buffering shape" /><div class="kind-banner__text"><code class="kind-banner__formula">stream → [state] → stream</code><p class="kind-banner__desc">Holds every input row in state before emitting — the basis for sorts, top-k, and full-stream reductions.</p></div></div>

When output depends on the **whole** input — a global sort, top-k, a full reduction — use a buffering
function. It runs in three phases: `process` (the **sink**, per batch and parallel), `combine` (once,
on the coordinator), and `finalize` (the **source**).

<Collapsible summary="rowcount.ts">
<CodeBlock code={rowCountSrc} lang="typescript" tryable={false} />
</Collapsible>

<CodeBlock code={`ATTACH 'buffers' (TYPE vgi, LOCATION 'bun run ./rowcount.ts');
SELECT * FROM buffers.row_count((SELECT * FROM (VALUES (1), (2), (3), (4), (5)) AS t(x)));`} lang="sql" tryable={false} />

<QueryIO inColumns={["x"]} inRows={[[1], [2], [3], [4], [5]]} outColumns={["count"]} outRows={[[5]]} />

<Callout type="warning" title="A module-level variable will not survive the phases">
The sink and source phases can run in **different worker processes**, so anything a `let` at module
scope accumulates during `process` may simply not be there in `finalize`. State goes in
`params.storage`, which is scoped to the execution and shared by every worker serving it.

`stateAppend` is an append-only log, which is what makes the parallel sink safe: concurrent appends
cannot lose each other the way a read-modify-write would.
</Callout>

<Callout type="info" title="Buffering vs. table-in-out">
Both consume a relation, but a **table-in-out** function emits *per input batch* and never holds the
whole input — use it for streaming transforms. Reach for **buffering** only when output genuinely
depends on every row. One observable difference: an empty input yields **no rows** from a buffering
function rather than a zero — with nothing to sink, the source phase never runs.
</Callout>
