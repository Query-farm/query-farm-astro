The second tutorial step: add a **table** function that *generates* rows, so one worker serves both
a scalar and a table function — about **10 minutes**, picking up from
[step 1](/vgi/docs/python/tutorial/scalar/).

A scalar function maps one row to one row. A **table function** produces a whole result set:
`series(3)` → a three-row table `0, 1, 2`. This one is **stateless** — it computes every row from
its argument in a single pass. (Step&nbsp;3 introduces streaming state for results too large to
build at once.)

## Step 1 — Grow the worker

Here's the new part — a `Series` generator that *produces* rows from its `count` argument:

<CodeBlock code={workerSrc.slice(workerSrc.indexOf('@dataclass'), workerSrc.indexOf('class CalcWorker')).trimEnd()} lang="python" title="calc_worker.py · new code" tryable={false} />

What's new compared to the scalar:

1. **Arguments are a dataclass.** `SeriesArgs` declares one positional argument, `count`, with an
   `Arg(0, …, ge=0)` — the `0` is its position and `ge=0` rejects negatives at bind time.
2. **`TableFunctionGenerator[SeriesArgs]`** is parameterised by the argument type. There's no second
   type parameter because this generator keeps **no state** between calls.
3. **`@bind_fixed_schema`** declares the output schema once, from `FIXED_SCHEMA` (one `int64`
   column, `n`). **`@init_single_worker`** runs the generator in a single worker process.
4. **`process` emits, then finishes.** It builds the whole column from `params.args.count`, calls
   `out.emit(batch)` once, then `out.finish()` to close the stream.

<InfoTip label="Why “generator” and not just “function”?" title="Why “generator”?" width="32rem">
A table function is pulled, not called: the engine asks the worker for output until it signals
completion. `process` is the pull handler — emit a batch to yield rows, call `out.finish()` when
there are no more. Because this one produces everything in a single `process` call, it never needs
to remember anything between calls, which is what *stateless* means here.
</InfoTip>

## Step 2 — Attach and call it

Start Haybarn as in [step 1](/vgi/docs/python/tutorial/scalar/#step-2--start-haybarn)
(`npx haybarn@rc`, from the folder holding `calc_worker.py`). At the `memory H` prompt, load `vgi`
and attach the worker:

<CodeBlock code={`INSTALL vgi FROM community;
LOAD vgi;

ATTACH 'calc' (TYPE vgi, LOCATION 'uv run calc_worker.py');`} lang="sql" tryable={false} />

The catalog is still `calc`; the new function is `series`. Table functions are called in the `FROM`
clause:

<CodeBlock code={`SELECT * FROM calc.series(3);`} lang="sql" tryable={false} />

<QueryResult columns={["n"]} rows={[[0], [1], [2]]} />

The scalar function is still there too — one worker, both functions:

<CodeBlock code={`SELECT calc.double(n) AS doubled FROM calc.series(3);`} lang="sql" tryable={false} />

<QueryResult columns={["doubled"]} rows={[[0], [2], [4]]} />

<InfoTip label="It didn't work?" title="Troubleshooting" width="34rem" up>
- **`Binder Error: table function not found`** — table functions go in `FROM`, not `SELECT`:
  `SELECT * FROM calc.series(3)`, not `SELECT calc.series(3)`.
- **`Invalid Input Error: count must be >= 0`** — that's the `ge=0` constraint doing its job;
  pass a non-negative `count`.
- **Empty result** — `series(0)` is legitimately zero rows. Try `series(5)`.
</InfoTip>
