## Scalar

<div class="kind-banner kind-banner--scalar"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/scalar.svg" alt="scalar shape" /><div class="kind-banner__text"><code class="kind-banner__formula">1 row → 1 value</code><p class="kind-banner__desc">Runs on each row independently and returns a single value — a pure per-row transform.</p></div></div>

One row in, one row out. Operate on the whole column with `pyarrow.compute`; the `Annotated` types
*are* the schema.

<CodeBlock code={scalarSrc} lang="python" tryable={false} />

<CodeBlock code={`ATTACH 'calc' (TYPE vgi, LOCATION 'uv run calc_scalar_worker.py');
SELECT calc.double(n) FROM (VALUES (1), (2), (3)) AS t(n);`} lang="sql" tryable={false} />

<QueryResult columns={["double(n)"]} rows={[[2], [4], [6]]} />

Scalars aren't just for numbers — any column type works. A string transform looks the same; here
`compute` joins `Hello, ` + name + `!` across the column:

<CodeBlock code={greetingSrc} lang="python" tryable={false} />

<CodeBlock code={`SELECT greetings.greeting(name) FROM (VALUES ('Alice'), ('Bob')) AS t(name);`} lang="sql" tryable={false} />

<QueryResult columns={["greeting(name)"]} rows={[["Hello, Alice!"], ["Hello, Bob!"]]} />

## Table

<div class="kind-banner kind-banner--table"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/table.svg" alt="table shape" /><div class="kind-banner__text"><code class="kind-banner__formula">args → N rows</code><p class="kind-banner__desc">A table-valued source: scalar arguments in, a whole set of rows out.</p></div></div>

Generate rows from arguments, no input table. Declare a typed args dataclass and a `FIXED_SCHEMA`;
`process` emits batches until `out.finish()`. The `@bind_fixed_schema` / `@init_single_worker`
decorators wire up the common single-worker lifecycle. (This is the full tutorial worker — the
scalar `double` plus the `series` generator.)

<CodeBlock code={calcSrc} lang="python" tryable={false} />

<CodeBlock code={`ATTACH 'calc' (TYPE vgi, LOCATION 'uv run calc_worker.py');
SELECT * FROM calc.series(3);`} lang="sql" tryable={false} />

<QueryResult columns={["n"]} rows={[[0], [1], [2]]} />

### Streaming with state

The tutorial's `series` emits every row in a single `process` call. That's fine for small results,
but `process` is actually called *repeatedly* until you call `out.finish()` — so for large output
you emit a bounded chunk per call and remember your place in a small **state** object. The state
extends `ArrowSerializableDataclass` so it survives HTTP state round-trips:

<CodeBlock code={streamingSrc} lang="python" tryable={false} />

<CodeBlock code={`SELECT * FROM calc.series(1000000);   -- streamed CHUNK rows per process() call`} lang="sql" tryable={false} />

## Table-in-out

<div class="kind-banner kind-banner--table-in-out"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/table-in-out.svg" alt="table-in-out shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → M rows</code><p class="kind-banner__desc">Consumes a relation and streams a transformed relation back, batch by batch.</p></div></div>

Stream an input table through, batch by batch, emitting transformed output. `on_bind` declares the
output schema; `process` receives each input `batch` and emits results. Here we keep only rows
whose `value` column is positive.

<CodeBlock code={filterSrc} lang="python" tryable={false} />

<CodeBlock code={`ATTACH 'filters' (TYPE vgi, LOCATION 'uv run filter_worker.py');
SELECT * FROM filters.filter_positive((SELECT * FROM (VALUES (-2), (5), (0), (9), (-1)) AS t(value)));`} lang="sql" tryable={false} />

<QueryResult columns={["value"]} rows={[[5], [9]]} />

## Aggregate

<div class="kind-banner kind-banner--aggregate"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/aggregate.svg" alt="aggregate shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → 1 value</code><p class="kind-banner__desc">Folds many rows down into a single value per group.</p></div></div>

Accumulate input rows into per-group state, then emit one row per group. Aggregates are driven by
DuckDB's `GROUP BY` and run in three phases — `update` (fold a batch into per-group state),
`combine` (merge partial states across parallel workers), and `finalize` (state → output row).

<CodeBlock code={sumSrc} lang="python" tryable={false} />

<CodeBlock code={`ATTACH 'aggregates' (TYPE vgi, LOCATION 'uv run sum_worker.py');
SELECT category, aggregates.vgi_sum(value) AS total
FROM (VALUES (0, 10), (0, 5), (1, 1), (1, 2), (1, 3)) AS t(category, value)
GROUP BY category ORDER BY category;`} lang="sql" tryable={false} />

<QueryResult columns={["category", "total"]} rows={[[0, 15], [1, 6]]} />

<Callout type="info" title="State must be an ArrowSerializableDataclass">
Table generators and aggregates keep state between calls. Because that state is serialized across
parallel workers (aggregates) and HTTP round-trips, the framework requires it to extend
`ArrowSerializableDataclass`. Annotate fields with `ArrowType(...)` so the wire type is explicit.
</Callout>

## Buffering

<div class="kind-banner kind-banner--buffering"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/buffering.svg" alt="buffering shape" /><div class="kind-banner__text"><code class="kind-banner__formula">stream → [state] → stream</code><p class="kind-banner__desc">Holds every input row in state before emitting — the basis for sorts, top-k, and full-stream reductions.</p></div></div>

When a function must see the **whole** input before it can produce *any* output — a global sort,
top-k, or a full reduction — use a buffering function. Unlike table-in-out (which emits per input
batch), it runs in three phases: `process` (the **sink** — stash each batch, return a `state_id`),
`combine` (reduce all the partials once), and `finalize` (the **source** — stream the result out).
Because the phases can run in different worker processes, state can't live in memory — it goes in
`params.storage`, a shared store keyed to this call.

<CodeBlock code={rowCountSrc} lang="python" tryable={false} />

<CodeBlock code={`ATTACH 'buffers' (TYPE vgi, LOCATION 'uv run row_count_worker.py');
SELECT * FROM buffers.row_count((SELECT * FROM (VALUES (1), (2), (3), (4), (5)) AS t(x)));`} lang="sql" tryable={false} />

<QueryResult columns={["count"]} rows={[[5]]} />

<Callout type="info" title="Buffering vs. table-in-out">
Both consume a relation, but a **table-in-out** function emits *per input batch* and never holds the
whole input — use it for streaming transforms (filter, enrich, reshape). Reach for **buffering**
only when output genuinely depends on every row.
</Callout>
