Each of the five VGI function shapes in Java, with a complete, runnable worker for each — so you can
find the shape that fits your problem. (Do the [tutorial](/vgi/docs/java/tutorial/scalar/) first.)

<InfoTip label="Before you run these" title="Session setup">
Each section assumes you're in a **[Haybarn](/haybarn)** shell that has loaded the extension once
with `INSTALL vgi FROM community;` then `LOAD vgi;`, and that you've built the worker with
`./gradlew installDist`.

All five register into **one** worker below, which is what the examples project ships — so a single
`ATTACH` serves every query on this page.
</InfoTip>

## Scalar

<div class="kind-banner kind-banner--scalar"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/scalar.svg" alt="scalar shape" /><div class="kind-banner__text"><code class="kind-banner__formula">1 row → 1 value</code><p class="kind-banner__desc">Runs on each row independently and returns a single value — a pure per-row transform.</p></div></div>

Extend `ScalarFn` and write one `compute()`. Parameter annotations derive the signature, the output
type and the dispatch — there is no spec to keep in sync by hand.

<Collapsible summary="ScalarExample.java">
<CodeBlock code={scalarSrc} lang="java" tryable={false} />
</Collapsible>

<CodeBlock code={`SELECT demo.upper_case('hello');`} lang="sql" tryable={false} />

<QueryResult columns={["upper_case('hello')"]} rows={[["HELLO"]]} />

<InfoTip label="The annotation vocabulary" title="Four parameter roles">
`@Vector` is a per-row input column (the Arrow vector type is the SQL type), `@Const` a bind-time
constant, `@Setting` a session setting, and the **last unannotated vector is the output**, allocated
for you. `@Vector(any=true) FieldVector` accepts any type; `@Vector(varargs=true) List<FieldVector>`
takes the rest.
</InfoTip>

## Table-in-out

<div class="kind-banner kind-banner--table-in-out"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/table-in-out.svg" alt="table-in-out shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → M rows</code><p class="kind-banner__desc">Consumes a relation and streams a transformed relation back, batch by batch.</p></div></div>

## Aggregate

<div class="kind-banner kind-banner--aggregate"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/aggregate.svg" alt="aggregate shape" /><div class="kind-banner__text"><code class="kind-banner__formula">N rows → 1 value</code><p class="kind-banner__desc">Folds many rows down into a single value per group.</p></div></div>

Partial aggregation with a cross-process state combine: DuckDB decides how many workers run and in
what order their partials merge, so the combine must be associative and commutative.

## Buffering

<div class="kind-banner kind-banner--buffering"><img class="kind-banner__glyph" src="/vgi/docs/assets/kinds/buffering.svg" alt="buffering shape" /><div class="kind-banner__text"><code class="kind-banner__formula">stream → [state] → stream</code><p class="kind-banner__desc">Holds every input row in state before emitting — the basis for sorts, top-k, and full-stream reductions.</p></div></div>

When output depends on the **whole** input — a global sort, top-k, a full reduction. Three phases:
`process` (the sink, per batch and parallel), `combine` (once, on the coordinator), and a finalize
producer (the source).

<Collapsible summary="BufferingExample.java">
<CodeBlock code={bufferingSrc} lang="java" tryable={false} />
</Collapsible>

<CodeBlock code={`SELECT n FROM demo.collect((SELECT * FROM demo.numbers(4)));`} lang="sql" tryable={false} />

<QueryIO inColumns={["n"]} inRows={[[0], [1], [2], [3]]} outColumns={["n"]} outRows={[[0], [1], [2], [3]]} />

<Callout type="warning" title="Call `storage()`, not a captured field">
`BufferingFinalizeProducer` exposes storage as a **method**. That is not style: after an HTTP
continuation the producer is deserialized with a null storage view, and the accessor re-binds it from
`(executionId, attachId)`. A field read cannot, so a producer that captured one works locally and
fails the moment the transport resumes it.

This example used to read the field. It compiled against the SDK it was written for and stopped
compiling later — which is the good outcome; the bad one would have been an NPE in production.
</Callout>

<Callout type="info" title="Buffering vs. table-in-out">
Both consume a relation, but a **table-in-out** function emits *per input batch* and never holds the
whole input — use it for streaming transforms. Reach for **buffering** only when output genuinely
depends on every row.
</Callout>
