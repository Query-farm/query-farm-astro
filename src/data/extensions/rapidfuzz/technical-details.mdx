## Comparing records

A similarity score helps identify records to review. It does not establish that two records refer to the same person or company. Choose a threshold using examples from your own data, and check both false matches and missed matches.

## Architecture

This extension binds the [RapidFuzz](https://rapidfuzz.github.io/RapidFuzz/) C++ library — the same engine behind Python's `rapidfuzz` package and the spiritual successor to `fuzzywuzzy` — as DuckDB scalar functions. There is no extra state, no secrets, no `ATTACH` interface; calls are pure functions composable into any `SELECT`, `WHERE`, `ON`, or `ORDER BY` clause.

Four function families coexist:

- **Ratio scores** (`rapidfuzz_ratio`, `rapidfuzz_wratio` and friends) return a `DOUBLE` from 0 to 100, mirroring the Python [`rapidfuzz.fuzz`](https://rapidfuzz.github.io/RapidFuzz/Usage/fuzz.html) family.
- **Metrics** (Levenshtein, Damerau-Levenshtein, OSA, Indel, LCS, Hamming, Jaro, Jaro-Winkler, Prefix, Postfix) ship four variants each — `_distance`, `_similarity`, `_normalized_distance`, `_normalized_similarity`. The naming is mechanical: `rapidfuzz_<algo>[_normalized]_<distance|similarity>`.
- **Best match** — [`rapidfuzz_extract`](#rapidfuzz_extract) and [`rapidfuzz_extract_one`](#rapidfuzz_extract_one) rank a list of choices, like Python's `rapidfuzz.process`.
- **Alignment** — the edit operations and matching ranges behind a score: [`rapidfuzz_levenshtein_editops`](#rapidfuzz_levenshtein_editops), [`rapidfuzz_levenshtein_opcodes`](#rapidfuzz_levenshtein_opcodes), their Indel counterparts, and [`rapidfuzz_partial_ratio_alignment`](#rapidfuzz_partial_ratio_alignment).

Behavior matches the upstream library closely enough that the [RapidFuzz documentation](https://rapidfuzz.github.io/RapidFuzz/) is the authoritative reference for algorithm semantics.

### Characters, not bytes

Strings are compared by Unicode character. An accented letter or a CJK character is one character, so scores, distances and alignment positions agree with Python's `rapidfuzz`:

```sql
SELECT rapidfuzz_levenshtein_distance('café', 'cafe') AS rapidfuzz,
       levenshtein('café', 'cafe') AS builtin_bytes;
```

DuckDB's built-in `levenshtein` compares bytes and reports 2 here. Pure ASCII strings take a byte-level fast path.

### Return types

Raw `_distance` and `_similarity` of the counting metrics (Levenshtein, Damerau-Levenshtein, OSA, Indel, LCS, Hamming, Prefix, Postfix) return `BIGINT`. Normalized variants, Jaro, Jaro-Winkler and the ratio scores return `DOUBLE`. A NULL string gives NULL.

### Options

Options are passed by name with `:=` and must be constants:

| Option | Functions | Default |
|---|---|---|
| `score_cutoff` | every scorer, `rapidfuzz_extract`, `rapidfuzz_extract_one` | NULL (no cutoff) |
| `insert_cost`, `delete_cost`, `replace_cost` | `rapidfuzz_levenshtein_*` | 1 |
| `pad` | `rapidfuzz_hamming_*` | `true` |
| `prefix_weight` | `rapidfuzz_jaro_winkler_*` (0 to 0.25) | 0.1 |
| `scorer`, `top_k` | `rapidfuzz_extract` (`scorer` also on `rapidfuzz_extract_one`) | `'wratio'`, 5 |

`score_cutoff` follows RapidFuzz: distances above the cutoff come back as `cutoff + 1` (1.0 when normalized) and similarities below it as 0. Besides making the threshold explicit, it lets RapidFuzz abandon a comparison as soon as it can't reach the cutoff:

```sql
SELECT name
FROM customers
WHERE rapidfuzz_levenshtein_distance(name, 'Acme Corp', score_cutoff := 3) <= 3;
```

### Changes in the DuckDB 2.0 release

The DuckDB 2.0 build of the extension compares Unicode characters instead of bytes, returns `BIGINT` for the counting metrics (previously `DOUBLE`), and adds Levenshtein, Damerau-Levenshtein, `rapidfuzz_wratio`, `rapidfuzz_qratio`, the `token_ratio` variants, best-match extraction, alignment functions and the options above. Results for ASCII strings are unchanged. The [changelog](https://github.com/Query-farm/rapidfuzz/blob/v2.0/CHANGELOG.md) lists every change.

## Pick the right algorithm

| Situation | Function |
|---|---|
| One score, 0–100, sane default | [`rapidfuzz_ratio`](#rapidfuzz_ratio) |
| Don't know how the strings differ | [`rapidfuzz_wratio`](#rapidfuzz_wratio) |
| Best match from a list of choices | [`rapidfuzz_extract_one`](#rapidfuzz_extract_one) |
| One string is a fragment of the other | [`rapidfuzz_partial_ratio`](#rapidfuzz_partial_ratio) |
| Same words, different order | [`rapidfuzz_token_sort_ratio`](#rapidfuzz_token_sort_ratio) |
| Duplicated or stray words | [`rapidfuzz_token_set_ratio`](#rapidfuzz_token_set_ratio) |
| Human names, typos at the end | [`rapidfuzz_jaro_winkler_normalized_similarity`](#rapidfuzz_jaro_winkler_normalized_similarity) |
| Single-character typos / adjacent swaps | [`rapidfuzz_osa_distance`](#rapidfuzz_osa_distance) |
| Edit distance with custom costs | [`rapidfuzz_levenshtein_distance`](#rapidfuzz_levenshtein_distance) |
| Swaps that are also edited further | [`rapidfuzz_damerau_levenshtein_distance`](#rapidfuzz_damerau_levenshtein_distance) |
| Equal-length identifiers (SKUs, hashes) | [`rapidfuzz_hamming_distance`](#rapidfuzz_hamming_distance) |

For cross-pair comparisons where strings differ in length, prefer the `_normalized_*` variants — raw distance penalizes longer strings just for being long. See the [Wikipedia article on Jaro–Winkler distance](https://en.wikipedia.org/wiki/Jaro%E2%80%93Winkler_distance) for the formal definitions of the name-matching variants.

## Blocking strategies

A cross join of two tables with 100,000 rows produces 10 billion candidate pairs. Restrict those pairs before scoring. Each restriction trades fewer comparisons for a risk of missing a match:

**Length bucket.** Two strings that differ in length by more than `k` characters can't have a Levenshtein distance ≤ `k`. Filter on `length(a) BETWEEN length(b) - k AND length(b) + k`.

**First-letter (or first-N) prefix.** Cheap join key. Misses pairs where the first letter is itself the typo (rare for names, common for OCR'd text).

**Length + first-letter combined.** Combine both rules when they fit your data. Measure the remaining candidate count before running the full join.

**Phonetic prefix (soundex / metaphone).** When typos are phonetic ("Smyth" vs "Smith"). DuckDB's built-in [`fuzzy`](https://duckdb.org/docs/extensions/fuzzy.html) extension supplies the codes; group by code and only score within a group.

**Token-based blocking.** For multi-word strings, require at least one token in common (e.g. via a normalized array intersection). Excellent for company names where the legal suffix differs but the brand word is shared.

Put the candidate restrictions in the join condition and inspect the query plan when performance matters.

## Pre-normalize once, score many

Hoist deterministic transformations out of the join so they run `O(n)` instead of `O(n²)`:

```sql
WITH normalized AS (
  SELECT id,
         regexp_replace(lower(name), '[^a-z0-9 ]', '', 'g') AS name_n,
         length(name) AS len,
         left(lower(name), 1)              AS block_letter
  FROM customers
)
SELECT a.id, b.id,
       rapidfuzz_token_set_ratio(a.name_n, b.name_n) AS score
FROM normalized a
JOIN normalized b
  ON a.id < b.id
 AND a.block_letter = b.block_letter
 AND a.len BETWEEN b.len - 3 AND b.len + 3
WHERE rapidfuzz_token_set_ratio(a.name_n, b.name_n) > 90;
```

When you also need consistent casing, pluralization, or struct-key rewrites, the sibling [`inflector`](/products/extensions/inflector) extension covers the cleanup side of the same workflow — both sit in the matching-and-casing string-munging bucket.

## Top-1 per left row

Record-linkage usually wants exactly one best match per left record. Use `QUALIFY` (DuckDB's window-filter clause):

```sql
SELECT a.id AS left_id,
       b.id AS right_id,
       rapidfuzz_jaro_winkler_normalized_similarity(a.name, b.name) AS score
FROM left_records  a
JOIN right_records b
  ON left(a.name, 1) = left(b.name, 1)            -- blocking
WHERE rapidfuzz_jaro_winkler_normalized_similarity(a.name, b.name) > 0.92
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY a.id
  ORDER BY rapidfuzz_jaro_winkler_normalized_similarity(a.name, b.name) DESC, b.id
) = 1;
```

## Best match from a list

When the candidates fit in a list — a few hundred canonical names, a product catalog's categories — [`rapidfuzz_extract_one`](#rapidfuzz_extract_one) returns the best one per row without a join or a window function. The query string is preprocessed once and compared with every choice:

```sql
SELECT a.id, a.name,
       rapidfuzz_extract_one(a.name, c.names, scorer := 'jaro_winkler_normalized_similarity',
                             score_cutoff := 0.9) AS best
FROM left_records a,
     (SELECT list(name ORDER BY id) AS names FROM right_records) c
ORDER BY a.id;
```

The result is a struct with `choice`, `score` and the 1-based `choice_index`, or NULL when nothing reaches the cutoff. [`rapidfuzz_extract`](#rapidfuzz_extract) returns the `top_k` best matches as a list instead.

## Performance

- **Compare against a constant when you can.** When one argument is a constant, it is preprocessed once and reused for every row — about twice as fast as comparing two columns.
- **The scorer matters more than anything else.** `rapidfuzz_ratio` and the metrics are cheap; `rapidfuzz_partial_ratio` and `rapidfuzz_wratio` try many alignments and are an order of magnitude slower. Pass `score_cutoff` so they can skip hopeless pairs.
- **Small tables use few threads.** DuckDB parallelizes a scan in row groups of about 122,880 rows, so an expensive scorer over a table of a few hundred thousand rows only uses a few cores. Large tables and joins parallelize normally.

## When to reach for something else

- **Trigram indexes / FTS.** For a single query string against millions of rows, a trigram or full-text index returns top-N candidates in sub-linear time. Score the candidates with RapidFuzz, but don't expect this extension to replace the index.
- **Embeddings / vector search.** If "similarity" really means semantic similarity (paraphrase, translation), edit distance is the wrong tool. Reach for an embedding model and a vector index instead.
- **Production fuzzy joins on >10M rows.** Even with aggressive blocking, very large self-joins benefit from purpose-built record-linkage tooling (Splink, Dedupe). RapidFuzz is the right primitive for the inner-loop score; a record-linkage framework manages the candidate generation, blocking, and resolution around it.
