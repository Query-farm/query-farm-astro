## What you can do with one query

The single most useful pattern: drain an entire Redis keyspace into a DuckDB table without writing a script:

```sql
CREATE TABLE redis_users_dump AS
SELECT key, field, value
FROM redis_hscan_over_scan(
  /* scan_pattern  */ 'user:*',
  /* hscan_pattern */ '*',
  /* count         */ 100,
  /* secret        */ 'redis'
);
```

[`redis_hscan_over_scan`](#redis_hscan_over_scan) chains the upstream [`SCAN`](https://redis.io/docs/latest/commands/scan/) and [`HSCAN`](https://redis.io/docs/latest/commands/hscan/) cursor commands into one streaming `(key, field, value)` row source. Server-friendly cursor pagination throughout — no `KEYS` blocking, no Python in the middle.

## Authentication

Every `redis_*` function takes a trailing `secret` argument naming a DuckDB secret of `TYPE redis`. This keeps credentials out of query text and lets multiple environments (dev/staging/prod) live as separate secrets — pick the right one per query:

```sql
CREATE SECRET prod_redis (
  TYPE redis,
  PROVIDER config,
  host 'cache.prod.internal',
  port '6379',
  password :prod_password
);

SELECT redis_get('counter', 'prod_redis');
```

See [`CREATE SECRET`](https://duckdb.org/docs/sql/statements/create_secret) and the [DuckDB Secrets Manager](https://duckdb.org/docs/configuration/secrets_manager) for the secrets infrastructure, and the [Secrets](#secrets) section below for the parameter table the `redis` secret type accepts.

## SCAN, never KEYS

The [`KEYS`](https://redis.io/docs/latest/commands/keys/) command **blocks the Redis server for the duration of the scan**, which can stall traffic on a large production instance. No function in this extension issues it. Every key-listing function is built on cursor-paginated, non-blocking [`SCAN`](https://redis.io/docs/latest/commands/scan/):

- [`redis_keys`](#redis_keys) is the convenience function: it follows the `SCAN` cursor page by page until iteration completes and returns every matching key as a table, each key once.
- [`redis_scan`](#redis_scan) is the manual primitive: one `SCAN` page per call. You re-pass the returned cursor to fetch the next page; cursor `0` means iteration is complete:

```sql
SELECT redis_scan('0', 'user:*', 100, 'redis');
-- "1024:user:1,user:2,...,user:50"
```

[`redis_hscan_over_scan`](#redis_hscan_over_scan) (used in the lead snippet above) chains both into one streaming pipeline: for every key matching `scan_pattern`, run [`HSCAN`](https://redis.io/docs/latest/commands/hscan/) `hscan_pattern` and emit `(key, field, value)` rows, following both cursors to the end. Matching keys that aren't hashes are skipped. The fastest way to drain a Redis hash dataset into DuckDB.

Because `redis_keys` and `redis_hscan_over_scan` walk the whole matching keyspace in one query, keep their patterns narrow on large instances.

## Return values and NULLs

- [`redis_get`](#redis_get) and [`redis_hget`](#redis_hget) return `NULL` for a missing key or field, so `coalesce(redis_get(k, 'redis'), 'default')` and `IS NULL` checks work as expected.
- [`redis_hset`](#redis_hset) returns a `BIGINT` count of fields added (`1` for a new field, `0` when an existing one is overwritten); [`redis_lpush`](#redis_lpush) returns the list length after the push as a `BIGINT`.
- [`redis_mget`](#redis_mget) returns values comma-joined in request order, with an empty entry for each missing key so positions line up with the keys you asked for. Empty key names (for example, from a trailing comma) are ignored.
- A `NULL` in any argument, including the secret name, gives a `NULL` result.

Every argument is read per row, so the key, value, and even the secret can come from columns. The scalar functions are registered as volatile: DuckDB runs them for every row and never constant-folds or deduplicates a call, which matters because most of them change server state.
