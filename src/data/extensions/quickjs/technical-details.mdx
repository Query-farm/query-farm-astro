## What you can do with one query

The magic moment — when SQL doesn't have the right primitive, drop into JavaScript inline:

```sql
SELECT id,
       quickjs_eval(
         '(payload) => {
            const d = JSON.parse(payload);
            if (d.event === "purchase") {
              return { user: d.user, amount: d.amount, ccy: d.meta?.currency ?? "USD" };
            }
            return { user: d.user, event: d.event };
          }',
         payload
       ) AS extracted
FROM events;
```

[`quickjs_eval`](#quickjs_eval) hands each row's `payload` to the arrow function, runs it inside the embedded [QuickJS-NG](https://github.com/quickjs-ng/quickjs) engine, and returns the result as `JSON` — ready to chain into `->>` extractors or `UNNEST`. Conditional shapes that turn into a tower of `CASE` and [`json_extract`](https://duckdb.org/docs/data/json/json_functions) in pure SQL stay short and readable here.

<Callout type="note" title="A power feature, not a default">
Row-by-row JavaScript is genuinely slower than vectorized SQL. **Reach for QuickJS when you actually need expressiveness JavaScript provides** — conditional JSON reshaping, text munging beyond regex, custom parsing — not as a first resort.

- If [DuckDB's scalar functions](https://duckdb.org/docs/sql/functions/overview), the [`json_*`](https://duckdb.org/docs/data/json/loading_json.html) family, or [regex functions](https://duckdb.org/docs/sql/functions/patternmatching) cover your transform, they will be substantially faster.
- This is fine for ETL and ad-hoc analytics over millions of rows. It is not the right tool for an interactive dashboard that runs the same UDF against a billion-row fact table on every refresh.
- Don't `quickjs_eval` untrusted JavaScript in a multi-tenant context. QuickJS has no I/O surface, but it isn't hardened against adversarial source.

If your snippet is small and type-driven, the sibling [`evalexpr_rhai`](/products/extensions/evalexpr_rhai) extension embeds [Rhai](https://rhai.rs/) — a more constrained language that tends to integrate more cleanly with SQL types. Worth comparing.
</Callout>

## Two surfaces

The extension exposes the same engine two ways. The right one depends on what you want back.

[`quickjs`](#quickjs) — used after `SELECT`, evaluates a JS expression and returns a `VARCHAR`:

```sql
SELECT quickjs('2 + 2');                       -- '4'
```

```sql
SELECT quickjs('"hello".toUpperCase()');       -- 'HELLO'
```

The same name used after `FROM` is the *table form* — JS returns an array, DuckDB unpacks it into rows:

```sql
SELECT * FROM quickjs('[1, 2, 3].map(x => x * x)');
-- 1, 4, 9
```

[`quickjs_eval`](#quickjs_eval) — calls a JS function with positional arguments and returns the result as `JSON`. This is the form to use for per-row UDFs:

```sql
SELECT quickjs_eval('(a, b) => a + b', 5, 3);  -- 8 (JSON)
```

## Argument binding

Positional arguments to the table form of [`quickjs`](#quickjs) are exposed inside the snippet as `arg0`, `arg1`, … . `parsed_arg0` holds `arg0` parsed as JSON when `arg0` is a string containing valid JSON, and `arg0` itself otherwise, so the snippet doesn't have to call `JSON.parse`:

```sql
SELECT *
FROM quickjs('parsed_arg0.map(x => x * arg1)',
             '[1, 2, 3, 4, 5]', 3);
-- 3, 6, 9, 12, 15
```

The table form's code runs as a script: its result is the value of the last expression, so it may declare variables and loop before producing the array.

```sql
SELECT * FROM quickjs('const out = []; for (const x of arg0) out.push(x * x); out', [1, 2, 3]);
-- 1, 4, 9
```

For [`quickjs_eval`](#quickjs_eval), arguments map to the function's formal parameters — no `argN` aliasing. In the DuckDB 2.0 build both functions hand SQL values to JavaScript as native values:

| SQL type | JavaScript value |
|---|---|
| `TINYINT` … `BIGINT`, unsigned and `HUGEINT` integers | `number`; `BigInt` when the magnitude exceeds 2^53 − 1, so no digits are lost |
| `FLOAT`, `DOUBLE`, `DECIMAL` | `number` |
| `VARCHAR`, `JSON` | `string` (JSON text is not parsed automatically) |
| `BOOLEAN` | `boolean` |
| `DATE`, `TIMESTAMP`, `TIMESTAMPTZ`, `TIMESTAMP_S/MS/NS` | `Date` (UTC, millisecond precision); infinite values arrive as strings |
| `BLOB` | `Uint8Array` |
| `LIST`, `ARRAY` | array |
| `STRUCT`, `MAP` | object (MAP keys are stringified) |
| `UNION` | the active member's value |
| `NULL` | `null` |
| anything else (`UUID`, `INTERVAL`, `ENUM`, `TIME`, …) | its string form |

```sql
SELECT quickjs_eval('(tags, user) => tags.map(t => user.name + ":" + t)', ['a', 'b'], {'name': 'duck'});
-- ["duck:a","duck:b"]
```

Results go back through `JSON.stringify`. `BigInt` values serialize as JSON numbers, and a result with no JSON form (`undefined`, a function, a symbol) is SQL `NULL`. A returned `Promise` — for example from an `async` function — is awaited; a rejection becomes an error.

## What's in the language

The extension links [QuickJS-NG](https://github.com/quickjs-ng/quickjs), an actively-maintained fork of [Fabrice Bellard's QuickJS](https://bellard.org/quickjs/). It implements the bulk of the [ECMAScript specification](https://tc39.es/ecma262/) — arrow functions, destructuring, `let`/`const`, `Map`/`Set`, `Promise`, modern `Array` / `String` / `Object` methods, template literals, optional chaining, nullish coalescing.

There is no browser layer and no Node API surface — no `fetch`, no `fs`, no `process`, no `require`. This is a pure language runtime, by design. If your snippet needs network or filesystem access, do it in DuckDB's own httpfs / file readers and pass the resulting value into the JS as an argument.

## Performance shape

In the DuckDB 2.0 build, [`quickjs_eval`](#quickjs_eval) keeps one JavaScript runtime, context and compiled function per worker thread and recompiles only when the script text changes, so the per-row cost is the call itself — around a microsecond for a small arrow function (200,000 rows of `(x) => x * 2` take about 0.2 s). Because the context is reused, globals a function mutates persist between the rows one thread processes; don't rely on that state.

The scalar [`quickjs`](#quickjs) gives each row a fresh context so declarations never collide between rows. Creating a context costs on the order of 100 µs, so use `quickjs_eval` for per-row work and keep `quickjs` for one-off expressions.

The standard playbook:

1. Start in pure SQL. If the [scalar function reference](https://duckdb.org/docs/sql/functions/overview) or [`json_*`](https://duckdb.org/docs/data/json/loading_json.html) family covers it, you're done.
2. If regex isn't expressive enough or `CASE` chains are getting unreadable, reach for QuickJS.
3. If the snippet is small and type-driven (numbers, strings, simple records), benchmark against [`evalexpr_rhai`](/products/extensions/evalexpr_rhai) — Rhai's tighter SQL-type integration sometimes wins.

## Resource limits

The DuckDB 2.0 build bounds every script so a bad snippet fails the query instead of taking down the process:

| Setting | Default | Effect |
|---|---|---|
| `quickjs_memory_limit` | `'256MB'` | Maximum heap of each QuickJS runtime (one per thread and query). Accepts DuckDB memory sizes; `'none'` disables it. Exceeding it raises `InternalError: out of memory (quickjs_memory_limit is …)`. |
| `quickjs_timeout_ms` | `0` (off) | Maximum wall-clock time of one evaluation: one row of `quickjs` / `quickjs_eval`, or the whole table form. |

```sql
SET quickjs_timeout_ms = 1000;
SET quickjs_memory_limit = '64MB';
```

Independently of these settings, a running script stops when the query is cancelled (Ctrl-C, `interrupt()`) or exceeds DuckDB's [`max_execution_time`](https://duckdb.org/docs/configuration/overview). Unbounded recursion or deeply nested input raises `RangeError: Maximum call stack size exceeded`; the stack limit is sized to the native thread stack the query actually runs on.

The JavaScript environment has no filesystem, network, process or module loader access, so the functions keep working when `enable_external_access` is `false`.

## Changes in the DuckDB 2.0 release

<Callout type="warning" title="Behaviour changes in the DuckDB 2.0 build">
- **Native argument types.** `quickjs_eval` and table-form arguments arrive as numbers, BigInt, Date, Uint8Array, arrays and objects (see [Argument binding](#argument-binding)). Earlier builds passed SMALLINT, TINYINT, DECIMAL, dates, lists and structs as strings, so `quickjs_eval('(x) => x + 1', 1::SMALLINT)` returned `"11"`; it now returns `2`. Snippets that called string methods on such arguments need updating.
- **`undefined` is SQL NULL.** `quickjs_eval` used to return the text `undefined` in its JSON column.
- **NULL arguments reach JavaScript as `null`** instead of being stringified.
- **Table form runs as a script.** Multi-statement code works, and `parsed_arg0` falls back to `arg0` when `arg0` is not valid JSON instead of failing.
- **Promises are awaited** instead of being returned as `{}`.
- **Lone UTF-16 surrogates** in results are replaced with U+FFFD rather than producing invalid UTF-8.
</Callout>

Also new in the DuckDB 2.0 build:

- **Crash fixes:** returning or throwing a `Symbol` and deep recursion no longer crash DuckDB.
- **Limits and cancellation:** `quickjs_memory_limit`, `quickjs_timeout_ms`, `max_execution_time` and Ctrl-C (see [Resource limits](#resource-limits)).
- **Performance:** `quickjs_eval` reuses its compiled function per thread instead of building a new engine for every row — over 100× faster on per-row workloads.
- **QuickJS-NG 0.18.0.**
