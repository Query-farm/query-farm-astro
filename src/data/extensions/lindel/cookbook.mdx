## What this is for

Lindel computes Hilbert and Morton sort keys from multi-dimensional values. Ordering rows by one of these keys groups related coordinates together when writing Parquet or loading a table, so readers can use min/max statistics to skip data for multi-column predicates. The benefit depends on the data, the coordinate transform and the row-group size.

## Sort points by latitude and longitude

`hilbert_encode_latlon` quantizes valid latitude and longitude onto a grid with 32 bits per axis and returns a `UBIGINT` key:

```sql
SELECT lat, lon, hilbert_encode_latlon(lat, lon) AS hilbert
FROM source
ORDER BY hilbert;
```

Pass a third argument to change the resolution: `hilbert_encode_latlon(lat, lon, 16)` returns a `UINTEGER`. The grid is angular, so cells are narrower in metres near the poles. Coordinates outside `[-90, 90]` and `[-180, 180]` raise an error.

## Write the sorted layout to Parquet

```sql
COPY (
  SELECT * FROM source
  ORDER BY hilbert_encode_latlon(lat, lon)
) TO 'spatial.parquet' (FORMAT PARQUET);
```

Query the original columns normally:

```sql
SELECT * FROM 'spatial.parquet'
WHERE lat BETWEEN 40 AND 41
  AND lon BETWEEN -74 AND -73;
```

A reader can skip a row group when its statistics cannot match the predicates. Curve sorting makes that pruning more effective, but it does not guarantee tight bounds for every group or column. Benchmark with enough rows to produce multiple row groups. You don't need to store the key column unless another system will look rows up by it.

## Quantize any numeric range

For other coordinates with known bounds, `hilbert_encode_bounded` maps each dimension onto `2^bits` cells between a minimum and a maximum. This example uses 16 bits for altitude and time:

```sql
SELECT alt, time,
       hilbert_encode_bounded(
         [alt, time]::DOUBLE[2],
         [0, 1700000000],      -- minimum per dimension
         [20000, 1800000000],  -- maximum per dimension
         16                    -- bits per dimension
       ) AS hilbert
FROM source
ORDER BY hilbert;
```

Values outside the bounds are clamped to the edge cells. `hilbert_decode_bounded` returns the centre of a key's cell.

## Mix dates, timestamps and IDs

Pass the coordinates as separate arguments. They are cast to their common type, and keys sort like the values, including dates before 1970:

```sql
SELECT symbol_id, time, hilbert_encode(symbol_id, time) AS hilbert
FROM source
ORDER BY hilbert;
```

Arguments of different kinds, such as a `TIMESTAMP` and a `BIGINT`, have no common type. Cast them to one first, for example `epoch(ts)::BIGINT`.

## Encode signed and floating-point values directly

Signed and floating-point coordinates are mapped to order-preserving bits, so negative values sort before positive ones:

```sql
SELECT x, hilbert_encode([x]::INTEGER[1]) AS key
FROM (VALUES (-2), (-1), (0), (1), (2)) t(x)
ORDER BY key;
```

Wide types spread keys thinly, so for spatial data with known bounds, `hilbert_encode_bounded` usually gives a better ordering than encoding `DOUBLE` values directly.

## Use up to four 32-bit dimensions

Four `UINTEGER` coordinates produce a 128-bit `UHUGEINT` key:

```sql
SELECT hilbert_encode([10, 20, 30, 40]::UINTEGER[4]) AS hilbert;
```

For inputs with different units, choose a consistent scaling and offset for each dimension before encoding. Four `DOUBLE` dimensions are not supported because their combined width exceeds 128 bits.

## Try Morton / Z-order

Every function has a Morton equivalent:

```sql
SELECT lat, lon, morton_encode_latlon(lat, lon) AS morton
FROM source
ORDER BY morton;
```

Morton interleaves bits and has a simpler mapping than Hilbert. Compare encoding time and the resulting query performance before choosing an ordering.

## Decode keys

Name the type the key was encoded from:

```sql
SELECT hilbert_decode(hilbert_encode([-1.5, 2.25]::DOUBLE[2]), 'DOUBLE[2]') AS roundtrip;
-- [-1.5, 2.25]
```

The original form takes the dimension count and two type flags, `return_float` and `return_unsigned`:

```sql
SELECT hilbert_decode(
  hilbert_encode([10, 20]::UINTEGER[2]),
  /* num_elements    */ 2,
  /* return_float    */ false,
  /* return_unsigned */ true
) AS unsigned_roundtrip;
-- [10, 20]
```

```sql
SELECT hilbert_decode(
  hilbert_encode([-10, 20]::INTEGER[2]), 2, false, false
) AS signed_roundtrip;
-- [-10, 20]
```

Preserve the key's original SQL type when storing or decoding it. The integer width and dimension count determine the decoded coordinate width. Decoding recovers the values passed to the encoder; it does not undo any earlier quantization or offsets.


## Look up a box in a key-only store

When another system stores rows by key, `hilbert_ranges_bounded` turns a box into the key ranges to scan. Use the same bounds and bits that encoded the keys:

```sql
SELECT lo, hi
FROM hilbert_ranges_bounded(
  [40, -74],    -- box minimum
  [41, -73],    -- box maximum
  [-90, -180],  -- encoding bounds
  [90, 180],
  16,           -- bits per dimension
  8             -- at most 8 ranges
);
```

With a small range budget, the ranges also cover some keys outside the box, so filter the fetched rows on their coordinates. Inside DuckDB, skip the ranges: a plain coordinate filter on curve-sorted data is faster.
