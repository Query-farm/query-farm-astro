## What you can do with one query

The shortest path from "I want this SQL to run every 5 minutes" to a live schedule:

```sql
SELECT cron(
  'CREATE OR REPLACE TABLE hourly_rollup AS
     SELECT bucket, SUM(amount) AS total
     FROM events
     WHERE ts >= now() - INTERVAL 1 HOUR
     GROUP BY bucket',
  '0 */5 * * * *'
);
-- → 'task_0'
```

[`cron`](#cron) registers the query against a six-field cron expression and returns a `job_id`. A background thread owned by the database wakes when the job is due, runs the query, and writes the outcome into [`cron_jobs`](#cron_jobs). No external scheduler, no shell wrapper.

<Callout type="warning" title="Schedules die when the DuckDB process exits">
Cronjob lives entirely **inside the running DuckDB process**. A graceful shutdown, a `kill`, a crash, an OOM, a deploy — any of these wipe every registered job. There is no on-disk registry, no WAL entry, no resume after restart.

If the work needs to happen on wall-clock time regardless of process state, drive it from an external scheduler — system [`cron(8)`](https://man7.org/linux/man-pages/man8/cron.8.html), [`systemd` timers](https://www.freedesktop.org/software/systemd/man/systemd.timer.html), or [Kubernetes CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/) — and have it invoke DuckDB. Use this extension when DuckDB is *already* a long-running service and you want SQL-defined scheduling inside that lifetime.
</Callout>

## Cron expression format

Cronjob uses **six fields**, with `seconds` as the leading field — one more than POSIX [`cron(8)`](https://man7.org/linux/man-pages/man8/cron.8.html):

```
┌────────── second  (0–59)
│ ┌──────── minute  (0–59)
│ │ ┌────── hour    (0–23)
│ │ │ ┌──── day of month (1–31)
│ │ │ │ ┌── month   (1–12)
│ │ │ │ │ ┌ day of week (0–6, Sun..Sat, or MON–SUN)
* * * * * *
```

Schedules are evaluated in **UTC**. Operators: `*` (any), `?` (no specific value, used in day-of-month / day-of-week), `,` (list), `-` (range), `/` (step). [crontab.guru](https://crontab.guru/) is the standard sanity-check tool — note that crontab.guru parses the five-field POSIX form, so prepend a `0 ` (or `*/N `) to translate.

A few common patterns:

| Pattern | Meaning |
|---|---|
| `0 0 * * * *` | Top of every hour |
| `0 */5 * * * *` | Every 5 minutes |
| `*/15 * * * * *` | Every 15 seconds |
| `0 0 0 * * *` | Daily at midnight |
| `0 0 7 ? * MON-FRI` | Weekdays at 07:00 |
| `0 0 0 1 * ?` | First of every month |

## What runs, where

Each run of a job opens a **fresh connection to the same database** the extension was loaded into. That has two consequences:

- The scheduled query sees the same tables, attached databases, persistent secrets and database-wide settings (such as `enable_external_access`) as the registering session. Session state — `SET` variables, temporary tables, temporary secrets — does not carry over.
- Each database instance has its own scheduler. Closing the database stops its scheduler and drops its jobs, even before process exit — so if you load Cronjob in a session that targets an in-memory database, the schedule disappears with the database. [`cron_jobs`](#cron_jobs) lists only the jobs registered in that database instance (attached databases share it).

Each database has one scheduler thread, and it runs due jobs one after another. A job never overlaps itself; fire times missed while a run was in progress are skipped rather than replayed. A slow job also delays the other jobs in the same database until it finishes.

## Inspect and cancel

[`cron_jobs`](#cron_jobs) is the introspection table — every registered job, its next scheduled run, the last run, and the last result (or error message):

```sql
SELECT job_id, schedule, next_run, status, last_run, last_result
FROM cron_jobs()
ORDER BY next_run;
```

[`cron_delete`](#cron_delete) un-registers a job by `job_id`. It returns `TRUE`, or raises an error if no job has that id; a run already in progress finishes. Restart wipes everything anyway, so this is for un-registration during a live process:

```sql
SET VARIABLE job = (SELECT cron('ANALYZE', '0 30 1 * * *'));
SELECT cron_delete(getvariable('job'));
```

## Changes in the DuckDB 2.0 build

The DuckDB 2.0 build reworked the scheduler. The Haybarn 1.5 build keeps the earlier behaviour.

- **Timestamps are `TIMESTAMPTZ`.** `cron_jobs().next_run` and `last_run` used to be `VARCHAR` text in the server's local time; they are now `TIMESTAMPTZ` values. `last_run` is the start of the last run. New columns `run_count`, `error_count` and `created_at` follow the existing ones.
- **Run history.** [`cron_job_history`](#cron_job_history) lists the last 100 runs of each job with start and finish times, success and the result or error message.
- **Every row schedules its own job.** `cron` and `cron_delete` are `VOLATILE`. `SELECT cron(query, schedule) FROM t` uses each row's query and schedule, and `EXPLAIN` or `PREPARE` never schedule a job. A `NULL` argument returns `NULL` and schedules nothing.
- **Bad input is rejected up front.** A query with a syntax error, an empty query, or a schedule that never matches a real date (`'0 0 0 30 2 *'`) is an error from `cron`, instead of a job that fails on every run or runs continuously.
- **Jobs can inspect jobs.** A scheduled query may call `cron_jobs()`, `cron()` or `cron_delete()` itself, and a slow job no longer blocks `cron_jobs()` from other sessions.

<Callout type="warning" title="Jobs run with the database's full access">
A scheduled query runs with the same rights as any other connection to the database, in the background, until it is deleted or the database closes. Only schedule SQL you would run yourself, and check `cron_jobs()` when you share a long-running database with others.
</Callout>

## Pairing with other extensions

Cronjob is one of two **"operate your DuckDB process"** extensions in this collection — pick by what you want to drive:

- **Cronjob** schedules SQL queries on a wall-clock cadence inside the process.
- **[Events](/products/extensions/events)** streams query / transaction / connection events out of the process to an external handler.

Together they cover *push* (Events fires on internal activity) and *pull* (Cronjob fires on time). Both share the same fundamental scope: they only operate while the DuckDB process is alive.

For the alerting and exporting recipes, Cronjob composes naturally with:

- **[`http_client`](/products/extensions/http_client)** — schedule a query that POSTs to a webhook (Slack, PagerDuty, generic HTTP).
- **[`webmacro`](/products/extensions/webmacro)** — wrap repeated HTTP integrations as named macros, then schedule the macro.
- **[`httpfs`](https://duckdb.org/docs/extensions/httpfs/overview)** — schedule a [`COPY ... TO`](https://duckdb.org/docs/sql/statements/copy) that writes Parquet to S3 / GCS.

## When to use system cron instead

If any of the following are true, reach for system [`cron(8)`](https://man7.org/linux/man-pages/man8/cron.8.html) / `systemd` timers / Kubernetes CronJob and have *that* invoke `duckdb -c '...'`:

- The DuckDB process is short-lived (a CLI invocation, a script, a query runner).
- The schedule must survive deploys, restarts, or host moves.
- You need delivery guarantees, retries, or observability the host scheduler already provides.
- The work spans multiple databases or extends beyond what one DuckDB session can express.

Cronjob is for the opposite case: DuckDB is already a long-running service, and the convenience of "schedule it from SQL" outweighs the cost of "schedule lifetime equals process lifetime."
