## Schedule a query

```sql
-- Refresh an hourly rollup every 5 minutes
SELECT cron(
  'CREATE OR REPLACE TABLE hourly_rollup AS
     SELECT bucket, SUM(amount) AS total
     FROM events
     WHERE ts >= now() - INTERVAL 1 HOUR
     GROUP BY bucket',
  '0 */5 * * * *'
);
-- → 'task_0'
```

[`cron`](#cron) returns a `job_id` (e.g. `task_0`) — capture it if you need to cancel later. Schedules tick only while this DuckDB process is running.

## Inspect what's scheduled

```sql
-- All scheduled jobs and their last result
SELECT job_id, schedule, next_run, status, last_run, last_result
FROM cron_jobs()
ORDER BY next_run;
```

```sql
-- Jobs that have never run yet
SELECT job_id, schedule
FROM cron_jobs()
WHERE last_run IS NULL;
```

```sql
-- Jobs whose last run failed
SELECT job_id, last_run, last_result
FROM cron_jobs()
WHERE last_result LIKE 'Error:%';
```

On DuckDB 2.0, `next_run` and `last_run` are `TIMESTAMPTZ`, so you can do date arithmetic on them directly. The Haybarn 1.5 build returns them as text.

## Run history (DuckDB 2.0)

[`cron_job_history`](#cron_job_history) keeps the last 100 runs of each job:

```sql
-- Every failed run, newest first
SELECT job_id, started_at, result
FROM cron_job_history()
WHERE NOT success
ORDER BY started_at DESC;
```

```sql
-- Success rate per job
SELECT job_id, run_count, error_count,
       round(100.0 * (run_count - error_count) / nullif(run_count, 0), 1) AS success_pct
FROM cron_jobs();
```

## Cancel a job

```sql
-- Keep the id cron() returns, then pass it to cron_delete
SET VARIABLE job = (SELECT cron('ANALYZE', '0 30 1 * * *'));
SELECT cron_delete(getvariable('job'));
-- TRUE; raises an error if no job has that id
```

```sql
-- Cancel every job in this database
SELECT cron_delete(job_id) FROM cron_jobs();
```

Restart of the DuckDB process also cancels every registered job — `cron_delete` is for un-registering during a live process.

## Periodic refresh of materialized data

```sql
-- Every 5 minutes: rebuild a recent-events rollup
SELECT cron(
  'CREATE OR REPLACE TABLE recent_events AS
     SELECT * FROM events WHERE ts >= now() - INTERVAL 1 HOUR',
  '0 */5 * * * *'
);
```

```sql
-- Daily at 02:00: rebuild a heavy daily aggregate
SELECT cron(
  'CREATE OR REPLACE TABLE daily_summary AS
     SELECT date_trunc(''day'', ts) AS day,
            user_id,
            SUM(amount) AS total
     FROM events
     GROUP BY 1, 2',
  '0 0 2 * * *'
);
```

## Recurring exports to disk or S3

With the [`httpfs`](https://duckdb.org/docs/extensions/httpfs/overview) extension loaded, [`COPY ... TO`](https://duckdb.org/docs/sql/statements/copy) writes to S3 / GCS just like any local path:

`COPY ... TO` takes a literal path, so each run appends a new Hive partition (`export_hour=…/`, `export_date=…/`) instead of building a file name with `||`. On DuckDB 2.0, `cron` rejects a query with a syntax error when you schedule it.

```sql
-- Local Parquet snapshot every hour
SELECT cron(
  'COPY (SELECT *, strftime(now(), ''%Y%m%d_%H'') AS export_hour
         FROM events WHERE ts >= now() - INTERVAL 1 HOUR)
   TO ''/var/exports/events''
   (FORMAT PARQUET, PARTITION_BY (export_hour), APPEND)',
  '0 0 * * * *'
);
```

```sql
-- Daily export to S3 at 03:00
SELECT cron(
  'COPY (SELECT *, current_date AS export_date FROM daily_summary)
   TO ''s3://my-bucket/exports/daily''
   (FORMAT PARQUET, PARTITION_BY (export_date), APPEND)',
  '0 0 3 * * *'
);
```

## Periodic Slack / webhook alerts

Pair with the [`http_client`](/products/extensions/http_client) extension to fire a webhook when a metric crosses a threshold:

```sql
-- Every minute: post to Slack if error rate is high
SELECT cron(
  'WITH r AS (
     SELECT 100.0 * SUM(CASE WHEN status >= 500 THEN 1 END) / COUNT(*) AS pct
     FROM requests WHERE ts >= now() - INTERVAL 5 MINUTE
   )
   SELECT http_post(
     ''https://hooks.slack.com/services/XXX/YYY/ZZZ'',
     ''{"text":"Error rate '' || round(pct, 2) || ''%"}'',
     MAP {''Content-Type'': ''application/json''}
   )
   FROM r WHERE pct > 5',
  '0 * * * * *'
);
```

The query writes nothing to disk — `http_post` is a side effect that fires only when the `WHERE` filter passes.

## Maintenance: ANALYZE and pruning

```sql
-- Nightly ANALYZE at 01:30
SELECT cron('ANALYZE', '0 30 1 * * *');
```

```sql
-- Prune log rows older than 30 days, weekly on Sunday at 04:00
SELECT cron(
  'DELETE FROM audit_log WHERE ts < now() - INTERVAL 30 DAY',
  '0 0 4 ? * SUN'
);
```

## Six-field cron quick reference

```
┌────────── second  (0–59)
│ ┌──────── minute  (0–59)
│ │ ┌────── hour    (0–23)
│ │ │ ┌──── day of month (1–31)
│ │ │ │ ┌── month   (1–12)
│ │ │ │ │ ┌ day of week (0–6, Sun..Sat, or MON–SUN)
* * * * * *
```

| Pattern | Meaning |
|---|---|
| `0 0 * * * *` | Top of every hour |
| `0 */5 * * * *` | Every 5 minutes |
| `*/15 * * * * *` | Every 15 seconds |
| `0 0 0 * * *` | Daily at midnight |
| `0 0 7 ? * MON-FRI` | Weekdays at 07:00 |
| `0 0 0 1 * ?` | First of every month |

Times are evaluated in UTC: `0 0 7 ? * MON-FRI` fires at 07:00 UTC. Operators: `*` (any), `?` (no specific value), `,` (list), `-` (range), `/` (step). Sanity-check on [crontab.guru](https://crontab.guru/) — note crontab.guru is five-field POSIX, so drop the leading seconds field when pasting.

## Restart-safe scheduling: external orchestrator

When jobs must survive process restarts, drive DuckDB from system [`cron(8)`](https://man7.org/linux/man-pages/man8/cron.8.html) instead of using this extension. Example crontab entry:

```
*/5 * * * * /usr/local/bin/duckdb /var/data/analytics.db -c "CREATE OR REPLACE TABLE hourly_rollup AS SELECT ..."
```

Or a [`systemd` timer](https://www.freedesktop.org/software/systemd/man/systemd.timer.html), or a [Kubernetes CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/). Use the Cronjob extension only when DuckDB is already a long-running service and the schedule's lifetime can equal the process's.
