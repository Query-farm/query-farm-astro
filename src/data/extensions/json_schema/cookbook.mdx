## Validate one document

```sql
SELECT json_schema_validate('{
  "$schema": "https://json-schema.org/draft-07/schema",
  "type": "object",
  "properties": {
    "id":   {"type": "integer"},
    "name": {"type": "string"}
  },
  "required": ["id"]
}', {'id': 5, 'name': 'George'}) AS valid;
-- TRUE
```

The schema document follows the [JSON Schema specification](https://json-schema.org/specification). See [`json_schema_validate`](#json_schema_validate).

## Validate a column

Most real workloads point validation at a `JSON` column instead of a literal:

```sql
SELECT
  COUNT(*)                                                         AS total,
  COUNT(*) FILTER (WHERE     COALESCE(TRY(json_schema_validate(:schema, payload)), false)) AS valid,
  COUNT(*) FILTER (WHERE NOT COALESCE(TRY(json_schema_validate(:schema, payload)), false)) AS invalid
FROM events;
```

[`json_schema_validate`](#json_schema_validate) returns `TRUE` for valid data and raises an error for invalid data. `TRY` turns errors into `NULL`; `COALESCE(..., false)` counts errors and SQL `NULL` inputs as invalid. Validate the schema once outside `TRY` before processing rows, because `TRY` also catches invalid-schema errors. Here `:schema` and `:event_schema` stand for schema values supplied by your application.

## Lint the schema before deploying

Before pushing a schema to production, verify it's well-formed:

```sql
SELECT json_schema_validate_schema('{
  "$schema": "https://json-schema.org/draft-07/schema",
  "type": "object",
  "properties": { "id": { "type": "integer" } }
}') AS schema_ok;
-- TRUE
```

[`json_schema_validate_schema`](#json_schema_validate_schema) checks whether the validator can load a schema, raising on errors. It is not exhaustive meta-schema validation and may accept unsupported keyword values. To find entries that fail to load without aborting the registry scan:

```sql
SELECT name, version
FROM schema_registry
WHERE NOT COALESCE(TRY(json_schema_validate_schema(definition)), false);
```

## Quality-gate filter at ingest

Reject non-conforming payloads at the boundary; tee the rest into a quarantine table for review:

```sql
INSERT INTO events_clean
SELECT * FROM events_raw
WHERE     COALESCE(TRY(json_schema_validate(:event_schema, payload)), false);
```

```sql
INSERT INTO events_quarantine
SELECT * FROM events_raw
WHERE NOT COALESCE(TRY(json_schema_validate(:event_schema, payload)), false);
```

## Compute a defaults patch

Given a schema with `default` values declared, [`json_schema_patch`](#json_schema_patch) returns the [JSON Patch (RFC 6902)](https://datatracker.ietf.org/doc/html/rfc6902) `add` operations needed to fill in the missing fields:

```sql
SELECT json_schema_patch('{
  "$schema": "https://json-schema.org/draft-07/schema",
  "type": "object",
  "properties": {
    "id":   {"type": "integer", "default": 5},
    "name": {"type": "string"}
  }
}', {'name': 'George'}) AS patch;
-- [{"op":"add","path":"/id","value":5}]
```

Useful when you want to log or audit which fields were synthesized, or when the same diff has to apply to multiple downstream representations.

## Apply defaults inline

When you want enriched JSON rather than the diff, reach for [`json_schema_update`](#json_schema_update) instead:

```sql
SELECT json_schema_update('{
  "$schema": "https://json-schema.org/draft-07/schema",
  "type": "object",
  "properties": {
    "id":   {"type": "integer", "default": 5},
    "name": {"type": "string"}
  }
}', {'name': 'George'}) AS updated;
-- {"id":5,"name":"George"}
```

Build a clean enriched table in one step — validate, then enrich:

```sql
CREATE TABLE events_enriched AS
SELECT json_schema_update(:schema, payload) AS payload
FROM events_raw
WHERE COALESCE(TRY(json_schema_validate(:schema, payload)), false);
```

## Validate JSON files on ingest

Pair with DuckDB's [`read_json_auto`](https://duckdb.org/docs/data/json/loading_json.html) for file-based inputs:

```sql
SELECT *
FROM read_json_auto('events/*.json') AS event
WHERE COALESCE(TRY(json_schema_validate(:schema, to_json(event))), false);
```

For records arriving as already-typed JSON columns, pass the column directly without the `to_json` wrap.

## Use a schema parameter

Keep the schema out of query text by binding it as a SQL variable — handy when the same query runs against different contracts:

```sql
SET VARIABLE event_schema = (SELECT definition FROM schema_registry WHERE name = 'events.v3');
SELECT json_schema_validate_schema(getvariable('event_schema'));

SELECT COUNT(*) AS valid
FROM events
WHERE COALESCE(TRY(json_schema_validate(getvariable('event_schema'), payload)), false);
```
