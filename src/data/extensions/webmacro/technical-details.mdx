These examples use DuckDB 2.0 or later. Complete the [repository setup and installation](#quick-install) first.

## What you can do with one query

Define a macro in a Git repo, point [`load_macro_from_url`](#load_macro_from_url) at the raw URL, and use it like any built-in DuckDB function:

```sql
SELECT load_macro_from_url(
  'https://raw.githubusercontent.com/Query-farm/sql-macros/main/macros/search_posts.sql'
);
-- 'Successfully loaded macro: search_posts'

SELECT *
FROM search_posts('alice.example.com', text := 'quack');
```

The whole extension is one function. One URL is one macro. The interesting part isn't the protocol — it's that the URL becomes the unit of distribution: pull requests review the SQL, tags pin versions, and every machine in your team gets the same macro from the same place.

<Callout type="danger" title="The URL is executable code — only load from URLs you control">
[`load_macro_from_url`](#load_macro_from_url) fetches arbitrary text from a URL and executes it as SQL in your DuckDB session. Treat every URL you load with the same posture you'd use for `curl ... | bash`:

- **Only load from URLs you control or fully trust.** Your own Git repos, your team's internal artifact host, your own gists — not arbitrary URLs from chat messages, blog posts, or Stack Overflow snippets.
- **Checking the statement is not a sandbox.** The extension parses the response and accepts only one `CREATE MACRO` statement, so a file can't run anything else when it loads. But a macro's body can do whatever your session can, such as reading files or URLs, and it runs whenever you call the macro.
- **Pin URLs to immutable revisions.** Prefer `https://raw.githubusercontent.com/org/repo/<commit-sha>/macros/foo.sql` over `.../main/macros/foo.sql` so a rebase or branch compromise doesn't silently change what you load.
- **Keep HTTPS.** Plain `http://` URLs are vulnerable to in-flight tampering. On DuckDB 2.0 the extension refuses them unless you `SET webmacro_allow_http = true`, and it refuses to fetch anything when `enable_external_access` is false.

In a multi-tenant or hosted DuckDB environment, consider not loading the WebMacro extension at all, or restricting which roles can use it. See [OWASP — Code Injection](https://owasp.org/www-community/attacks/Code_Injection) for the threat model.
</Callout>

## The single function

The whole API surface is one scalar function: `load_macro_from_url(url VARCHAR) → VARCHAR` — accepts a URL, returns the loaded macro's name (or an error).

[`load_macro_from_url`](#load_macro_from_url) does exactly three things, in order:

1. `GET` the URL. On DuckDB 2.0 this uses DuckDB's HTTP stack (httpfs is autoloaded for `https://`), so `http_timeout`, `http_retries`, `http_proxy` and HTTP secrets apply; redirects are followed and every hop is checked again; responses over `webmacro_max_response_size` bytes are refused. The Haybarn 1.5 build uses cpp-httplib with a 10 s read timeout.
2. Parse the response with DuckDB's parser and require exactly one [`CREATE MACRO`](https://duckdb.org/docs/sql/statements/create_macro) or `CREATE OR REPLACE MACRO` statement. Nothing runs if the response holds anything else, including a macro followed by another statement.
3. Create the macro and return `Successfully loaded macro: <name>`. On DuckDB 2.0 the macro is created in your own transaction and search path, like typing the `CREATE MACRO` yourself: `TEMP` macros work and a `ROLLBACK` removes the macro. The Haybarn 1.5 build creates it on a separate connection and rejects `TEMP` macros.

The macro is then callable by name, like any hand-typed `CREATE MACRO`. There's no separate registry to query and no `unload` — drop the macro with [`DROP MACRO`](https://duckdb.org/docs/sql/statements/drop) when you no longer need it.

## Settings (DuckDB 2.0)

| Setting | Default | Meaning |
| --- | --- | --- |
| `webmacro_allow_http` | `false` | Allow plain `http://` URLs. The response runs as SQL, so anyone on the network path could swap the macro; use only for localhost or lab networks. |
| `webmacro_max_response_size` | `1048576` | Largest response, in bytes, that `load_macro_from_url` accepts. |

DuckDB's own `http_timeout` (default 30 s), `http_retries` and `http_proxy` settings apply too. `load_macro_from_url` is `VOLATILE`, so `EXPLAIN` or constant folding never fetches a URL or creates a macro.

## Hosting the macro

WebMacro doesn't care where the URL lives, only that an HTTP `GET` against it returns a body that parses as a DuckDB macro. Common patterns:

- **Git raw URL** (recommended): `https://raw.githubusercontent.com/org/repo/<sha>/macros/foo.sql`. Pinning to a commit SHA makes the macro deterministic forever.
- **Gist raw URL**: `https://gist.githubusercontent.com/<user>/<id>/raw/foo.sql`. Convenient for one-off sharing; harder to review than a Git PR.
- **Internal artifact server / S3 + presigned URL**: any HTTPS endpoint that returns the SQL body works. TLS certificates are verified.
- **Self-hosted "macro registry"**: a tiny static site at `macros.your-org.internal/` mapping path → SQL. The whole thing can be a directory of `.sql` files behind any static webserver.

## Loading at session start

A typical bootstrap pattern: pull a known set of macros at the top of a notebook or script, fail loudly if any URL is unreachable.

```sql
INSTALL webmacro FROM query_farm;
LOAD webmacro FROM query_farm;

SELECT
  url,
  load_macro_from_url(url) AS status
FROM (VALUES
  ('https://raw.githubusercontent.com/Query-farm/sql-macros/main/macros/search_posts.sql'),
  ('https://raw.githubusercontent.com/Query-farm/sql-macros/main/macros/normalize_handle.sql'),
  ('https://raw.githubusercontent.com/Query-farm/sql-macros/main/macros/active_users.sql')
) AS macros(url);
```

If any URL fails the fetch or the statement check, the query errors out — so a missing macro shows up immediately rather than as a "function not found" later.

## Compared to alternatives

- **Hand-rolled wrapper around [`http_client`](/products/extensions/http_client) + [`query`](https://duckdb.org/docs/sql/query_syntax/query)**. Possible — `http_client` returns the URL body, then you `EXECUTE` it. WebMacro collapses that to one statement and adds the (best-effort) safety filter. For everything beyond loading macros — calling REST APIs, posting form data, handling JSON responses — reach for [`http_client`](/products/extensions/http_client) directly.
- **Copy-pasting `CREATE MACRO` into every notebook**. The thing this extension exists to replace. Drift between notebooks is the failure mode.
- **Baking macros into a startup `.duckdbrc` / init script**. Works for a single machine, doesn't scale to a team or to ephemeral workers. WebMacro lets the URL be the artifact instead.

## Caveats

- **No caching.** Every call hits the network. If you load the same macro 100 times in a session, that's 100 HTTP requests.
- **No dependency graph.** If macro `A` calls macro `B`, you must load `B` first. WebMacro doesn't parse the SQL to discover dependencies.
- **No version negotiation.** The URL is the version. If you want immutability, pin to a commit SHA or a content-addressed URL.
- **Status is experimental.** The function surface is small and stable in shape, but pin a known-good extension version in production setups.
