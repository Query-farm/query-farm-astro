## Pick the right function

| You want… | Pick |
|---|---|
| A modern fast 64-bit default | [`xxh3_64`](#xxh3_64) |
| Maximum throughput | [`rapidhash`](#rapidhash) |
| One key for several columns | [`xxh3_64`](#xxh3_64) of a tuple: `xxh3_64((a, b, c))` |
| The same hash BigQuery, Spark, Kafka, Iceberg or ClickHouse computes | [`farm_fingerprint`](#farm_fingerprint), [`spark_hash`](#spark_hash), [`kafka_partition`](#kafka_partition), [`iceberg_bucket`](#iceberg_bucket), [`clickhouse_cityhash64`](#clickhouse_cityhash64) |
| Shards you can add to without moving most keys | [`jump_hash`](#jump_hash) |
| A checksum another system verifies | [`crc32c`](#crc32c) |
| Stable hex digest matching Python / Rust xxhash | [`xxh3_128_hex`](#xxh3_128_hex) |
| 128-bit space for billions of distinct keys | [`xxh3_128`](#xxh3_128) or [`murmurhash3_x64_128`](#murmurhash3_x64_128) |
| Cryptographic guarantees | not this extension — use [`crypto`](/products/extensions/crypto) |

For digests, signatures, HMAC, secure random, or anywhere an attacker controls the input, reach for [`crypto`](/products/extensions/crypto). None of the functions in this extension are designed to resist adversarial collisions.

## Hash partitioning

Pick a partition by taking the hash modulo the partition count:

```sql
SELECT user_id,
       xxh3_64(user_id) % 16 AS partition
FROM users;
```

A seed gives you a separate, uncorrelated hash space — useful when you want two different shardings of the same column without correlation between bucket assignments:

```sql
SELECT user_id,
       xxh3_64(user_id, 1) % 16 AS shard_a,
       xxh3_64(user_id, 2) % 16 AS shard_b
FROM users;
```

Materialize the result with [`CREATE TABLE AS`](https://duckdb.org/docs/sql/statements/create_table) to write a partitioned [Parquet](https://duckdb.org/docs/data/parquet/overview) dataset.

## Multi-column keys

Hash a tuple to get one key for several columns. Unlike concatenating strings, the [row encoding](#hashing-several-columns-at-once) can't confuse `('a|', 'b')` with `('a', '|b')`, and it keeps `NULL` apart from an empty string:

```sql
-- One 64-bit key per (user, query) pair, e.g. for deduplication or joins
SELECT user_id,
       query_text,
       xxh3_64((user_id, query_text)) AS row_key
FROM query_log;
```

Any `STRUCT`, `LIST`, `MAP` or `ARRAY` column works the same way, and every algorithm accepts a tuple — `rapidhash((a, b), 7)`, `xxh3_128((a, b, c))`.

## Routing like Kafka, Spark, Iceberg and BigQuery

Predict which partition a keyed Kafka record lands on — the same answer as Kafka's default partitioner — for example to co-partition DuckDB output with a topic:

```sql
-- Partition for each key on a 12-partition topic
SELECT key,
       kafka_partition(key, 12) AS partition
FROM rows_to_route;
```

Reproduce a Spark bucket id. Spark buckets rows by `pmod(hash(cols), numBuckets)`; [`spark_hash`](#spark_hash) applies Spark's type rules, so pass the same column types Spark sees:

```sql
-- Spark bucket id for 16 buckets
SELECT key,
       ((spark_hash(key) % 16) + 16) % 16 AS spark_bucket
FROM rows_to_route;
```

Compute the Iceberg `bucket[N]` partition of each row — for example to find which bucket files hold a key, or to write data partitioned the way an Iceberg table expects:

```sql
-- Iceberg bucket[16] partition of each key
SELECT key,
       iceberg_bucket(key, 16) AS bucket
FROM rows_to_route;
```

Reproduce a BigQuery sampling split built on `FARM_FINGERPRINT`:

```sql
-- Same rows BigQuery's MOD(ABS(FARM_FINGERPRINT(key)), 10) = 0 would keep
SELECT key
FROM rows_to_route
WHERE abs(farm_fingerprint(key)) % 10 = 0;
```

For [Apache Cassandra](https://cassandra.apache.org/_/index.html), note that `Murmur3Partitioner` tokens are derived from MurmurHash3 x64-128 but are not the raw [`murmurhash3_x64_128`](#murmurhash3_x64_128) value — verify against Cassandra before routing with it.

## Adding shards without moving every key

With `hash % n`, adding a shard reassigns almost every key. [`jump_hash`](#jump_hash) moves only the keys the new shard takes over:

```sql
-- Which keys move when growing from 4 to 5 shards?
SELECT key,
       jump_hash(xxh3_64(key), 4) AS shard_before,
       jump_hash(xxh3_64(key), 5) AS shard_after
FROM rows_to_route;
```

Every key either keeps its shard or moves to the new shard `4`; about a fifth of them move.

## String cache keys

[`xxh3_128_hex`](#xxh3_128_hex) emits the canonical 32-character hex digest used by [Python xxhash](https://pypi.org/project/xxhash/) and [xxhash-rust](https://docs.rs/xxhash-rust/latest/xxhash_rust/) — the right pick when the key needs to be a string (Redis key, filename, URL component):

```sql
-- Stable cache key for a (user, query) tuple
SELECT user_id,
       query_text,
       xxh3_128_hex(
         CAST(user_id AS VARCHAR) || '|' || query_text
       ) AS cache_key
FROM query_log;
```

Concatenation is only unambiguous when the separator can't appear in the values before it — true here, since `user_id` is a number. When the key doesn't need to be a string, hash the tuple instead (see [Multi-column keys](#multi-column-keys)).

## Bloom / XOR / Cuckoo filter input

Pair with the [`bitfilters`](/products/extensions/bitfilters) extension. Most filter constructors take `UBIGINT` hashes — exactly what [`xxh3_64`](#xxh3_64) and [`rapidhash`](#rapidhash) produce:

```sql
-- Build an xor8 filter from a column of strings
SELECT xor8_filter(xxh3_64(email)) AS filter
FROM allowed_users;
```

```sql
-- Test membership
SELECT xor8_filter_contains(f.filter, xxh3_64(:candidate_email))
       AS might_be_allowed
FROM filter_table f;
```

For a [Bloom filter](https://en.wikipedia.org/wiki/Bloom_filter) using two independent hash functions, use two seeds of the same algorithm rather than two different algorithms:

```sql
SELECT xxh3_64(key, 1) AS h1,
       xxh3_64(key, 2) AS h2
FROM data;
```

## Cross-language fingerprints

These examples require the corrected `v1.5` source from October 7, 2026. Older community builds may still emit the reversed halves; see [XXH3-128 compatibility across builds](#xxh3-128-compatibility-across-builds) before migrating stored digests.

[`xxh3_128_hex`](#xxh3_128_hex) matches the canonical lowercase 32-character hex form (`high64 || low64`) defined by the [xxHash specification](https://github.com/Cyan4973/xxHash/blob/dev/doc/xxhash_spec.md). The same bytes hashed in any of these will produce the same digest:

```sql
SELECT xxh3_128_hex('hello');
-- b5e9c1ad071b3e7fc779cfaa5e523818
```

```python
# Python — pip install xxhash (https://pypi.org/project/xxhash/)
import xxhash
xxhash.xxh3_128(b'hello').hexdigest()
# 'b5e9c1ad071b3e7fc779cfaa5e523818'
```

```rust
// Rust — xxhash-rust (https://docs.rs/xxhash-rust/latest/xxhash_rust/)
use xxhash_rust::xxh3::xxh3_128;
format!("{:032x}", xxh3_128(b"hello"));
```

Useful as a content fingerprint shared between SQL and application code.

## Cheap deduplication

`SELECT DISTINCT xxh3_64(...)` collapses duplicate payloads at near-RAM bandwidth. Drop to 128 bits when the keyspace is large enough that 64-bit birthday collisions matter:

```sql
-- Distinct payloads in a high-volume event stream
SELECT DISTINCT xxh3_64(payload) AS payload_hash
FROM events;
```

```sql
-- Same idea with more headroom
SELECT DISTINCT xxh3_128(payload) AS payload_hash
FROM events;
```

Treat the hash as an *accidental*-collision-safe key, not a security claim.

## Independent hashes via seeds

Two different seeds give two uncorrelated hashes from the same input. Useful for double-hashing schemes, parallel shardings, and probabilistic data structures that need multiple hash functions:

```sql
SELECT key,
       xxh3_64(key, 1) AS h1,
       xxh3_64(key, 2) AS h2,
       xxh3_64(key, 3) AS h3
FROM keys;
```
