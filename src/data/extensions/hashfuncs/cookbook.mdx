## Pick the right function

| You want… | Pick |
|---|---|
| A modern fast 64-bit default | [`xxh3_64`](#xxh3_64) |
| Maximum throughput | [`rapidhash`](#rapidhash) |
| Cross-system compatibility (Cassandra / Spark) | [`murmurhash3_x64_128`](#murmurhash3_x64_128) |
| Stable hex digest matching Python / Rust xxhash | [`xxh3_128_hex`](#xxh3_128_hex) |
| 128-bit space for billions of distinct keys | [`xxh3_128`](#xxh3_128) or [`murmurhash3_x64_128`](#murmurhash3_x64_128) |
| Cryptographic guarantees | not this extension — use [`crypto`](/products/extensions/crypto) |

For digests, signatures, HMAC, secure random, or anywhere an attacker controls the input, reach for [`crypto`](/products/extensions/crypto). None of the functions in this extension are designed to resist adversarial collisions.

## Hash partitioning

Pick a partition by taking the hash modulo the partition count:

```sql
SELECT user_id,
       xxh3_64(user_id) % 16 AS partition
FROM users;
```

A seed gives you a separate, uncorrelated hash space — useful when you want two different shardings of the same column without correlation between bucket assignments:

```sql
SELECT user_id,
       xxh3_64(user_id, 1) % 16 AS shard_a,
       xxh3_64(user_id, 2) % 16 AS shard_b
FROM users;
```

Materialize the result with [`CREATE TABLE AS`](https://duckdb.org/docs/sql/statements/create_table) to write a partitioned [Parquet](https://duckdb.org/docs/data/parquet/overview) dataset.

## Cross-system routing (Cassandra / Spark)

Use [`murmurhash3_x64_128`](#murmurhash3_x64_128) when DuckDB needs to compute the same routing hash that an upstream [Apache Cassandra](https://cassandra.apache.org/_/index.html) `Murmur3Partitioner` or [Apache Spark](https://spark.apache.org/) job would assign:

```sql
-- Same hash Cassandra's Murmur3Partitioner would compute
SELECT key,
       murmurhash3_x64_128(key) AS token
FROM rows_to_route;
```

## String cache keys

[`xxh3_128_hex`](#xxh3_128_hex) emits the canonical 32-character hex digest used by [Python xxhash](https://pypi.org/project/xxhash/) and [xxhash-rust](https://docs.rs/xxhash-rust/latest/xxhash_rust/) — the right pick when the key needs to be a string (Redis key, filename, URL component):

```sql
-- Stable cache key for a (user, query) tuple
SELECT user_id,
       query_text,
       xxh3_128_hex(
         CAST(user_id AS VARCHAR) || '|' || query_text
       ) AS cache_key
FROM query_log;
```

## Bloom / XOR / Cuckoo filter input

Pair with the [`bitfilters`](/products/extensions/bitfilters) extension. Most filter constructors take `UBIGINT` hashes — exactly what [`xxh3_64`](#xxh3_64) and [`rapidhash`](#rapidhash) produce:

```sql
-- Build an xor8 filter from a column of strings
SELECT xor8_filter(xxh3_64(email)) AS filter
FROM allowed_users;
```

```sql
-- Test membership
SELECT xor8_filter_contains(f.filter, xxh3_64(:candidate_email))
       AS might_be_allowed
FROM filter_table f;
```

For a [Bloom filter](https://en.wikipedia.org/wiki/Bloom_filter) using two independent hash functions, use two seeds of the same algorithm rather than two different algorithms:

```sql
SELECT xxh3_64(key, 1) AS h1,
       xxh3_64(key, 2) AS h2
FROM data;
```

## Cross-language fingerprints

[`xxh3_128_hex`](#xxh3_128_hex) matches the canonical lowercase 32-character hex form (`low64 || high64`) defined by the [xxHash specification](https://github.com/Cyan4973/xxHash/blob/dev/doc/xxhash_spec.md). The same bytes hashed in any of these will produce the same digest:

```sql
SELECT xxh3_128_hex('hello');
-- c779cfaa5e523818b5e9c1ad071b3e7f
```

```python
# Python — pip install xxhash (https://pypi.org/project/xxhash/)
import xxhash
xxhash.xxh3_128('hello').hexdigest()
# 'c779cfaa5e523818b5e9c1ad071b3e7f'
```

```rust
// Rust — xxhash-rust (https://docs.rs/xxhash-rust/latest/xxhash_rust/)
use xxhash_rust::xxh3::xxh3_128;
format!("{:032x}", xxh3_128(b"hello").swap_bytes());
```

Useful as a content fingerprint shared between SQL and application code.

## Cheap deduplication

`SELECT DISTINCT xxh3_64(...)` collapses duplicate payloads at near-RAM bandwidth. Drop to 128 bits when the keyspace is large enough that 64-bit birthday collisions matter:

```sql
-- Distinct payloads in a high-volume event stream
SELECT DISTINCT xxh3_64(payload) AS payload_hash
FROM events;
```

```sql
-- Same idea with more headroom
SELECT DISTINCT xxh3_128(payload) AS payload_hash
FROM events;
```

Treat the hash as an *accidental*-collision-safe key, not a security claim.

## Independent hashes via seeds

Two different seeds give two uncorrelated hashes from the same input. Useful for double-hashing schemes, parallel shardings, and probabilistic data structures that need multiple hash functions:

```sql
SELECT key,
       xxh3_64(key, 1) AS h1,
       xxh3_64(key, 2) AS h2,
       xxh3_64(key, 3) AS h3
FROM keys;
```
