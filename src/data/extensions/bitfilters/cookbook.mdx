## Pick the Right Filter

| Need | Pick |
|---|---|
| Static set, smallest possible memory | **`binary_fuse8_filter`** |
| Static set, very low FPR | **`binary_fuse16_filter`** or **`xor16_filter`** |
| Add to it over time, merge per-partition filters, read alongside Parquet Bloom filters | **`bloom_filter`** |
| Mergeable, sized to its input without guessing | **`quotient_filter(r, value)`** |
| Plug into DuckDB's join optimizer | **`bitfilters_duckdb_bloom_filter_*`** |

In short: **Bloom** is incremental, mergeable and Parquet-compatible; **XOR / Binary Fuse** are the smallest but build-once; **Quotient** is mergeable and can size itself.

The XOR, Binary Fuse, Quotient and split block Bloom constructors accept supported scalar values directly. They hash values with XXH64 of a fixed encoding that stays the same across DuckDB versions, so you don't need `hash()`. XOR, Binary Fuse and Quotient use `UBIGINT` values as keys exactly as given; split block Bloom hashes them too. The separate `bitfilters_duckdb_bloom_filter_create` constructor takes hashes produced by `bitfilters_duckdb_hash`.

## Build a Filter

Filter constructors are **aggregate functions** — pass every member of the set and the result is a single BLOB you can store anywhere DuckDB stores BLOBs:

```sql
-- Materialize a filter per partition
CREATE TABLE allowed_filters AS
SELECT bucket,
       binary_fuse8_filter(id) AS filter
FROM allowed_ids
GROUP BY bucket;
```

The filter is self-contained: its header records the filter type, how values were hashed and the value type. At probe time just call the matching `*_contains` function (or `bitfilter_contains`) with the value — it is cast to the type the filter was built from, so `42` and `'42'` both work against a `BIGINT` filter.

## Pre-Filter an Expensive Join

The classic use case — avoid an expensive lookup or cross-partition join when you can probabilistically rule rows out:

```sql
-- 1. Build a filter from "interesting" keys, once
CREATE OR REPLACE TABLE interesting_filter AS
SELECT xor8_filter(key) AS filter FROM interesting_keys;

-- 2. Probe the filter to skip the expensive operation entirely for non-members
SELECT e.*
FROM events e, interesting_filter f
WHERE xor8_filter_contains(f.filter, e.key)          -- fast: maybe-member
  AND e.key IN (SELECT key FROM interesting_keys);   -- slow: confirm if maybe
```

Because filters never produce false negatives, the probe-then-verify pattern is exact — you only pay the expensive `IN` for rows that pass the cheap filter.

## Per-Partition Data Skipping

Materialize one filter per logical partition; use it to skip whole partitions at query time:

```sql
-- Build filters at write time
CREATE OR REPLACE TABLE partition_filters AS
SELECT day,
       binary_fuse8_filter(user_id) AS users_in_partition
FROM events
GROUP BY day;

-- At query time, only scan partitions that might contain the user
SELECT day, COUNT(*) AS hits
FROM events
WHERE day IN (
  SELECT day FROM partition_filters
  WHERE binary_fuse8_filter_contains(users_in_partition, 7)
)
  AND user_id = 7
GROUP BY day;
```

For large fact tables this can skip 99%+ of partitions when looking for a specific user/key.

## Verify the False-Positive Rate

If you want to confirm the FPR on your data, count probes that the filter says yes to but the source set doesn't actually contain:

```sql
-- Real members
SELECT COUNT(*) AS true_positives
FROM source_set s, the_filter f
WHERE xor8_filter_contains(f.filter, s.id);
```

```sql
-- Non-members that the filter incorrectly accepts
SELECT COUNT(*) AS false_positives
FROM unrelated_set u, the_filter f
WHERE xor8_filter_contains(f.filter, u.id);
```

Both xor8 and binary_fuse8 have an expected false-positive rate of 1/256 (~0.39%); the 16-bit variants have a rate of 1/65,536 (~0.0015%). Binary Fuse uses less space at the same fingerprint width. `bitfilter_info(filter).expected_fpr` gives the rate the filter expects.

## Inspect a Filter

`bitfilter_info` describes XOR, Binary Fuse, Quotient and split block Bloom filter BLOBs — type, key type, size, entries, expected false positive rate. It does not accept the separate DuckDB-internal Bloom format. Fields a filter type doesn't have are NULL:

```sql
SELECT i.filter_type, i.key_type, i.size_bytes, i.expected_fpr
FROM the_filter, LATERAL (SELECT bitfilter_info(filter) AS i);
```

Use `bitfilter_is_valid` (or the per-type `*_is_valid`) to find damaged or mismatched BLOBs without raising the error a probe would. Passing one filter type to another's function fails with a clear error, e.g. *the filter BLOB is a xor8_filter, not a quotient_filter*.

## Bloom Filters — Incremental and Parquet-Compatible

`bloom_filter(ndv, fpp, value)` builds a split block Bloom filter sized for `ndv` distinct values at false positive rate `fpp`. For the same values and sizing, its payload after the 16-byte Bitfilters header is byte-for-byte the Bloom filter blocks DuckDB writes into Parquet files.

```sql
-- One filter per bucket, each sized for ~1,000 keys at 1% FPR
CREATE OR REPLACE TABLE bucket_blooms AS
SELECT bucket,
       bloom_filter(1000, 0.01, key) AS bf
FROM keys
GROUP BY bucket;

-- Roll them up into one filter (bitwise OR)
SELECT bloom_filter_merge(bf) AS all_keys FROM bucket_blooms;
```

Filters merge when their payload sizes and value types match. Using the same `ndv` and `fpp` guarantees matching sizes; different settings can also round to the same size. A Bloom filter never gets "full" — insert more than `ndv` values and its false positive rate degrades gradually.

## Quotient Filter — Mergeable Sets

Quotient filters can be merged, and can pick their own size. The `q` and `r` parameters tune the size/FPR tradeoff:

- `q` — number of slot index bits. The filter holds at most 2^q − 1 values; inserting more is an error.
- `r` — remainder bits per slot. Higher `r` → lower FPR, more memory.

Approximate FPR ≈ 2^(−r). At `r = 4`, expect ~6% FPR; at `r = 8`, ~0.4%.

```sql
SELECT bucket,
       quotient_filter(20, 8, id) AS filter   -- up to ~1M values, ~0.4% FPR
FROM ids
GROUP BY bucket;
```

Don't know how many values you have? Leave out `q` and the filter sizes itself so the distinct values fill at most 3/4 of the slots:

```sql
SELECT bucket,
       quotient_filter(8, id) AS filter   -- ~0.4% FPR, q chosen for you
FROM ids
GROUP BY bucket;
```

To merge, pass filter BLOBs instead of values. The result has exactly the `q` and `r` you give, and each input needs at least `q + r` hash bits — so a merge can grow `q` only by giving up as many remainder bits:

```sql
-- Per-bucket (16, 8) filters merge into one (20, 4) filter — not (20, 8)
WITH parts AS (
  SELECT quotient_filter(16, 8, id) AS filter FROM ids GROUP BY bucket
)
SELECT quotient_filter(20, 4, filter) AS merged FROM parts;
```

## DuckDB-Compatible Bloom Filters

The `bitfilters_duckdb_*` family produces filters in DuckDB's *internal* Bloom filter format — the same one the optimizer materializes during certain joins. Use these when you want to:

- Persist a filter and re-use it later in a join hint.
- Build per-zone Bloom filters for custom data-skipping logic.

All three functions take a constant version string (e.g. `'v2.0'`) as their first argument — bind-folded at parse time — so the produced hash and filter layout match the DuckDB build that will probe them later.

```sql
-- Build one DuckDB-shaped Bloom filter per bucket. The aggregate's middle
-- argument (16384 here) is the sector count — must be a power of two.
CREATE OR REPLACE TABLE zone_filters AS
SELECT bucket,
       bitfilters_duckdb_bloom_filter_create(
         'v2.0',
         16384,
         bitfilters_duckdb_hash('v2.0', key)
       ) AS bf
FROM keys
GROUP BY bucket;

-- Probe the matching filter at scan time. Select the event columns: bf is
-- a large BLOB holding the whole filter.
SELECT e.*
FROM events e, zone_filters z
WHERE z.bucket = e.bucket
  AND bitfilters_duckdb_bloom_filter_probe('v2.0', z.bf, e.key);
```

`bitfilters_duckdb_hash` and `bitfilters_duckdb_bloom_filter_create` produce hashes / sector layouts that match the DuckDB build named by the version string — pin it to your runtime's exact version.
