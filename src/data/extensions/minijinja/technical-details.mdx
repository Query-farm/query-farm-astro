## What you can do with one query

The shortest path from "rows in a table" to "rendered HTML, one body per row":

```sql
SELECT email,
       minijinja_render_with_context(
         '<h1>Hi {{ name }}!</h1><p>You have {{ unread }} new messages.</p>',
         json_object('name', name, 'unread', unread_count)
       ) AS html_body
FROM users
WHERE unread_count > 0;
```

[`minijinja_render_with_context`](#minijinja_render_with_context) compiles the template, binds the [`json_object`](https://duckdb.org/docs/sql/functions/json) context, and returns the rendered string. The template body is plain [Jinja2 syntax](https://jinja.palletsprojects.com/en/stable/templates/) — anything that renders correctly under Python's Jinja2 for these basic features should render the same way here.

<Callout type="note" title="Trusted templates only">
MiniJinja interpolation is **not** parameter-safe against SQL injection. If you template SQL strings (the dynamic-SQL pattern), the template body and the values flowing through `{{ ... }}` must come from a source you trust. For untrusted user input, render the SQL **shape** with MiniJinja and bind values through prepared-statement parameters.

Autoescape is on by default for HTML output (`B&O` becomes `B&amp;O`). Pass `autoescape := false` when rendering non-HTML targets like configs, JSON, or SQL — see the recipes in the [Cookbook](#cookbook).
</Callout>

## Architecture

Two scalar entry points use the [`minijinja`](https://docs.rs/minijinja/) Rust crate: `minijinja_render(template, *, options)` for rendering without context, and `minijinja_render_with_context(template, context, *, options)` for JSON context. Use the latter for both literals and per-row context columns — `minijinja_render` takes exactly one positional argument, so passing a context to it is rejected when the query is bound.

The template argument is a `VARCHAR` literal or column. The context argument is any DuckDB `JSON` value — a literal string, [`json_object(...)`](https://duckdb.org/docs/sql/functions/json), or a JSON column. Inside the template you address fields with normal Jinja syntax: `{{ user.name }}`, `{% for x in items %}`, `{{ items | length }}`, `{% if user.admin %}…{% endif %}`.

Filters (`upper`, `lower`, `length`, `default`, `join`, `replace`, `trim`, …), control flow (`if` / `elif` / `else`, `for` with the [`loop` object](https://jinja.palletsprojects.com/en/stable/templates/#for)), and tests (`is defined`, `is none`) all work as documented in the [Jinja2 template reference](https://jinja.palletsprojects.com/en/stable/templates/) and the [MiniJinja crate docs](https://docs.rs/minijinja/).

## Options

The render options are native DuckDB named parameters, declared keyword-only with typed defaults — DuckDB matches the names, casts the values and fills in the defaults, so the signature you see in `duckdb_functions()` is the one the binder enforces:

```
minijinja_render(template VARCHAR, *,
                 autoescape BOOLEAN := true,
                 template_path VARCHAR := '',
                 undefined_behavior VARCHAR := 'lenient',
                 autoescape_extensions VARCHAR[] := [])

minijinja_render_with_context(template VARCHAR, context JSON, *, ...same options...)
```

| Option | Default | Effect |
|---|---|---|
| `autoescape` | `true` | HTML-escape interpolated values. Pass `false` for configs, SQL, JSON or plain text. |
| `template_path` | `''` | Directory to load templates from; `template` then names a file there, enabling `{% include %}` / `{% extends %}`. |
| `undefined_behavior` | `'lenient'` | `'lenient'`, `'chainable'`, `'semi_strict'` or `'strict'` — how undefined variables render. Other values are a binder error. |
| `autoescape_extensions` | `[]` | When non-empty, autoescape only templates whose name ends with one of these suffixes. |

- **Keyword-only.** Options are always passed as `name := value`; `minijinja_render('Hello', false)` does not match any signature. The positional arguments can be named too, in any order: `minijinja_render_with_context(context := '{"a": 1}', template := '{{ a }}')`.
- **Typed.** A value is accepted if DuckDB can cast it implicitly — string literals included, so `autoescape := 'false'` works — while `autoescape := 1` or an unknown name such as `autoescap := false` fails with DuckDB's standard *No function matches the given name and argument types* error.
- **Constant.** Options are read once when the query is bound, so they must be constant expressions (`autoescape := random() > 0.5` is an error). Per-row values belong in the context.
- **NULL in, NULL out.** A NULL template, a NULL context, or an explicit NULL option (`autoescape := NULL`) returns NULL. A NULL element inside `autoescape_extensions` is still an error.

```sql
SELECT minijinja_render('A & B', autoescape := 'false');
-- 'A & B'
```

## Compared to alternatives

- **String concatenation in SQL** — fine for two or three substitutions; falls apart once you need loops, conditionals, or autoescape. MiniJinja gives you the structured-template surface without leaving the query.
- **Python / Node.js post-processing** — pull rows, render in app code, push results back. Works, but introduces an extra hop and serializer per template. With this extension the rendering happens inline in DuckDB's vectorized execution.
- **[`tera`](/products/extensions/tera)** — the sibling Jinja-style engine in this catalog. Tera ships a wider built-in filter and tester library, template-file inclusion via a `template_path` glob, and a handful of Tera-specific syntax extensions. Pick Tera when you want those features; pick MiniJinja when you want strict [Jinja2](https://jinja.palletsprojects.com/) semantics that match an existing Python codebase.
