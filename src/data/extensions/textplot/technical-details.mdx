## What you can do with one query

The shortest path from "a column of numbers" to "I can see what's going on" — without leaving the [DuckDB CLI](https://duckdb.org/docs/api/cli/overview):

```sql
SELECT tp_density(array_agg(value)) AS distribution
FROM measurements;
```

[`tp_density`](#tp_density) renders the array as a one-line Unicode density plot — enough to tell whether the data is roughly normal, bimodal, or has a long tail. No notebook, no `matplotlib`, no BI tool round-trip. The same shape works for sparklines and threshold-colored bars in any result table:

```sql
SELECT host,
       tp_sparkline(cpu_history, theme := 'utf8_blocks', width := 24) AS cpu,
       tp_bar(disk_pct, min := 0, max := 100, width := 12,
              thresholds := [(90, 'red'), (75, 'yellow'), (0, 'green')]) AS disk
FROM hosts_status
ORDER BY disk_pct DESC;
```

One sparkline per row, one threshold-colored bar per row, all inline in the result table.

<Callout type="note" title="Quick eyeballing, not real visualization">
Textplot is a CLI ergonomics tool. Character-grid resolution caps the detail you can see — these plots are for *quick visual checks during interactive SQL*, not a replacement for [Matplotlib](https://matplotlib.org/), [Vega-Lite](https://vega.github.io/vega-lite/), or a proper BI dashboard. When you need axes, hover, drilldown, or pixels, use a real charting tool. When you just want to know the shape of a column without leaving the terminal, use this.
</Callout>

## How it fits the CLI workflow

Every function returns a single `VARCHAR`. That's the whole API: any chart you produce is just another column in the result set. It composes with [`.mode line`](https://duckdb.org/docs/api/cli/output_formats), `.mode markdown`, log redirection, `tee` to a file, or paste into a status email — same as any other string column.

The companion piece for the CLI is [`fuzzycomplete`](/products/extensions/fuzzycomplete), which fixes tab-completion for table and column names. Together they're the two extensions worth installing for "I live in the DuckDB REPL" workflows: `fuzzycomplete` makes typing queries painless, `textplot` makes reading their output painless.

## Function map

| Function | Shape | Use for |
|---|---|---|
| [`tp_bar`](#tp_bar) | Single bar | Progress, percentages, SLA indicators |
| [`tp_sparkline`](#tp_sparkline) | One-line trend | Time series, KPIs in tables |
| [`tp_density`](#tp_density) | Distribution plot | Spotting outliers, shape of a column |
| [`tp_qr`](#tp_qr) | QR code | Scannable links in terminal/docs |

## Styling vocabulary

The named-parameter surface is shared in spirit across functions:

- **Shapes / styles / themes** — `shape := 'circle' | 'square' | 'heart'` on [`tp_bar`](#tp_bar); named character-set styles on [`tp_density`](#tp_density) (`shaded`, `ascii`, `dots`, `height`, `circles`, `rainbow_circle`, ...); per-mode themes on [`tp_sparkline`](#tp_sparkline) (`utf8_blocks`, `arrows`, `faces`, `slopes`, ...).
- **Colors** — `on_color` / `off_color` on [`tp_bar`](#tp_bar). `thresholds := [(threshold, color), ...]` gives value-conditional coloring; each block uses the highest threshold it satisfies.
- **Custom characters** — [`tp_bar`](#tp_bar) and [`tp_qr`](#tp_qr) take `on` / `off`, and [`tp_density`](#tp_density) takes `graph_chars` and `marker`; all accept arbitrary strings (single chars, emoji, multi-char sequences). `on` and `off` are SQL reserved words — quote them as `"on"` and `"off"`.
- **Width** — fixed character width keeps charts aligned in tables.

## Named parameters

Each function takes one positional argument — the value, list, or data to plot — and every option is a **keyword-only named parameter with a default**, declared natively in the function signature:

```sql
SELECT tp_bar(75, min := 0, max := 100, width := 20);
```

- **Pass options by name**, in any order. A positional option such as `tp_bar(0.5, 0, 1)` is rejected; so is an option name the function doesn't declare.
- **Values are cast to the declared type** — `width := 4::UTINYINT` is fine — but there is no lossy implicit cast: `width := 2.5` is an error, and a string that doesn't parse (`marker_value := 'x'`) fails the cast.
- **Options must be constant** within a query (a literal, a constant expression, or a prepared-statement `?` parameter), not a per-row column.
- **An explicit `NULL` option makes the result `NULL`**, the same as a `NULL` first argument.
- **Some defaults mean "not passed"**: `style := ''` on [`tp_density`](#tp_density) means `shaded` (unless `graph_chars` is given), `theme := ''` on [`tp_sparkline`](#tp_sparkline) picks the mode's default theme, `on` / `off` := `''` use the built-in glyphs, `marker_value := NaN` means no marker, and `graph_chars := []` means "use `style`".

An unknown option, a positional option, or a value of the wrong type fails at bind time with DuckDB's standard `No function matches the given name and argument types` error, which lists the full signature with every option and its default:

```text
Binder Error: No function matches the given name and argument types 'tp_bar(DECIMAL(2,1), "bogus" := INTEGER_LITERAL)'.
	Candidate functions:
	tp_bar("value" DOUBLE, /, *, min DOUBLE := 0.0, max DOUBLE := 1.0, width BIGINT := 10, "on" VARCHAR := , "off" VARCHAR := , on_color VARCHAR := red, off_color VARCHAR := white, shape VARCHAR := square, filled BOOLEAN := true, thresholds ANY := []) -> VARCHAR
```

Value checks — ranges, allowed shapes/styles/themes/ECC levels, `min < max`, `marker` requiring `marker_value`, `style` vs `graph_chars` — still run at bind time with textplot's own messages (for example `tp_bar: 'width' argument must be at least 1`). `duckdb_functions()` reports every option with its real name and type.

## Portability: ASCII vs Unicode

Defaults use Unicode block characters and emoji, which look great in modern terminals but vary by font. For maximum portability:

```sql
-- ASCII-only density plot
SELECT tp_density([1, 5, 3, 8, 2], style := 'ascii');
```

```sql
-- ASCII sparkline
SELECT tp_sparkline([1, 3, 2, 5, 4, 6], theme := 'ascii_basic');
```

```sql
-- ASCII bar with custom characters
SELECT tp_bar(0.7, "on" := '#', "off" := '-', width := 15);
```

```sql
-- ASCII QR code
SELECT tp_qr('https://query.farm', "on" := '##', "off" := '  ');
```

For QR codes specifically, `.mode ascii` in the CLI gives the cleanest rendering — the default table borders interact poorly with multi-line block output.

## When to reach for it (and when not to)

**Reach for Textplot when:**

- You're in the **DuckDB CLI** doing ad-hoc analysis and want to *see* a distribution or trend without copying values out.
- You need **per-row visual cells** in a result table — sparklines per host, bars per SLA, etc.
- The output goes to a **terminal**, **log file**, **status email**, or **README**.

**Reach for a real charting tool when:**

- You're building an **interactive web dashboard** with hover/zoom/drilldown.
- You need **precise pixel control** for publication-quality figures.
- The audience expects **polished graphics** and the data deserves them.

The two are complementary, not competing — Textplot is the "I'm at a SQL prompt right now" tool.
