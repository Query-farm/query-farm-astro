## Encode a point as a cell ID

The everyday entry point — convert `(lon, lat)` to a `UBIGINT` cell ID at a chosen resolution:

```sql
SELECT a5_lonlat_to_cell(-74.0060, 40.7128, 15) AS nyc_cell;
```

Higher resolution = smaller cells. See [`a5_lonlat_to_cell`](#a5_lonlat_to_cell) for the full signature and [`a5_cell_area`](#a5_cell_area) for the equal-area cell size at any resolution:

```sql
SELECT a5_cell_area(15) AS cell_area_m2;
```

## Aggregate point data into cells

The common heatmap pattern — bucket points by cell, then count / sum / aggregate:

```sql
SELECT a5_lonlat_to_cell(longitude, latitude, 10) AS cell_id,
       COUNT(*)                                   AS point_count,
       AVG(amount)                                AS avg_amount
FROM   transactions
GROUP  BY cell_id
ORDER  BY point_count DESC
LIMIT  100;
```

Because A5 cells are equal-area at each resolution, the resulting counts are directly comparable across latitudes — no per-cell area normalization needed.

## Recover the cell center

Round-trip a cell ID back to `(lon, lat)` for labeling or display:

```sql
SELECT a5_cell_to_lonlat(a5_lonlat_to_cell(-74.0060, 40.7128, 15)) AS center_coords;
```

## Render a cell as a polygon

[`a5_cell_to_geometry`](#a5_cell_to_geometry) returns the cell boundary directly as DuckDB's built-in `GEOMETRY` type — no [`spatial`](https://duckdb.org/docs/extensions/spatial) extension needed to produce it. Load `spatial` only for functions that consume it, like `ST_AsGeoJSON`:

```sql
INSTALL spatial; LOAD spatial;

SELECT ST_AsGeoJSON(
    a5_cell_to_geometry(
        a5_lonlat_to_cell(-3.7037, 40.41677, 10)
    )
) AS geojson;
```

## Cover a polygon (or point, or line) with cells

[`a5_geometry_to_cells`](#a5_geometry_to_cells) runs the inverse of `a5_cell_to_geometry` — hand it any `GEOMETRY` and a resolution, and it returns the covering set of A5 cells. A plain `::GEOMETRY` cast from WKT text works with no extension beyond `a5` itself. For a polygon the result is a **covering**: complete groups of sibling cells collapse to a coarser parent, sorted in curve order, followed by a trailing **compaction marker** — a `UBIGINT` that is not a cell but records the resolution the covering stands for (see [Coverings and the compaction marker](#coverings-and-the-compaction-marker)). That's the right shape for storage, transfer, and set operations. But the marker is not a cell, and cell boundaries at different resolutions don't nest geometrically, so **uncompact before unnesting or drawing the cells on a map** — [`a5_uncompact`](#a5_uncompact) drops the marker and expands every cell to the resolution the covering was built at; skip it and a mixed-resolution result will show gaps that aren't really there:

```sql
SELECT unnest(a5_uncompact(
    a5_geometry_to_cells(
        'POLYGON((-74.02 40.70, -73.99 40.70, -73.99 40.72, -74.02 40.72, -74.02 40.70))'::GEOMETRY,
        12
    )
)) AS cell;
```

Points map to their containing cell, lines are traced, and polygons are filled by cell-center containment by default — which really does leave a gap at the polygon's edge, visible below where the query rectangle's left and bottom edges cross cells whose center falls just outside it:

To ask whether a single cell falls inside the covering, skip the unnest entirely — [`a5_contains`](#a5_contains) probes the compacted covering directly, as long as the cell is at the covering's resolution. To join against an indexed cell column, `a5_uncompact` first and join on the expanded cells — but that's a different reason to uncompact than the rendering one above: joins care about matching resolutions, drawing cares about geometric nesting.

## Roll up to a coarser resolution

Encode once at the finest resolution you'll need, then re-aggregate at every coarser zoom without re-reading raw points:

```sql
-- Encode at resolution 15 once
CREATE OR REPLACE TABLE indexed AS
SELECT *, a5_lonlat_to_cell(lon, lat, 15) AS cell_15
FROM raw_points;

-- Roll up to resolution 10
SELECT a5_cell_to_parent(cell_15, 10) AS cell_10,
       COUNT(*)                       AS n
FROM indexed
GROUP BY cell_10;
```

[`a5_get_resolution`](#a5_get_resolution) recovers the resolution from a cell ID; [`a5_get_num_children`](#a5_get_num_children) returns the parent/child cell ratio between two resolutions. Omit the resolution — `a5_cell_to_parent(cell_15)` — for the immediate parent one level up.

## Parent vs supercell

A5 cells don't nest exactly across resolutions: a cell's **parent** is its ancestor in the cell-ID hierarchy, and it need not contain the cell. When you want the coarser cell a point *actually lies in* — which is usually what a spatial roll-up means — use [`a5_cell_to_supercell`](#a5_cell_to_supercell), which returns the coarser cell containing the cell's center:

```sql
SELECT a5_cell_to_parent(c, 5)                   AS parent,
       a5_cell_to_supercell(c, 5)                AS supercell,
       a5_lonlat_to_cell(-74.0060, 40.7128, 5)   AS containing
FROM (SELECT a5_lonlat_to_cell(-74.0060, 40.7128, 15) AS c);
```

<QueryResult

/>

The supercell matches encoding the original point directly at resolution 5; the parent is a neighboring cell. The parent is the cheaper, purely integer walk and is fine for bucketing that only needs to be consistent; use the supercell when the coarse buckets must respect real geography.

## Drill down to children

The inverse of roll-up — get the immediate children, or all descendants at a target resolution:

```sql
-- Immediate children (one level finer)
SELECT a5_cell_to_children(a5_lonlat_to_cell(-74.0060, 40.7128, 10)) AS kids;
```

```sql
-- All descendants at resolution 12
SELECT a5_cell_to_children(a5_lonlat_to_cell(-74.0060, 40.7128, 10), 12) AS descendants;
```

The spatial counterpart is [`a5_cell_to_subcells`](#a5_cell_to_subcells): the finer cells whose *centers* lie inside the cell — the inverse of `a5_cell_to_supercell`. The two sets differ slightly at the edges:

```sql
SELECT a5_count(a5_cell_to_subcells(a5_lonlat_to_cell(-74.0060, 40.7128, 5), 8)) AS subcells,
       a5_count(a5_cell_to_children(a5_lonlat_to_cell(-74.0060, 40.7128, 5), 8)) AS children;
```

<QueryResult columns={["subcells", "children"]} rows={[["62", "64"]]} />

Subcells come back as a covering, so count them with [`a5_count`](#a5_count) rather than `len()`; the subcells of every cell at one resolution partition each finer resolution exactly.

## Neighborhood search by metric radius

When you have a real-world distance budget rather than a step count:

```sql
-- All cells within 5 km of Times Square at resolution 15
SELECT a5_spherical_cap(a5_lonlat_to_cell(-74.0060, 40.7128, 15), 5000.0) AS nearby_cells;
```

That's a compacted covering — 248 cells plus the marker standing in for 2,480 resolution-15 cells. Test a single cell against it directly with [`a5_contains`](#a5_contains):

```sql
WITH cap AS (
  SELECT a5_spherical_cap(a5_lonlat_to_cell(-74.0060, 40.7128, 15), 5000.0) AS cells
)
SELECT a5_contains(cells, a5_lonlat_to_cell(-73.9857, 40.7484, 15)) AS midtown_in_range,
       a5_contains(cells, a5_lonlat_to_cell(-73.7781, 40.6413, 15)) AS jfk_in_range
FROM cap;
```

<QueryResult columns={["midtown_in_range", "jfk_in_range"]} rows={[["true", "false"]]} />

For a join against an indexed cell column, uncompact to the column's resolution and probe:

```sql
WITH cells AS (
  SELECT unnest(a5_uncompact(
      a5_spherical_cap(a5_lonlat_to_cell(-74.0060, 40.7128, 15), 5000.0)
  )) AS c
)
SELECT t.*
FROM   transactions t
JOIN   cells ON cells.c = t.cell_15;
```

## Coverings and the compaction marker

[`a5_compact`](#a5_compact) replaces complete groups of sibling cells with their parent — fewer rows to ship, expandable on the consumer side. The four resolution-6 children of a cell compact back to that one resolution-5 cell:

```sql
SELECT a5_compact(a5_cell_to_children(a5_lonlat_to_cell(-122.4, 37.8, 5))) AS compacted;
```

<QueryResult columns={["compacted"]} rows={[["[1937110789722734592, 17295511418962968640]"]]} />

The second element is not a cell. It's the **compaction marker** that ends every covering — from `a5_compact`, `a5_grid_disk`, `a5_grid_disk_vertex`, `a5_spherical_cap`, `a5_cell_to_subcells`, the set operations, and polygon results of `a5_geometry_to_cells` — and it records the resolution the cells stand for. Without it, a covering that compacted down to a single resolution-5 cell would look the same whether it was built at resolution 6 or 12. Read it, and the size of the region, without expanding anything:

```sql
WITH c AS (SELECT a5_compact(a5_cell_to_children(a5_lonlat_to_cell(-122.4, 37.8, 5))) AS cells)
SELECT a5_covering_resolution(cells)                             AS resolution,
       a5_count(cells)                                           AS cell_count,
       list_filter(cells, lambda x: NOT a5_is_compaction_marker(x)) AS compacted_cells
FROM c;
```

<QueryResult
  columns={["resolution", "cell_count", "compacted_cells"]}
  rows={[["6", "4", "[1937110789722734592]"]]}
/>

[`a5_uncompact`](#a5_uncompact) is the inverse — it expands a covering to its own resolution and drops the marker:

```sql
SELECT a5_uncompact(a5_compact(a5_cell_to_children(a5_lonlat_to_cell(-122.4, 37.8, 5)))) AS expanded;
```

A plain list with no marker is accepted too; its resolution is that of its finest cell. To expand a hand-built list to a resolution of your choosing, expand each cell instead:

```sql
SELECT flatten(list_transform(
    [a5_lonlat_to_cell(-122.4, 37.8, 5)],
    lambda c: a5_cell_to_children(c, 7)
)) AS expanded;
```

## Combine regions with set operations

Coverings compose directly — [`a5_union`](#a5_union), [`a5_intersect`](#a5_intersect), and [`a5_difference`](#a5_difference) return a new covering, [`a5_overlaps`](#a5_overlaps) answers yes/no, and [`a5_area`](#a5_area) measures the result in square meters. Nothing is unnested along the way:

```sql
WITH zones AS (
  SELECT a5_spherical_cap(a5_lonlat_to_cell(-74.0060, 40.7128, 13), 3000.0) AS lower_manhattan,
         a5_spherical_cap(a5_lonlat_to_cell(-73.9903, 40.6928, 13), 3000.0) AS brooklyn_heights
)
SELECT a5_overlaps(lower_manhattan, brooklyn_heights)                  AS overlaps,
       a5_count(a5_union(lower_manhattan, brooklyn_heights))           AS either,
       a5_count(a5_intersect(lower_manhattan, brooklyn_heights))       AS both_zones,
       a5_count(a5_difference(lower_manhattan, brooklyn_heights))      AS manhattan_only,
       round(a5_area(a5_intersect(lower_manhattan, brooklyn_heights)) / 1e6, 2) AS shared_km2
FROM zones;
```

<QueryResult
  columns={["overlaps", "either", "both_zones", "manhattan_only", { name: "shared_km2", align: "right" }]}
  rows={[["true", "84", "30", "27", 15.2]]}
/>

Both arguments must be at the same resolution — combining a resolution-12 covering with a resolution-13 one is an error, not a silent mix. `a5_area` and `a5_count` count overlapping cells more than once, so `a5_union` two regions before measuring their combined size.

## Migrate cell IDs stored before A5 1.0

A5 1.0 renumbered cells along a new curve. The cells themselves are unchanged at resolution 2 and finer, but their IDs are different — and an old ID is still well-formed, so it silently names a *different* cell instead of failing. [`a5_migrate`](#a5_migrate) converts a pre-1.0 ID to the current one:

```sql
SELECT a5_migrate(2742821848331845632)          AS migrated,
       a5_lonlat_to_cell(-74.0060, 40.7128, 15) AS current;
```

<QueryResult columns={["migrated", "current"]} rows={[["2760559170984869888", "2760559170984869888"]]} />

`2742821848331845632` is the resolution-15 Times Square cell as earlier versions of this extension encoded it. Migrate stored IDs exactly once — nothing in an ID says which index it belongs to, so running it twice corrupts them:

```sql
UPDATE indexed SET cell_15 = a5_migrate(cell_15);
```

Resolution-1 cells were redefined in 1.0 rather than renumbered, so `a5_migrate` leaves their IDs alone; re-index resolution-1 data from its source coordinates instead.

## Round-trip cell IDs as hex strings

Useful when sharing cell IDs with the upstream JS / TypeScript [A5 library](https://github.com/felixpalmer/a5), which uses the canonical 16-character hex form:

```sql
SELECT a5_u64_to_hex(a5_lonlat_to_cell(-122.4, 37.8, 10)) AS hex_id;
-- '1ae2988000000000'
```

```sql
SELECT a5_hex_to_u64('1ae2988000000000') AS cell_id;
```

[`a5_u64_to_hex`](#a5_u64_to_hex) and [`a5_hex_to_u64`](#a5_hex_to_u64) are pure conversions — store the `UBIGINT` form for compactness, hex for interchange.

## Spatial join via shared cell ID

Encode both sides at the same resolution and join on the cell ID — much cheaper than `ST_Intersects` for the "are these in the same neighborhood" question:

```sql
WITH events AS (
  SELECT *, a5_lonlat_to_cell(lon, lat, 12) AS cell FROM event_points
),
zones AS (
  SELECT *, a5_lonlat_to_cell(lon, lat, 12) AS cell FROM zone_centroids
)
SELECT z.zone_name, COUNT(*) AS event_count
FROM   events e
JOIN   zones  z USING (cell)
GROUP  BY z.zone_name;
```

For polygon zones rather than centroids, encode each zone with [`a5_geometry_to_cells`](#a5_geometry_to_cells) instead and `UNNEST(a5_uncompact(...))` the covering before joining.

## Inspect the base grid

The 12 root cells covering the entire globe at resolution 0:

```sql
SELECT unnest(a5_get_res0_cells()) AS root_cell;
```

[`a5_get_num_cells`](#a5_get_num_cells) returns the total cell count at any resolution (up to [`a5_max_resolution()`](#a5_max_resolution), 30) — useful for sizing decisions before encoding a large dataset. [`a5_world_cell`](#a5_world_cell) returns the single root cell (ID `0`) above all twelve of these; [`a5_is_valid_cell`](#a5_is_valid_cell) is a quick sanity check when a `UBIGINT` came from outside DuckDB — it rejects a cell whose encoded origin points past the 12 base cells, which is the shape of ID corruption you'd actually hit (a bit-flipped or truncated cell), not just any small integer:

```sql
SELECT a5_is_valid_cell(a5_lonlat_to_cell(-74.0060, 40.7128, 10)) AS ok,
       a5_is_valid_cell(63::UBIGINT << 58)                       AS bogus;
```
