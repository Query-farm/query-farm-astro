## Architecture

The `Shellfs` extension registers a DuckDB FileSystem subclass that recognizes two patterns:

- **Path ending in `|`** — the extension runs the command and reads bytes from its stdout.
- **Path beginning with `|`** — the extension runs the command and writes bytes to its stdin.

On Linux and macOS the command runs as `/bin/sh -c <command>`, started with [`posix_spawn`](https://man7.org/linux/man-pages/man3/posix_spawn.3.html) so the child gets the default `SIGPIPE` handling; the pipe is read and written unbuffered. On Windows the command runs through [`_popen`](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/popen-wpopen) (`cmd.exe`) in binary mode, so Parquet and other binary output passes through unchanged.

Everything else goes to the next filesystem in the chain (local disk, [`httpfs`](https://duckdb.org/docs/extensions/httpfs/overview.html), [`aws`](https://duckdb.org/docs/extensions/aws.html), etc. as usual). The integration is one sentence of glue: any DuckDB function that takes a filename — [`read_csv`](https://duckdb.org/docs/data/csv/overview.html), [`read_json`](https://duckdb.org/docs/data/json/loading_json.html), [`read_parquet`](https://duckdb.org/docs/data/parquet/overview.html), [`COPY ... TO`](https://duckdb.org/docs/sql/statements/copy.html#copy--to), `COPY ... FROM` — accepts pipe paths transparently.

## Why this exists

DuckDB ships with a strong built-in toolbox — HTTP, S3, parquet, JSON, etc. But the long tail is endless: a private API with custom auth, a tool that emits a proprietary text format, a one-off script that walks a directory tree. Rather than building a DuckDB extension for each, the `Shellfs` extension lets the existing Unix toolchain be the adapter.

## Performance

Pipes are streaming — DuckDB starts processing rows as soon as the first chunk arrives, not after the upstream command finishes. For a `seq 1 1_000_000_000 |` you can `LIMIT 100` and the upstream `seq` is killed via [`SIGPIPE`](https://man7.org/linux/man-pages/man7/signal.7.html) without producing the rest.

Process overhead per pipeline is small (one spawn of `/bin/sh`). The bottleneck is whatever your shell pipeline is doing, not the bridge.

## Exit status and early exits

The command's exit status is checked when the pipe closes. A command that exits with a non-zero status raises an `IO Error` (`Pipe process exited abnormally code=2: ...`), whether DuckDB is reading from it or writing to it.

For a command DuckDB reads from, list other acceptable exit codes in an `{allowed_exit_codes=...}` suffix just before the final `|`. `grep` exits with status 1 when nothing matches, for example:

```sql
SELECT count(*) AS matches
FROM read_csv('(echo n; seq 1 20 | grep 99) {allowed_exit_codes=0,1}|');
```

The codes are comma-separated non-negative integers, and listing them replaces the default of `0`. The suffix is only recognized on read pipes.

When writing, a command that exits before reading all of its input (for example `COPY ... TO '| head -n 3'`) closes the pipe early. By default that is an error (`Could not write to pipe "| head -n 3": Broken pipe`); it does not kill the DuckDB process. Set [`ignore_sigpipe`](#ignore_sigpipe) to treat it as success instead:

```sql
SET ignore_sigpipe = true;
COPY (SELECT * FROM range(1000000) t(n)) TO '| head -n 3' (FORMAT CSV, HEADER);
```

With `ignore_sigpipe` on, the rest of the output is discarded, the command's exit status is still checked, and a reading command that is terminated by `SIGPIPE` is not reported as an error. The setting is read for each pipe as it is opened.

## Compared to alternatives

- **[`copy ... from program 'cmd'`](https://www.postgresql.org/docs/current/sql-copy.html)** in PostgreSQL — same idea, more cumbersome syntax. The `Shellfs` extension slips into any DuckDB filename context.
- **Python [`subprocess`](https://docs.python.org/3/library/subprocess.html) + DataFrames** — much heavier setup; you give up DuckDB's vectorized execution against the streamed data.
- **[DuckDB built-ins](https://duckdb.org/docs/extensions/overview.html)** — use those first. Reach for the `Shellfs` extension only when the data lives behind a tool DuckDB can't speak natively.

## Security

<Callout type="danger" title="Pipe paths execute arbitrary shell commands">
The same rule that applies to [`os.system(user_input)`](https://docs.python.org/3/library/os.html#os.system) in Python applies here: **never** build pipe paths from untrusted strings. In a multi-tenant or hosted DuckDB environment, consider not loading the `Shellfs` extension at all, or restricting which roles can use it. See [OWASP — Command Injection](https://owasp.org/www-community/attacks/Command_Injection) for the threat model.
