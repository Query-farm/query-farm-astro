## Architecture

The `Shellfs` extension registers a DuckDB FileSystem subclass that recognizes two patterns:

- **Path ending in `|`** — the extension runs the command and reads bytes from its stdout.
- **Path beginning with `|`** — the extension runs the command and writes bytes to its stdin.

On Linux and macOS the command runs as `/bin/sh -c <command>`, started with [`posix_spawn`](https://man7.org/linux/man-pages/man3/posix_spawn.3.html) so the child gets the default `SIGPIPE` handling; the pipe is read and written unbuffered. On Windows the command runs through [`_popen`](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/popen-wpopen) (`cmd.exe`) in binary mode, so Parquet and other binary output passes through unchanged.

Everything else goes to the next filesystem in the chain (local disk, [`httpfs`](https://duckdb.org/docs/extensions/httpfs/overview.html), [`aws`](https://duckdb.org/docs/extensions/aws.html), etc. as usual). The integration is one sentence of glue: any DuckDB function that takes a filename — [`read_csv`](https://duckdb.org/docs/data/csv/overview.html), [`read_json`](https://duckdb.org/docs/data/json/loading_json.html), [`read_parquet`](https://duckdb.org/docs/data/parquet/overview.html), [`COPY ... TO`](https://duckdb.org/docs/sql/statements/copy.html#copy--to), `COPY ... FROM` — accepts pipe paths transparently.

## Why this exists

DuckDB ships with a strong built-in toolbox — HTTP, S3, parquet, JSON, etc. But the long tail is endless: a private API with custom auth, a tool that emits a proprietary text format, a one-off script that walks a directory tree. Rather than building a DuckDB extension for each, the `Shellfs` extension lets the existing Unix toolchain be the adapter.

## Performance

Pipes are streaming — DuckDB starts processing rows as soon as the first chunk arrives, not after the upstream command finishes. For a `seq 1 1_000_000_000 |` you can `LIMIT 100` and the upstream `seq` is killed via [`SIGPIPE`](https://man7.org/linux/man-pages/man7/signal.7.html) without producing the rest.

Process overhead per pipeline is small (one spawn of `/bin/sh`). The bottleneck is whatever your shell pipeline is doing, not the bridge.

## Exit status and early exits

The command's exit status is checked when the pipe closes. A command that exits with a non-zero status raises an `IO Error` (`Pipe process exited abnormally code=2: ...`), whether DuckDB is reading from it or writing to it.

For a command DuckDB reads from, list other acceptable exit codes in an `{allowed_exit_codes=...}` suffix just before the final `|`. `grep` exits with status 1 when nothing matches, for example:

```sql
SELECT count(*) AS matches
FROM read_csv('(echo n; seq 1 20 | grep 99) {allowed_exit_codes=0,1}|');
```

The codes are comma-separated non-negative integers, and listing them replaces the default of `0`. The suffix is only recognized on read pipes.

When writing, a command that exits before reading all of its input (for example `COPY ... TO '| head -n 3'`) closes the pipe early. By default that is an error (`Could not write to pipe "| head -n 3": Broken pipe`); it does not kill the DuckDB process. Set [`ignore_sigpipe`](#ignore_sigpipe) to treat it as success instead:

```sql
SET ignore_sigpipe = true;
COPY (SELECT * FROM range(1000000) t(n)) TO '| head -n 3' (FORMAT CSV, HEADER);
```

With `ignore_sigpipe` on, the rest of the output is discarded and the command's exit status is still checked. The setting is read for each pipe as it is opened.

## Stopping early and cancelling

When DuckDB stops reading before the end of a command's output — a `LIMIT`, for example — it closes the pipe. A command that is still writing exits with `SIGPIPE`, which is not an error. In the DuckDB 2.0 build, a command that keeps running anyway (one that ignores `SIGPIPE`, or is busy with something else) gets one second to exit. After that it receives `SIGTERM`, then `SIGKILL` one second later. The query never waits for it indefinitely:

```sql
-- `yes` never ends; DuckDB reads one row and the command is stopped
SELECT * FROM read_csv('yes |', header = false) LIMIT 1;
```

The same applies when a `COPY ... TO '| command'` fails partway through.

In the DuckDB 2.0 build, cancelling a query (Ctrl-C in the CLI, `interrupt()` in a client API) also works while DuckDB is waiting on a pipe: waiting for a command's output, for room to write its input, or for the command to exit. The command is then terminated as above. On Windows, pipes still block until the command produces output or exits.

## Compared to alternatives

- **[`copy ... from program 'cmd'`](https://www.postgresql.org/docs/current/sql-copy.html)** in PostgreSQL — same idea, more cumbersome syntax. The `Shellfs` extension slips into any DuckDB filename context.
- **Python [`subprocess`](https://docs.python.org/3/library/subprocess.html) + DataFrames** — much heavier setup; you give up DuckDB's vectorized execution against the streamed data.
- **[DuckDB built-ins](https://duckdb.org/docs/extensions/overview.html)** — use those first. Reach for the `Shellfs` extension only when the data lives behind a tool DuckDB can't speak natively.

### Turning shellfs off

In the DuckDB 2.0 build, the extension runs **no** command while [`enable_external_access`](https://duckdb.org/docs/configuration/overview) is `false`. That includes paths that look like they are inside [`allowed_directories`](https://duckdb.org/docs/operations_manual/securing_duckdb/overview). DuckDB checks those with a prefix match, so a "file" such as `'/tmp/x; other-command |'` would otherwise pass. Earlier builds ran such a command.

{/* check: skip intentionally fails, and would disable external access for later snippets */}
```sql
SET enable_external_access = false;
SELECT * FROM read_csv('echo 1 |');
-- Permission Error: Cannot run shell command "echo 1 |": shellfs commands are
-- disabled because enable_external_access is false
```

To turn off shell commands while still allowing other external access (local files, HTTP), set [`shellfs_enabled`](#shellfs_enabled) to `false`. This setting only works in one direction: once it is `false`, `SET shellfs_enabled = true` and `RESET shellfs_enabled` are rejected. A plain `SET` affects the current connection. `SET GLOBAL` affects every connection that has not set it itself.

{/* check: skip would disable shellfs for later snippets */}
```sql
SET GLOBAL shellfs_enabled = false;
```

For a hard guarantee, combine either setting with [`lock_configuration`](https://duckdb.org/docs/configuration/overview), or don't load the extension.

## Changes in the DuckDB 2.0 build

- **Security:** no command runs when `enable_external_access` is `false`, even inside `allowed_directories` (see [Turning shellfs off](#turning-shellfs-off)).
- **New setting:** [`shellfs_enabled`](#shellfs_enabled), a one-way switch that turns shell commands off.
- **Wrong direction is an error:** writing to a path that ends in `|` (`COPY ... TO 'cmd |'`) now fails with `Cannot write to "cmd |": a path that ends with '|' is a command that DuckDB reads from`. Reading a path that starts with `|` fails the same way. Earlier builds started the command in the wrong direction.
- **No hangs:** queries waiting on a pipe can be cancelled, and a command that keeps running after DuckDB stops reading is terminated (see [Stopping early and cancelling](#stopping-early-and-cancelling)).
- **Early close is never an error:** stopping early (a `LIMIT`) is not reported as a failure of the command, with or without `ignore_sigpipe`. Earlier builds printed `Exception in ShellFileHandle destructor` to standard output. A non-zero exit status after DuckDB has read all of a command's output is still an error.
- **Binary pipes on Windows:** commands are opened in binary mode, so Parquet and other binary formats pass through without CRLF translation.
