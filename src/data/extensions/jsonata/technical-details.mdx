## What you can do with one query

The headline pattern — reshape a nested JSON column into a clean output object in a single SQL projection:

```sql
SELECT jsonata('{
  "name":     FirstName & " " & Surname,
  "mobile":   Phone[type="mobile"].number,
  "lifetime": $sum(Orders.(Quantity * UnitPrice))
}', payload) AS profile
FROM contacts;
```

One [`jsonata`](#jsonata) call replaces a stack of [`json_extract_string`](https://duckdb.org/docs/data/json/json_functions.html) projections plus an `unnest` subquery for the order roll-up. The expression — array filter, [object construction](https://docs.jsonata.org/construction), and an [aggregation function](https://docs.jsonata.org/aggregation-functions) — stays in one string.

<Callout type="note" title="Best fit, scoped honestly">
This extension exposes [JSONata](https://jsonata.org/) as a scalar SQL function — [`jsonata`](#jsonata), in two arities — plus [`jsonata_validate`](#jsonata_validate) for checking expression syntax. There is **no `ATTACH` interface, no secrets, no I/O**. The functions operate on `JSON` values DuckDB already has in memory.

It is the right tool when DuckDB's [native JSON functions](https://duckdb.org/docs/data/json/json_functions.html) get verbose — array predicate filters, object reshaping, multi-step transforms. It is **not** a JSON loader (use DuckDB's [`read_json`](https://duckdb.org/docs/data/json/loading_json.html) for that) and it does not register custom DuckDB UDFs as callables inside the JSONata expression.
</Callout>

## Architecture

The extension is a C++ scalar UDF built on [jsonata-cpp](https://github.com/rayokota/jsonata-cpp), a port of the JSONata reference implementation. Each call to [`jsonata`](#jsonata) takes a JSONata expression string and a `JSON` value, parses the expression into an AST, evaluates it against the document, and returns a `JSON` result. There is no network, no state carried from one row to the next, and no DuckDB type beyond the standard [`JSON`](https://duckdb.org/docs/data/json/json_functions.html) type.

Parsed expressions are cached. When the `expression` argument is a SQL constant — by far the common case — the parser runs once per worker thread and the compiled program is reused for every row. In the DuckDB 2.0 build an expression *column* is cached too: each thread keeps its 32 most recently used expressions, so a table of a few dozen stored expressions isn't re-parsed on every row. Per-row cost is dominated by the JSON walk plus operator application; deeply-nested documents and large arrays scale linearly with the data they touch.

The 3-arg form, [`jsonata(expr, json, bindings)`](#jsonata), takes a JSON object whose keys become `$variable` names inside the expression. This is how you pass per-query values — thresholds, ids, dates — into an otherwise static expression so the parse cache still applies.

## When to reach for JSONata vs DuckDB native JSON

DuckDB ships a [rich JSON function library](https://duckdb.org/docs/data/json/json_functions.html) — [`json_extract`](https://duckdb.org/docs/data/json/json_functions.html), [`json_extract_string`](https://duckdb.org/docs/data/json/json_functions.html), the [`->`/`->>` operators](https://duckdb.org/docs/data/json/json_functions.html), [`json_structure`](https://duckdb.org/docs/data/json/json_functions.html), and a [JSON data type](https://duckdb.org/docs/data/json/json_functions.html). For one-field-one-path access these are the right call — vectorized, idiomatic SQL, no extra extension.

JSONata is the better fit when the path includes any of:

- **Predicate filters on arrays.** `Phone[type="mobile"].number` selects matching elements *and* projects in one step. The native equivalent is `unnest` plus a subquery with a `WHERE` clause.
- **Object reshaping.** [Construction expressions](https://docs.jsonata.org/construction) build a fresh JSON object literal — pull, rename, and compute fields together. The native equivalent is one `json_extract_string` per output field.
- **Embedded aggregation.** [`$sum`, `$count`, `$max`](https://docs.jsonata.org/aggregation-functions) operate on arrays *inside* the JSON document. The native equivalent leaves the JSON value, unnests, aggregates, and returns.
- **Higher-order array operations.** [`$map`, `$filter`, `$reduce`](https://docs.jsonata.org/higher-order-functions) keep transforms inline. The native equivalent is a lateral subquery.

Concrete contrast — selecting the mobile number from a contact's `Phone` array:

```sql
-- DuckDB native: extract the array, unnest, filter, project
SELECT (
  SELECT json_extract_string(p, '$.number')
  FROM   unnest(json_extract(payload, '$.Phone')::JSON[]) AS t(p)
  WHERE  json_extract_string(p, '$.type') = 'mobile'
  LIMIT  1
) AS mobile
FROM contacts;
```

```sql
-- JSONata: one expression
SELECT jsonata('Phone[type="mobile"].number', payload) AS mobile
FROM contacts;
```

For a single field at a fixed path, native is simpler. The break-even is roughly "any predicate, any reshape, or more than two output fields."

## Compared to alternatives

- **DuckDB native JSON ([`->>`](https://duckdb.org/docs/data/json/json_functions.html), [`json_extract`](https://duckdb.org/docs/data/json/json_functions.html))** — the right choice for simple field-by-field access. Stays simpler and avoids the extension entirely. Use JSONata when the expression starts to fan out across array predicates or object construction.
- **[`jq`](https://github.com/jqlang/jq) outside DuckDB** — same general role for JSON, different language. `jq` is a separate process — file in, file out. JSONata-in-DuckDB keeps the transform inside the SQL plan, vectorized, joinable, and `EXPLAIN`-able alongside the rest of the query.
- **Application-side JSONata libraries** ([JS](https://github.com/jsonata-js/jsonata), [Python](https://github.com/qlyoung/python-jsonata-poc), etc.) — the right call when the surrounding logic already lives in the app. Bringing JSONata into DuckDB matters when the JSON sits in a column and the rest of the pipeline is SQL — no row-format conversion, no result shuttling.

## Iterating on expressions

JSONata expressions live inside SQL string literals, which makes them awkward to edit in place. The official [JSONata exerciser](https://try.jsonata.org/) takes a sample document and gives live results — the fastest loop for any non-trivial expression. The evaluator there matches what the extension runs, so once an expression is right in the exerciser it transfers unchanged into the SQL string.

## Resource limits

The DuckDB 2.0 build bounds every evaluation, so a runaway expression fails the query instead of crashing or hanging DuckDB:

| Setting | Default | Effect |
|---|---|---|
| `jsonata_max_depth` | `1000` | Maximum evaluation depth, which bounds recursion in user-defined functions. Exceeding it raises `JSONata evaluation exceeded the maximum evaluation depth of 1000`. `0` removes the depth limit. |
| `jsonata_timeout_ms` | `10000` | Maximum wall-clock time of one evaluation (one row). Exceeding it raises `JSONata evaluation timed out after … ms`. `0` disables the timeout. |

```sql
SET jsonata_max_depth = 5000;  -- deeper recursion
SET jsonata_timeout_ms = 500;  -- fail fast on slow expressions
```

Independently of these settings:

- A running evaluation stops when the query is cancelled (Ctrl-C, `interrupt()`).
- A native stack guard, sized to the thread the query actually runs on, stops recursion before it can overflow the stack even with `jsonata_max_depth = 0`.
- JSON documents and bindings nested more than 1,000 levels deep, and expressions nested too deeply for the available stack, are rejected with an error before evaluation.

A tail-recursive loop such as `($f := function($x){ $f($x) }; $f(1))` never grows the stack, so only the timeout or cancellation stops it.

## Regular expressions

In the DuckDB 2.0 build, JSONata regular expressions (`/pattern/flags`, and the patterns given to [`$match`](https://docs.jsonata.org/string-functions#match), [`$contains`](https://docs.jsonata.org/string-functions#contains), [`$split`](https://docs.jsonata.org/string-functions#split) and [`$replace`](https://docs.jsonata.org/string-functions#replace)) run on [RE2](https://github.com/google/re2/wiki/Syntax), the same engine as DuckDB's [`regexp_matches`](https://duckdb.org/docs/sql/functions/regular_expressions). Matching takes linear time, so no pattern can hang a query through catastrophic backtracking, and long subject strings are safe. The `i` (case-insensitive) and `m` (multiline: `^` and `$` match at line breaks) flags are supported.

RE2 has no lookaround (`(?=…)`, `(?!…)`, `(?<=…)`) and no backreferences (`\1`). Patterns that use them fail with `invalid regular expression`.

## Changes in the DuckDB 2.0 release

<Callout type="warning" title="Behaviour changes in the DuckDB 2.0 build">
- **Regular expressions use RE2.** Lookaround and backreferences now raise `invalid regular expression`, and the `m` flag is honoured (earlier builds ignored it). See [Regular expressions](#regular-expressions).
- **Evaluations are bounded.** Expressions that run longer than `jsonata_timeout_ms` (10 seconds by default) or recurse deeper than `jsonata_max_depth` (1,000) now fail; raise or disable the settings for legitimately heavy expressions. See [Resource limits](#resource-limits).
- **JSON nested more than 1,000 levels deep** is rejected.
</Callout>

Also new in the DuckDB 2.0 build:

- **Crash fixes:** non-terminating recursion, deeply nested JSON or expressions, and long regex subject strings used to crash DuckDB; they now raise errors, and a runaway evaluation can be cancelled.
- **New function:** [`jsonata_validate`](#jsonata_validate) checks whether a string is a valid JSONata expression without evaluating it.
- **Volatile time and random functions:** expressions that call `$now()`, `$millis()` or `$random()` are evaluated for every row instead of once per query.
- **Performance:** parsed expressions are cached per thread for expression columns as well as constants, and jsonata-cpp no longer throws and catches two internal exceptions for every result, which halves the per-row cost of simple expressions.
- **jsonata-cpp 0.3.0.**
