## Subscribe to a WebSocket channel

```sql
-- Open a subscription. The URL itself is the subscription identifier —
-- pass it to the read / send / unsubscribe functions later.
CALL radio_subscribe('wss://stream.example.com/events');

-- Inspect what's subscribed
SELECT * FROM radio_subscriptions();
```

The URL is what every other `radio_*` function takes as its subscription key. If you'll reuse it across many statements, stash it in a SQL variable and bind via `:feed`:

```sql
SET VARIABLE feed = 'wss://stream.example.com/events';

CALL radio_subscribe(getvariable('feed'));

SELECT * FROM radio_subscription_received_messages(getvariable('feed'));
```

See [`radio_subscribe`](#radio_subscribe) and [`radio_subscriptions`](#radio_subscriptions) for the full signatures, including the optional named parameters for buffer sizing and transmit retry tuning.

## Subscribe to Redis Pub/Sub

Same function, different URL — Radio routes WebSocket and [Redis Pub/Sub](https://redis.io/docs/latest/develop/interact/pubsub/) through the same surface:

```sql
CALL radio_subscribe('redis://cache.example.com:6379/0?channel=events');

-- Drain the same way as a WebSocket subscription, keyed by URL
SELECT receive_time, message
FROM radio_subscription_received_messages('redis://cache.example.com:6379/0?channel=events')
ORDER BY receive_time DESC;
```

## Drain received messages

```sql
-- Recent messages across all subscriptions
SELECT subscription_url, channel, receive_time, message
FROM radio_received_messages()
ORDER BY receive_time DESC
LIMIT 100;
```

```sql
-- One feed only — pass the same URL you subscribed with
SELECT receive_time, channel, message
FROM radio_subscription_received_messages('wss://stream.example.com/events')
ORDER BY receive_time DESC;
```

The full row shape from `radio_received_messages()` / `radio_subscription_received_messages(url)` is `(subscription_id UBIGINT, subscription_url VARCHAR, message_id UBIGINT, message_type, receive_time TIMESTAMP_MS, seen_count UBIGINT, channel VARCHAR, message BLOB)`. The payload is a `BLOB` — turn UTF-8 text into a `VARCHAR` with `decode(message)`, then use [DuckDB's JSON functions](https://duckdb.org/docs/data/json/loading_json.html) for structured payloads. (A plain `message::VARCHAR` cast escapes quotes and non-ASCII bytes in DuckDB 2.0.) These are normal DuckDB table functions — `JOIN`, filter, aggregate, push to Parquet, anything you'd do with a regular table. See [`radio_received_messages`](#radio_received_messages) and [`radio_subscription_received_messages`](#radio_subscription_received_messages).

## Wait for fresh messages before reading

For loops that need to act *as* messages arrive (rather than polling on a timer), [`radio_listen`](#radio_listen) blocks the connection until something lands in the inbox or a timeout elapses:

```sql
-- Block up to 30 seconds for an unread message on any subscription.
-- Args: (wait_for_messages, timeout). Returns the subscriptions with unread messages.
CALL radio_listen(true, INTERVAL '30 seconds');

-- Then drain
SELECT * FROM radio_received_messages() ORDER BY receive_time DESC LIMIT 1;
```

Reading messages marks them seen, so the next `radio_listen` waits for new ones. Pair with [`radio_sleep`](#radio_sleep) when scripting between polls. On the DuckDB 2.0 build a message that arrives while `radio_listen` is starting its wait is never missed, and the wait can be interrupted with Ctrl-C.

## Send a message and track delivery

```sql
-- Args: (subscription_url, channel, payload, max_attempts, expire_duration).
-- A message not delivered within expire_duration moves to the time_expired state.
CALL radio_transmit_message(
  'wss://stream.example.com/events',
  /* channel       */ 'main',
  /* payload       */ '{"type":"hello","at":"2026-04-28T12:00:00Z"}',
  /* max_attempts  */ 3,
  /* expire_duration */ INTERVAL '30 seconds'
);

-- Inspect transmit queue + delivery state
SELECT message_id, message
FROM radio_subscription_transmit_messages('wss://stream.example.com/events')
ORDER BY message_id DESC;
```

A `VARCHAR` payload goes out as a WebSocket text frame, which JSON APIs such as Slack expect; pass a `BLOB` (`'...'::BLOB`) to send a binary frame instead. The bytes are sent as-is either way. A `NULL` payload is an error.

Per-subscription delivery counters live on [`radio_subscriptions`](#radio_subscriptions) (`transmit_successes`, `transmit_failures`, `transmit_last_success_time`, `transmit_last_failure_time`); poll those to confirm delivery progress. See [`radio_transmit_message`](#radio_transmit_message) and [`radio_subscription_transmit_messages`](#radio_subscription_transmit_messages).

## Garbage-collect the outbox

```sql
-- Drop all already-delivered transmit messages
CALL radio_subscription_transmit_messages_delete_finished('wss://stream.example.com/events');
```

```sql
-- Or drop one specific pending outgoing message. Replace 42 with a message_id
-- from radio_subscription_transmit_messages.
CALL radio_subscription_transmit_message_delete('wss://stream.example.com/events', 42::UBIGINT);
```

See [`radio_subscription_transmit_messages_delete_finished`](#radio_subscription_transmit_messages_delete_finished) and [`radio_subscription_transmit_message_delete`](#radio_subscription_transmit_message_delete).

## Test pipelines without a real upstream

Inject messages straight into a subscription's inbox to exercise downstream SQL — no broker, no real WebSocket, no flake. On the DuckDB 2.0 build the `loopback://` transport needs no server at all: messages transmitted on it come back to the same subscription.

{/* check: skip DuckDB 2.0 build only (loopback transport) */}
```sql
CALL radio_subscribe('loopback://test');
```

{/* check: skip DuckDB 2.0 build only (loopback transport) */}
```sql
-- Inject a message as if it had arrived from the network
CALL radio_subscription_received_message_add('loopback://test', 'orders', '{"type":"test","value":42}');

-- Or transmit one and let the loopback deliver it
CALL radio_transmit_message('loopback://test', 'orders', '{"type":"test","value":43}', 3, INTERVAL '10 seconds');
CALL radio_flush(INTERVAL '5 seconds');

SELECT channel, decode(message)::JSON ->> 'value' AS value
FROM radio_subscription_received_messages('loopback://test')
ORDER BY message_id;
```

See [`radio_subscription_received_message_add`](#radio_subscription_received_message_add). On the Haybarn 1.5 build, which has no loopback transport, inject into any subscribed URL instead (the message must be a `BLOB` there).

## Detect dropped messages

Each subscription's receive queue holds `receive_message_capacity` messages (default 1000) and evicts the oldest when full. On the DuckDB 2.0 build, [`radio_subscriptions`](#radio_subscriptions) counts the evicted messages nobody had read:

{/* check: skip DuckDB 2.0 build only (new columns) */}
```sql
SELECT url, received_messages_queued, received_messages_dropped_unseen
FROM radio_subscriptions();
```

If `received_messages_dropped_unseen` grows, read more often or resubscribe with a larger `receive_message_capacity`.

## Tear down

```sql
-- Close the subscription
CALL radio_unsubscribe('wss://stream.example.com/events');
```

See [`radio_unsubscribe`](#radio_unsubscribe).

## Diagnostics

```sql
SELECT radio_version();   -- e.g. '2026110701' on the DuckDB 2.0 build
```

Use [`radio_version`](#radio_version) to confirm what's loaded when matching against bug reports. [`radio_flush`](#radio_flush) waits for every subscription's outgoing messages to be sent (or given up on) and returns whether they all finished in time — it does not touch received messages.

## Sandboxed sessions

On the DuckDB 2.0 build, `radio_subscribe` and `radio_transmit_message` refuse WebSocket and Redis URLs once `enable_external_access` is false:

{/* check: skip disabling external access would break the remaining examples */}
```sql
SET enable_external_access = false;
CALL radio_subscribe('wss://stream.example.com/events');
-- Permission Error: radio_subscribe is disabled because enable_external_access is false
```

Existing subscriptions can still be inspected, and `loopback://` subscriptions keep working.
