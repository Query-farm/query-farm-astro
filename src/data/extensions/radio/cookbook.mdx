## Subscribe to a WebSocket channel

```sql
-- Open a subscription to a WebSocket
CALL radio_subscribe('wss://stream.example.com/events', 'feed1');

-- Inspect what's subscribed
SELECT * FROM radio_subscriptions();
```

Each subscription gets a logical name (`'feed1'`) — use it everywhere downstream to filter the inbox / outbox. See [`radio_subscribe`](#radio_subscribe) and [`radio_subscriptions`](#radio_subscriptions) for the full signatures.

## Subscribe to Redis Pub/Sub

Same function, different URL — Radio routes WebSocket and [Redis Pub/Sub](https://redis.io/docs/latest/develop/interact/pubsub/) through the same surface:

```sql
CALL radio_subscribe('redis://cache.example.com:6379/0?channel=events', 'redis-feed');

-- Drain the same way as a WebSocket subscription
SELECT received_at, payload
FROM radio_subscription_received_messages('redis-feed')
ORDER BY received_at DESC;
```

## Drain received messages

```sql
-- Recent messages across all subscriptions
SELECT subscription, received_at, payload
FROM radio_received_messages()
ORDER BY received_at DESC
LIMIT 100;

-- One feed only
SELECT received_at, payload
FROM radio_subscription_received_messages('feed1')
ORDER BY received_at DESC;
```

These are normal DuckDB table functions — `JOIN`, filter, aggregate, push to Parquet, anything you'd do with a regular table. See [`radio_received_messages`](#radio_received_messages) and [`radio_subscription_received_messages`](#radio_subscription_received_messages).

## Wait for fresh messages before reading

For loops that need to act *as* messages arrive (rather than polling on a timer), [`radio_listen`](#radio_listen) blocks the connection until something lands in the inbox or a timeout elapses:

```sql
-- Block until a message arrives on any subscription
CALL radio_listen();

-- Then drain
SELECT * FROM radio_received_messages() ORDER BY received_at DESC LIMIT 1;
```

Pair with [`radio_sleep`](#radio_sleep) when scripting between polls.

## Send a message and track delivery

```sql
CALL radio_transmit_message('feed1', '{"type":"hello","at":"2026-04-28T12:00:00Z"}');

-- Inspect transmit queue + delivery state
SELECT message_id, status, transmitted_at, payload
FROM radio_subscription_transmit_messages('feed1')
ORDER BY queued_at DESC;
```

Pending messages get a `status` column you can poll until it flips to `delivered`. See [`radio_transmit_message`](#radio_transmit_message) and [`radio_subscription_transmit_messages`](#radio_subscription_transmit_messages).

## Garbage-collect the outbox

```sql
-- Drop all already-delivered transmit messages
CALL radio_subscription_transmit_messages_delete_finished('feed1');

-- Or drop one specific pending outgoing message
CALL radio_subscription_transmit_message_delete('feed1', :message_id);
```

See [`radio_subscription_transmit_messages_delete_finished`](#radio_subscription_transmit_messages_delete_finished) and [`radio_subscription_transmit_message_delete`](#radio_subscription_transmit_message_delete).

## Test pipelines without a real upstream

Inject messages straight into a subscription's inbox to exercise downstream SQL — no broker, no real WebSocket, no flake:

```sql
CALL radio_subscription_received_message_add('feed1', '{"type":"test","value":42}');

SELECT * FROM radio_subscription_received_messages('feed1');
```

See [`radio_subscription_received_message_add`](#radio_subscription_received_message_add). Useful for unit-testing pipelines that consume `radio_*` tables.

## Tear down

```sql
-- Close the subscription
CALL radio_unsubscribe('feed1');
```

See [`radio_unsubscribe`](#radio_unsubscribe).

## Diagnostics

```sql
SELECT radio_version();   -- e.g. '0.4.x'
```

Use [`radio_version`](#radio_version) to confirm what's loaded when matching against bug reports. [`radio_flush`](#radio_flush) drains all currently-buffered messages so subsequent reads see only fresh data.
