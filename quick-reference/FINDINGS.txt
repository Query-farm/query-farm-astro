QUICK-REFERENCE PREPARATION: VERIFIED FINDINGS
Recorded and reproduced: October 7, 2026

Scope: DuckDB CLI v1.5.6 on macOS 15.6.1, arm64. Community extension build
identifiers below come from duckdb_extensions(). These are observations of
these builds, not claims about every release or platform. Each SQL block
starts in a fresh in-memory connection; load already-installed extensions.
The observations below preserve the original reproductions against older
community builds. Implementation fixes have since been committed and pushed
to each repository's v1.5 branch; see the resolution record at the end.
The PDFs and authored website docs now describe the fixes while identifying
older affected builds. See validation.json for tested revisions, local-build
SHA-256 provenance, guide-example coverage and external-service deferrals.

VERIFIED IMPLEMENTATION / COMPATIBILITY ISSUES

1. STOCHASTIC: integer sampling disagrees with analytical functions
   Build: 234c881. Classification: likely correctness bug.

   LOAD stochastic;
   SELECT dist_uniform_int_pdf(1,6,3), dist_uniform_int_cdf(1,6,3),
          dist_uniform_int_mean(1,6), dist_uniform_int_variance(1,6);

   Observed: 0.2, 0.4, 3, 2.
   Expected for a discrete uniform draw from integers 1 through 6:
   1/6, 1/2, 3.5, 35/12. The local implementation in
   stochastic/src/distribution_uniform_int.cpp uses
   std::uniform_int_distribution for sampling and Boost's continuous uniform
   distribution for analytical functions. Mean and variance additionally
   return BIGINT, truncating fractional results. The mismatch affects the
   uniform_int family; this is not evidence that all 22 families are wrong.
   Guide mitigation: explicitly flag the analytical mismatch and use 1.0/6
   for a fair die's probability mass.

2. HASHFUNCS: advertised canonical XXH3-128 digest swaps 64-bit halves
   Build: 0dec806. Classification: verified interoperability bug relative to
   the documented promise to match canonical xxHash/Python hex digests.

   LOAD hashfuncs;
   SELECT xxh3_128_hex('hello');

   Observed: c779cfaa5e523818b5e9c1ad071b3e7f
   Independent comparison (no newline in the input):
     printf %s hello | xxhsum -H128
   Observed canonical digest: b5e9c1ad071b3e7fc779cfaa5e523818
   The extension formats low64 before high64; canonical xxHash formats
   high64 before low64. The local hashfuncs/src/hashfuncs_extension.cpp
   explicitly formats the reversed order while describing it as canonical.
   Scope: directly reproduced for the unseeded string 'hello'; seeded and
   other input overloads were not exhaustively tested. The UHUGEINT result's
   to_hex output has the same ordering in this build, so switching to that
   overload is not a demonstrated workaround.
   Guide mitigation: swap the 16-character halves for canonical interchange.

3. GEOSILO: documented spatial-first load order fails
   Builds: geosilo d088741; spatial 04270fe.
   Classification: verified extension compatibility / registration issue.

   LOAD spatial;
   LOAD geosilo;

   Observed: GeoSilo initialization raises
     Scalar Function with name "ST_GeometryType" already exists!
   Expected under the site's documented spatial-first setup: both load.
   Scope: load-order-specific. In a fresh connection, LOAD geosilo followed
   by LOAD spatial succeeds; that only establishes successful loading, not
   correctness of every combined spatial operation. GeoSilo alone also
   passes the guide's native-GEOMETRY storage and measurement examples.
   Guide mitigation: use geosilo alone for the printed examples on 1.5.6.

4. LINDEL: signed one-dimensional decode rejects its own encoded key
   Build: 6435106. Classification: likely correctness bug / unsupported path.

   LOAD lindel;
   SELECT hilbert_decode(hilbert_encode([-1]::INTEGER[1]),1,false,false);

   Observed: Invalid Input Error: Expected one of the following types:
     UINTEGER, USMALLINT, UTINYINT, UBIGINT, UHUGEINT
   Replacing both hilbert functions with morton functions produces the same
   error. Expected round trip for this signed one-dimensional input: [-1].
   Controls that succeed: unsigned UINTEGER[1] with flags false,true, and
   signed INTEGER[2] with flags false,false. This is distinct from the now
   corrected site claims about bit-pattern encoding, supported widths and
   unsigned casts of negative coordinates.
   Guide/site mitigation: disclose the signed one-dimensional limitation.

5. FUZZYCOMPLETE: loading after preloaded autocomplete does not activate it
   Build: 9746833. Classification: verified activation limitation and
   documentation mismatch; source explicitly makes this a current limitation.

   SELECT function_oid FROM duckdb_functions()
     WHERE function_name='sql_auto_complete';
   LOAD fuzzycomplete;
   SELECT function_oid FROM duckdb_functions()
     WHERE function_name='sql_auto_complete';
   SELECT extension_name, loaded FROM duckdb_extensions()
     WHERE extension_name IN ('autocomplete','fuzzycomplete');

   Observed: the function OID is unchanged (20625 in the reproduction),
   while both extensions report loaded=true. CLI 1.5.6 already loads stock
   autocomplete. Local fuzzycomplete/src/fuzzycomplete_extension.cpp only
   registers its function if autocomplete is not loaded. This contradicts
   the site's "last one loaded wins" and replacement claims. The SQL result
   alone would not establish implementation identity; source confirms it.
   Scope: preloaded-provider behavior; interactive Tab was not automated.
   Guide mitigation: inspect the provider and do not equate LOAD success
   with fuzzy-completion activation.

6. INFLECTOR: a common irregular singular is unchanged
   Build: ac9b69f. Classification: verified behavior; likely linguistic
   correctness gap, with intended upstream inflection rules still to confirm.

   LOAD inflector;
   SELECT inflector_to_plural('person'), inflector_to_singular('people');

   Observed: people, people. Expected for the ordinary plural of person:
   people, person. English inflection is context-dependent; this narrow test
   does not establish how all irregular words should be handled.
   Guide mitigation: warn that inflection is not always reversible.

DOCUMENTATION, API METADATA AND BUILD MISMATCHES

- Stochastic Pareto parameter labels (234c881):
    LOAD stochastic;
    SELECT dist_pareto_mean(1,3);
    SELECT parameters FROM duckdb_functions()
      WHERE function_name='dist_pareto_mean';
  Observed: mean=1.5, labels=[shape, minimum]. Runtime order is (scale, shape),
  consistent with the local sampling and Boost distribution constructors.
  The result 1.5 is correct for scale=1, shape=3. Fix labels/documentation
  before considering any incompatible change to established positional SQL.
  The Stochastic PDF uses the effective runtime order and calls out the labels.

- JSON Schema validation (20cc158):
    LOAD json_schema;
    SELECT json_schema_validate('{"type":"integer"}', '"five"');
  Observed: Invalid Input Error, "unexpected instance type"; not FALSE as
  some site prose claims. This alone does not establish an implementation
  defect. The guide uses COALESCE(TRY(json_schema_validate(...)), false),
  and notes that TRY also hides malformed-schema errors.

- MiniJinja row context (a4e836b):
    LOAD minijinja;
    SELECT minijinja_render('Hello {{ name }}', json_object('name',name))
    FROM (VALUES ('Ada'),('Grace')) t(name);
  Observed: Binder Error, "argument is not foldable". Existing row-based
  site examples use the wrong entry point. Use minijinja_render_with_context
  for a context constructed from columns; the guide executes that pattern.

- ADBC Scanner API generation (installed 7a21dda):
    LOAD adbc_scanner;
    SELECT function_name,parameter_types FROM duckdb_functions()
      WHERE function_name IN ('adbc_scan','adbc_scan_table','adbc_connect');
  Observed: adbc_scan and adbc_scan_table take BIGINT handles as their first
  argument. The newer source revision 7e5210c introduces the ATTACH API used
  in the guide. This is a build/API mismatch, not a verified connector defect.
  Driver-backed examples remain explicitly deferred until a matching build
  and separately installed driver are available.

- Shellfs gzip export (4f724fc):
    LOAD shellfs;
    COPY (SELECT 1 AS n) TO '| gzip > /tmp/example.csv.gz'
      (FORMAT CSV, HEADER);
  Observed in an isolated temporary-directory reproduction: one gzip
  decompression still begins with gzip magic bytes 1f8b; a second produces
  CSV "n\n1\n". DuckDB detects compression from the destination string, then
  the shell command compresses again. The guide adds COMPRESSION UNCOMPRESSED
  to COPY when gzip owns compression. This is an example/integration pitfall,
  not proof of a Shellfs implementation error.

- TSID optional seed (21457c7):
    LOAD tsid;
    SELECT tsid('example');
  Observed: no matching overload; the catalog offers only tsid() -> VARCHAR.
  Website descriptions of an optional seed and its ordering guarantees do
  not match the installed API. The guide uses tsid() and avoids promising
  strict global insertion order from concurrent generation.
