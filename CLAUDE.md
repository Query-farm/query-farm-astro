# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The query.farm website: an Astro 6 static site (`output: 'static'`) serving as a DuckDB extension marketplace/documentation hub, plus product pages (Haybarn, VGI), a blog, and company pages. Tailwind CSS 4 (via `@tailwindcss/vite`), React only for interactive islands, Zod for data validation.

## Commands

```sh
npm run dev              # dev server at localhost:4321
npm run build            # static build to ./dist/
npm run check            # Astro + TypeScript diagnostics
npm run validate         # current CI gate: deterministic production build
npm run preview          # serve the built dist/ locally
npm run check:examples   # validate all SQL examples actually parse & execute
npm run snapshot:usage   # refresh extension load numbers from Cloudflare AE
npm run refresh:snapshots # explicitly refresh all committed remote snapshots
```

`snapshot:usage` wraps `extension-diff-tools/usage-snapshot.py` (`scripts/snapshot-usage.sh`, 90-day window): it sources `.env` for `CF_API_TOKEN`/`CF_ACCOUNT_ID` and rewrites every `generated/usage.json` plus `src/data/generated/usage-summary.json`. Production builds consume committed snapshots and never refresh them implicitly. Run `refresh:snapshots` explicitly, review the resulting diff, and commit it to publish new data. The card/detail labels render the snapshot's own period string (e.g. "last 90 days"), so changing `--days` updates the displayed window automatically.

`npm run validate` is the standard local and CI gate. `npm run check` is available for the existing Astro/TypeScript diagnostics backlog but is not yet required in CI. `check:examples` (extension-diff-tools/check-examples.py) is the deeper content validation: it executes every SQL snippet in extension quickStarts, function examples, `cookbook.mdx`, and `technical-details.mdx`, reporting PARSE-FAIL/EXEC-FAIL. Per-extension test fixtures live in `src/data/extensions/<slug>/augment/check-fixtures.sql`.

Other tools in `extension-diff-tools/` (run against an extension repo, not this one): `extension-diff.py` regenerates an extension's `generated/*.json` (functions, pragmas, secrets, types, views — never `compatibility.json`) by diffing a baseline DuckDB build against one with the extension loaded; `bake-examples.py` executes example SQL and bakes real output tables into `augment/functions.json`; `coverage.py` reports documented vs undocumented functions. `binary-sizes-snapshot.py` (wrapped by `scripts/snapshot-binary-sizes.sh`, part of `refresh:snapshots`) is the **sole** source of `generated/compatibility.json` — it probes `haybarn-extensions.query.farm/community`, the distribution the in-browser REPL actually installs extensions from, for the platform/WASM matrix and binary sizes. `extension-diff.py` used to write that same file from a second, different source (`community-extensions.duckdb.org`, DuckDB's upstream registry); whichever tool ran most recently silently won, which could make a WASM-less extension show a "Try it" button (or vice versa) depending on run order. `extension-diff.py` no longer touches `compatibility.json` at all — run `binary-sizes-snapshot.py` (or `refresh:snapshots`) to update it.

## Deployment

GitHub Actions (`.github/workflows/deploy.yml`) deploys to the `query-farm-website` Cloudflare Pages project via wrangler (direct upload — the project is NOT git-connected on the Cloudflare side):

- Push/merge to `main` → production at https://query.farm
- Pull requests → preview at `https://<branch>.query-farm-website.pages.dev`, gated behind Cloudflare Access (email one-time PIN; allowed emails managed in Zero Trust → Access → Applications)
- Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` (GitHub repo secrets)
- Manual escape hatch: `npx wrangler pages deploy dist --project-name=query-farm-website --branch=<name>`

## Architecture

### Extension data: two-tree merge

Each extension lives in `src/data/extensions/<slug>/` with two parallel trees that merge at build time:

- `generated/` — machine-introspected, never hand-edit (`functions.json`, `compatibility.json`, `usage.json` load counts). Regenerated by `extension-diff.py` / `usage-snapshot.py`.
- `augment/` — hand-authored curation: `metadata.json` (display name, category, status, quickStart — presence of this file auto-registers the extension, no manifest needed), `functions.json` (descriptions, categories, examples with baked `outputTable`), `categories.json`, `technical-overview.json`.
- Optional `technical-details.mdx` and `cookbook.mdx` are lazy-loaded if present.

Key modules in `src/data/`:
- `extensions.ts` — `import.meta.glob()` discovery → the `Extension[]` list (filters drafts and the `example` template)
- `extension-loader.ts` — `loadExtensionData(slug)` merges generated + augment and validates against Zod schemas; **schema mismatch is a hard build failure by design**, not silent data loss
- `extension-merge.ts` — collapses polymorphic function overloads (hundreds of signatures → one card with a type union)
- `schemas.ts` — Zod schemas for every data shape (functions, pragmas, secrets, macros, filesystems, storage, log types, pricing)

Rendered by `src/pages/products/extensions/[slug].astro` (`getStaticPaths` over the extension list) using the `src/components/docs/DuckDBExtension*` component family — one component per DuckDB object type (function, pragma, secret, macro, filesystem, storage, log type).

### In-browser REPL (React islands)

`src/components/repl/ExampleShellMounter.tsx` mounts on extension pages, finds `<pre data-language="sql">` blocks, and injects "Try" buttons that open `ExampleShell.tsx` — a live DuckDB shell. `src/lib/repl/duckdb-boot.ts` boots a singleton `@haybarn/haybarn-wasm` engine from **unpkg** (single-threaded `eh` bundle — the site is NOT cross-origin isolated, so no `coi`), installs/loads the extension once per page, and gives each shell an isolated in-memory `ATTACH` session. It is unpkg and not jsDelivr deliberately: the package's unpacked size exceeds jsDelivr's 150 MB limit and 403s. Only xterm/Arrow/readline come from jsDelivr. Results come back as Arrow IPC and are rendered terminal-style via `src/lib/repl/format.ts` + `shell-table-renderer.ts`.

### Other dynamic routes

- `/blog/[slug]` — content collection defined in `src/content.config.ts` (glob loader over `src/content/blog/*.md`; frontmatter: title, description, pubDate, author, tags, draft, heroImage)
- `/haybarn/status/[version]` — per-DuckDB-version build status, driven by `src/data/haybarn-versions.ts` and the `haybarn-status.query.farm` API

### Conventions

- Astro components by default; React (`.tsx`) only when client-side state/interactivity is required (currently just the REPL).
- Layout chain: `BaseLayout` (head/nav/footer) → `PageLayout` (section container) or `BlogPostLayout`.
- Theme: the **Strata Sun** system — `sun` / `soil` / `rock` / `field` scales, plus `pipe-1..6` (homepage stage bands only) and `cat-*` category tints, in `src/styles/global.css`; custom Shiki `farmTheme` for code blocks in `astro.config.mjs`. Type is **Petrona** (display) + **Commissioner** (body) + **JetBrains Mono** (code), all three declared as `--font-display` / `--font-sans` / `--font-mono` in `global.css`. Petrona **replaced Fraunces** during the migration and has no `opsz`/`SOFT`/`WONK` axes — only weight and a real italic — so headings are 600 at every level and take their size from the ordinary Tailwind ladder. Any `font-variation-settings` naming those axes is dead code. **`DESIGN_BRIEF.md` (repo root) is the authority** — read it before changing any styling. Four rules from it bite constantly: figures are always tabular Commissioner and never Petrona (which ships no tabular set) — and the inverse, `.qf-figure` never goes on prose; *mid*-tone bands take ink text, not cream (cream on `pipe-3` is 2.7:1 and fails); code always sits on `rock-900`, never on a coloured band; and `Button.astro` plus `.qf-eyebrow` are single sources of truth, so hand-rolling either drifts on padding and hover. The old `earth-*`/`harvest-*`/`grain-*`/`duck-*` scales are gone.
- Page families: the six-band colour run is **homepage-only**. Every other page uses one of five templates and gets the palette only as a 5px `.hairband`, a single dark slab, or not at all. See `DESIGN_BRIEF.md` §5–6. Commercial landings — `/haybarn`, `/vgi`, `/products*`, `/consulting` — are **Family D** and share one shape vocabulary (`WRAP` / `CARD` / `EYEBROW` / `LEDE` consts, `PageHead variant="section"`, exactly one full-bleed `bg-pipe-6` slab, placed last). Copy those constants from a sibling page rather than re-deriving them.
- `SIGNATURE_RENDERER_GUIDE.md` (repo root) is current documentation for how function signatures are rendered from structured data (no HTML-in-JSON) — read it before touching `FunctionSignatureRenderer.astro` or the function-doc components. The other root-level files (`COMPONENT_REFACTORING_ANALYSIS.md`, `CATEGORY_FUNCTIONS_INDEX_EXAMPLE.md`, `STICKY_TOC_DEMO.md`) are historical working notes.

### VGI SDK documentation (Starlight, `/vgi/docs/`)

A single Starlight section serves the shared, language-neutral **Concepts** pages (`/vgi/docs/concepts/`) plus one subsection per SDK — **Python** (`/vgi/docs/python/`), **Go** (`/vgi/docs/go/`), **TypeScript** (`/vgi/docs/typescript/`), **Rust** (`/vgi/docs/rust/`) and **Java** (`/vgi/docs/java/`). Concepts is deliberately one copy, not one per language; each SDK section links into it. `/vgi/docs/` is the landing page over all of them.

**`src/lib/vgi-docs.ts` is the language table** — slug, name, icon, repo, blurb, and the sidebar group label it maps to. Adding a language is a row there plus its sidebar group in `astro.config.mjs`; four things read it and must agree:

- `src/starlightRouteData.ts` — a Starlight **route middleware** that scopes the sidebar. `astro.config.mjs` declares every section in one `sidebar` tree because that is the only place Starlight accepts one, so that tree is the *catalogue* and the middleware is the *view*: on a Go page it keeps Concepts + Go, unwraps the language group to the top level, drops the rest, and re-derives `pagination` (computed upstream from the full tree) and the `<title>` (`… | VGI Go`). Without it every page shipped all five languages — 179 links, ~53 KB, about two thirds of the markup.
- `components/starlight/Sidebar.astro` — the language switcher above the tree. **Its CSS lives in `starlight-shell.css`, not in the component**: the chips are anchors inside `#starlight__sidebar`, and that file's ID-specificity link rules beat any scoped class, so a local `display: flex` loses to `display: block` and each chip stacks its icon over its label.
- `components/starlight/DocsSubNav.astro` — the breadcrumb `VGI Docs › <language> › <group> › <page>`, every crumb but the last a link (group crumbs resolve to the group's first page).
- `content/docs/vgi/docs/index.mdx` + `components/starlight/DocsHome.astro` — the landing page.

The **Go** API reference is generated by `scripts/gen-api-go/` (`go/doc` → MDX, run via `gen-api-go.sh`); pages are curated topic groups because vgi-go is one package with ~600 exported symbols. Runnable Go examples live in `vgi-go/examples/docs/`. See §8 of the guide.

The **TypeScript** API reference is generated by `scripts/gen-api-ts/` (TypeScript compiler API → MDX, run via `gen-api-ts.sh`); pages are curated topic groups because `@query-farm/vgi` is one barrel over ~65 files. It parses with **this** repo's `typescript` devDependency — vgi-typescript is on TypeScript 7, the Go-native port, which ships no JS compiler API. Runnable examples live in `vgi-typescript/examples/docs/` with a `verify.sh` that runs them against a real engine. `api/index.mdx` is hand-written and not emitted by the generator. Unlike Go and Java, vgi-typescript documents its surface on interface **properties** rather than on declarations, so the generator renders each interface as a **field list** (name / type / that property's JSDoc as prose) instead of printing the declaration whole — printing it whole buried every explanation inside a code block and left the page with no prose at all. See §9 of the guide.

The **Rust** API reference is generated by `scripts/gen-api-rust/` (rustdoc JSON → MDX, run via `gen-api-rust.sh`); pages are topic groups, and the surface spans three crates (`vgi`, `vgi-protocol`, `vgi-client`) which are documented and merged — `CacheControl` lives in vgi-protocol, so reading only `vgi` renders an empty cache page. **rustdoc JSON is nightly-only**, the one build requirement the other generators lack. Signatures are sliced from source via rustdoc spans rather than reconstructed. Runnable examples live in `vgi-rust/examples/docs/` with a `verify.sh`. See §10 of the guide.

The **Java** API reference is generated by `scripts/gen-api-java/` (Java source parser → MDX, run via `gen-api-java.sh`); it needs no JDK or Gradle, only the `~/vgi-java` checkout. javadoc's doclet emits an HTML site rather than data, so declarations are parsed directly — and javadoc prose is HTML, so `<p>/<ul>/<h2>/<pre>` are converted to Markdown before MDX escaping. Java's runnable examples are `vgi-java/examples/docs/` (the `:examples:docs` Gradle subproject, built against `project(":vgi")`), with a `verify.sh` like the other sections. See §11 of the guide.

The **Python** docs are generated from the `vgi-python` package: the prose is converted from `vgi-python/docs/` and the API reference is generated from source via Griffe — so those pages are **regenerated, not hand-edited**. The generators/converters live in `scripts/` (`gen-api-mdx.py` + `gen-api.sh`, `mkdocs_to_starlight.py` + `convert-vgi-docs.sh`, `test_api_completeness.py`), the Starlight wiring is in `astro.config.mjs`, and the overrides/styles are under `src/components/starlight/` and `src/styles/starlight-*.css`. **`VGI_DOCS_GUIDE.md` (repo root) documents the whole system** — the integration, both generators, the example/source-of-truth flow, and the MDX/Starlight gotchas (Expressive Code doesn't process Markdown fences, GFM pipe tables aren't parsed, raw-HTML/escaping rules, the subnav + `--sl-nav-height`). Read it before changing anything under `/vgi/docs/`.
